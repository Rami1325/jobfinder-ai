### The tailor's LLM calls

**The pipeline reports its stages as it starts them** (2026-09-23, PLAN 31.3/2). `tailor_resume` takes an optional `progress` callback and calls it with each of `TAILOR_STAGES`, `plan` (score before ∥ `plan_cv`), `rewrite` (the TAILOR call), `facts` (invented roles cut, `fit_to_pages`, the guard), `voice` (the audit and the humanizer) and `rescore` (the keyword floor, the shortlist, the Arabic and numerals passes, `score_after`), at the line where each begins, so a page can say what is happening now and never what it guesses. The plain route and the kit drain pass nothing and are unchanged. `POST /tailor/stream` sends them as SSE frames (`cost-and-quota.md` for its charge, `llm-boundary.md` for its metering); `frontend/src/lib/tailorStages.ts` mirrors the tuple and check-mirrors 64 holds the two equal, while smoke drives the stream and checks the frames arrive in that order.

**The tailor runs one pair of LLM calls concurrently** (`score_before` ∥ `plan_cv`) — they read the same inputs and neither reads the other. There used to be a second pair, `review_credibility` ∥ `score_after`; **CREDIBILITY was removed** (below), so `score_after` runs inline — a one-member pool is a thread spawn and a context copy for zero concurrency, and an inline call is natively visible to `metering`. Both surviving submits go through **`copy_context().run`, never a bare `pool.submit`** — a worker starts from an EMPTY context, so two of the four calls would become invisible to `metering` and their tokens would vanish from `usage_log` silently, with the tailor still returning a perfect result. **Behaviour cannot pin that**: this suite runs on `StubClient` and only `OpenAIClient` calls `metering.record()`, so a driven assertion reads 0 calls whether the submits are right or wrong — it is pinned by parsing the AST instead. The same trap bit the A/B harness's own latency probe, which stored call timings in a `threading.local()`: `copy_context` propagates contextvars and knows nothing about thread-locals, so the probe lost the pooled calls and reported a 7.3 s pipeline the wall clock measured at 14.4 s. It is a `ContextVar` now.

**The analysed JD a tailor is handed is measured (P30-PASS-SIZE, 2026-09-21).** `TailorRequest.jd` is a `JDModel` straight from the client body, and `fit_score_user`, `plan_cv_user` and `tailor_user` take it as `jd_json`, which the prompt-input guard now caps at `4 × max_jd_kb` (derived from the analyser's input cap — why, in `llm-boundary.md`). A real analysed JD cannot reach it: smoke 14b-6 builds the largest ad the analyser accepts copied whole into responsibilities, qualifications and keywords (97 KB), and 32.6 tailors that JD over `/tailor`. Only a crafted body can. When one does, `score_before` raises the 413 out of its pool worker (`plan_cv` swallows its own and returns None, which is harmless: the tailor is refused anyway); `charged` gives the monthly use back, and the daily `tailor` count it spent is not refunded, which is the daily caps' rule for every refusal.

**`CREDIBILITY` IS GONE — removed 2026-08-31, not deferred.** It produced **7–18 advisory flags per tailor** (mean ~13 over 12 real runs) for **31% of the wall clock**, and the owner's answer to "do you ever read them" was no. Removal beat deferral on the very rule that made deferral awkward: a deferral needs a TRI-STATE (after it, an empty list means both *reviewed, nothing flagged* and *not yet reviewed*), and a deletion has no third state. **Keeping the field defaulting to `[]` would have MANUFACTURED that ambiguity** — `[]` on a new result meaning "we no longer do this" and the identical `[]` on last week's kit meaning "reviewed, nothing flagged", rendering the same blank for two different facts. So the field is gone from `TailorResult` entirely. That is safe because **`TailorResult` carries no `model_config`, so Pydantic v2's default `extra="ignore"` applies** — an old stored kit whose `result_json` still holds `credibility_flags` validates cleanly and the key is dropped (verified, not assumed). Nothing rewrites `tailor_kits.result_json`, so the historical flags survive byte-for-byte in the column and are recoverable if this is ever reversed; they simply stop rendering.

### The fabrication guard, the ledger and the flat skills surface

- The fabrication guard runs **after** every tailor call, not just in tests. If the LLM invents an employer/title/date/credential/number, the API still returns it but `fabrication_flags` will be non-empty. The UI surfaces these as warnings. Numbers are read from experience, military, the summary **and projects** — projects were missing until Phase 20 and the gap was invisible precisely because it was symmetric (the guard rebuilds the ledger the same way from the tailored resume, so nothing ever went red). Skills are still deliberately unguarded: the tailor is explicitly allowed to adopt the JD's wording for something the candidate has, so a strict check would false-positive on exactly that.
- **The fabrication guard can say "no new claims detected". It can never say "verified".** `_known` is containment in *either* direction, so a ledger holding `"5"` clears an invented `"250"`, and skills are unchecked by design. Nineteen strings claimed otherwise until Phase 22.
- **`ResumeModel.skills` is the flat surface everything SCORES; `skill_groups` is presentation.** The scorer's keyword coverage, the ATS scan, the ATS x-ray and resume health all read `skills` and none of them knows groups exist, so `skills` stays populated as the flat union of every group's items — enforced by a `model_validator` on `ResumeModel` rather than at each call site, because an LLM response, a stored JSON row and a test fixture all need the same guarantee. The validator only ever ADDS; the one place that removes a skill (`length_budget._drop_unmatched_skill`) drops it from its group too, or the union would resurrect it on the next round-trip and the trim would silently do nothing. Two consequences worth keeping: **nothing may be hidden** — a skill no group claims is still rendered, in a trailing unlabelled block, because an invisible skill is an x-ray "missing" on the file we told the user to send; and **group labels are not claims**, so the fabrication guard leaves them alone for exactly the reason it leaves skills alone. A tailored CV comes back from the MODEL flat — `tailor.py` strips `skill_groups` from the raw TAILOR response, for the measured reason recorded there — and is RE-GROUPED at the end of the pipeline by `skills.regroup_skills`, deterministically, under the master's own labels. See **The default template** in `rendering.md`.
- `FactsLedger` is derived from the **original** resume (before tailoring) and is never mutated. It is the source of truth for the guard.
- `ResumeModel.headline` (the target-title line) is a **claim**, so the guard reads it — but only for rank. The ledger keeps `headlines` separate from `titles` on purpose: running the headline through the generic title diff would flag every honest reposition and teach users to ignore flags. Only a seniority word no real title carries is a fabrication.

### Keyword preservation — the floor under the tailor

- **The tailor deletes JD keywords the candidate genuinely has, and until 23.7 nothing repaired it.** `score_after` MEASURED the drop and reported it. Five independent mechanisms, four reproduced: the model's own skills shortlist (TAILOR rule 2 orders curation — "drop irrelevant noise", "DROP whole areas it never mentions" — and every one of those rules runs ONE WAY; the self-check verified output ⊆ original and nothing verified the reverse); `length_budget` removing the prose that carried the only occurrence; `cv_planner` dropping the carrier project before the budget runs; `drop_invented_roles` cutting a promoted row; and the humanizer, whose acceptance gate weighed fabrication, voice and pages but never coverage. Measured: coverage fell **60.0 → 40.0**, deleting Kubernetes and Terraform from a candidate who lists both. The prompt work and the humanizer gate narrow the two biggest mechanisms; neither is a guarantee — "the LLM is *asked* to curate, but asked is not guaranteed".
- **It may only ever write a string that already exists byte-for-byte in `original.skills`.** Never synthesizes, never adopts the JD's spelling for something the candidate lacks, never writes prose. A keyword whose only home was a sentence is REPORTED, never repaired: re-inserting a sentence either duplicates a claim or grafts a token into the model's own prose, which the fabrication guard structurally cannot see. The argument is provable rather than argued — `build_facts_ledger` never reads `resume.skills`, so a restore cannot create a flag. **If anyone extends the guard to restore a bullet, that argument collapses and `check_fabrication` must be re-run for the restore too.**
- **A REPAIR IS NOT A MEASUREMENT.** Three functions, three jobs: `preserve_keywords` REPAIRS (its lists describe the resume IT returned, which the caller then trims), `lost_keywords` MEASURES (a rank comparison — no `model_copy`, no budget, no carrier search), and `report_restore` describes what SHIPPED, after the refit and the back-off. Driving the changelog off the repairer told two lies at once: "Put back: X" for keywords a later trim removed again, and — because the caller took only the repairer's *unrepairable* list — a keyword the refit deleted that the repairer had just proved it COULD restore landing in NEITHER list. Measured: 57 JD hard skills all in the master, 25 restored, 32 still lost, changelog naming 7.
- **One matcher, one answer, on BOTH sides of the trade.** `length_budget._drop_unmatched_skill` protects an entry when `scorer._keyword_present` reads it as carrying a JD keyword — the SAME call the carrier search selects with. It used to protect on whole-token overlap, which is a different question: every carrier matched through the substring branch — i.e. every Hebrew one, since ב/ל/ה/ו/מ/ש are word characters, and `Postgres` is inside `PostgreSQL` — shared no token with the JD and was fully eligible for a trim that removes the LONGEST unmatched entry. Measured on a Hebrew master: 10 carriers restored, 9 removed again under "dropped skills the job never asked for", the changelog still claiming they had been put back. **The honest guarantee is NOT "the budget cannot undo the restore":** the entries the guard writes are the entries the skills trim refuses to touch, and anything the budget removes anyway is REPORTED as `trimmed`, because the report is measured on what ships.
- **A keyword may not be bought with the page limit.** When the post-restore refit cannot get under `hard_max_pages` and the pre-restore CV was inside it, `shed_restored` hands entries back — longest first, stopping the moment the budget holds. `length_budget.OVERFLOW_NOTE` is public so that note can be RETRACTED when the back-off makes it false: a report carrying both "could not get below 3 pages" and a 3-page CV is worse than either. `shed_restored` takes its page measurement as a CALLABLE — the guard stays free of the renderer for the same reason it stays free of the LLM.
- **Four loss classes, because one sentence cannot be true of all of them.** `prose` (the original said it in wording this module does not rewrite), `partial` (the skills list holds part of the phrase; those entries ARE put back and the job's phrase still is not covered), `cap` (`MAX_RESTORED` spent — the only class a bigger number fixes) and `trimmed` (the page budget took it back — the only class WE caused rather than the user's wording).
- **The report goes through the CHANGELOG, never a new `TailorResult` field.** A changelog is a log of ACTIONS TAKEN, so its absence on a row written before this guard existed means "no such action", which is TRUE. A `kept_back: []` field would mean "nothing was lost" on every one of those rows, which is FALSE. "Put back:" names the ENTRIES, not the JD's phrase — they are different strings, and `REST APIs` restored from `['REST','APIs']` named something that appears nowhere in the shipped CV. The copy may never say "guaranteed", "verified" or "all keywords preserved" — smoke-pinned.
- **ONE call site, inside `tailor_resume`, and its POSITION is load-bearing.** After the humanizer (the last stage that can delete a keyword) and before `score_after`, so it describes the resume that ships. A second site would classify on a DIFFERENT gate and contradict this one about the same resume — the geo-restriction correction in a new costume. A smoke check walks every module under `app/` and asserts `core/tailor.py` is the only importer.
- **A source pin that greps cannot tell an import from a mention.** `keyword_guard` imports from `app.core.scorer`, and `scorer` imports `get_llm_client` — so appending `fit_score` to that existing import line puts the model in charge of the CV while every substring pin stays green. Both pins parse the AST: the imported-from-scorer set must be EXACTLY `_keyword_present`, `_resume_text`, `_tokens`.
- **It measures a WIDER set than the score does, deliberately.** `_jd_keywords` reads `hard_skills + keywords + preferred_skills`; `scorer.keyword_analysis` reads the first two. A preferred skill the candidate HAS and we deleted is still a deletion — but widening `keyword_analysis` would change the visible coverage denominator everywhere, a behaviour change with no defect behind it. The consequence to keep: a restored preferred-skill raises no visible number.
- **On a clean pair it returns the SAME OBJECT.** The caller keys the refit, the voice re-audit and the changelog entry off a non-empty `restored`, so the identity check pins all four at once.
- **`voice_report` describes what SHIPPED, so a restore forces a re-audit** — carrying the humanizer's `revised`/`fixed` across by hand, or the record of the only stage that rewrote anything is silently erased.

### The page budget keeps the bullets that fit the job (2026-09-22)

- **`_trim_project_bullets` kept `bullets[:keep]`, the first ones, whatever the job.** A project's first entry is its tech-stack line, so the "kept the top 2 bullets per project" step shipped every project as its stack line plus its first prose bullet. The owner's application to an "AI-First QA Automation Engineer" posting (Unframe) lost every testing bullet his master held: the smoke suite, "fourteen defects that had passed a green test suite" turned into CI checks, "pytest, Vitest and Playwright suites" behind 30 endpoints, the HAUL tap-target tests. All of them sat later in their lists. Found by reading the downloaded PDF against the master, not by any metric, since coverage was already high from the skills list.
- **Now:** the stack line (a bullet with two or more " / " separators) stays whenever two or more bullets do, the other slots go to `bullet_relevance` (the posting's terms through `scorer._keyword_present`, weighted 3/2/1 like `_relevance_parts`, half for a partial hit), and **ties go to the earlier bullet**, so a job that names none of the bullets keeps exactly what the old rule kept. The kept bullets stay in the candidate's own order: the module still only REMOVES. With `jd=None` it is the old first-N rule.
- **A testing role adds `TESTING_BULLET_BONUS` (6, two required skills) to a bullet that shows testing work**, because the JD's terms alone cannot see it: "an offline smoke suite of over 700 checks … pinned to a defect that actually shipped" never says "test" and scored 0. A testing role is the posting's title (QA, SDET, test, tester, quality assurance) or a test framework among its REQUIRED terms. **Bare "automation" is deliberately not one**: this market is full of business-automation roles (n8n, lead pipelines). The evidence pattern is how engineers describe test work (tests, suites, assert/asserting, smoke, regression, coverage, e2e, pytest, Playwright…), and "end to end" in prose ("built the platform end to end") is not evidence.
- **The pin is measured, not taste.** Without it, pure relevance dropped stack lines and cost 2.1 coverage points on the Unframe posting (66.7 → 64.6), because the stack line is the entry's densest keyword line.
- **Measured before it shipped, $0**: the real `fit_to_pages` on the owner's real master (production, 17 projects), each job given its top 6 projects (the tailor hands the budget about 5, not 17), over the six recorded A/B postings plus Unframe. Decision rule written first: coverage lower on no non-QA job, pages higher on none, and on Unframe the testing bullets survive. Result: coverage lower on **none** (up on four: +2.0, +2.7, +2.9, +11.6), pages unchanged everywhere, and on the real Unframe CV's five projects testing bullets **4 → 7** with coverage **64.6 → 68.8**. The first measurement ran on all 17 projects, where the budget cuts to one bullet and keeps a different project SET per arm, so a positional diff paired the wrong projects: compare kept bullets by project NAME.
- Smoke 18-ter pins it (8 checks), each probed red against its own planted defect (first-N back, no bonus, no pin, kept bullets re-sorted, "end to end" counted, bare "automation" as a testing role). Not done: `_trim_experience_bullets` still drops the LAST bullet on the premise that the tailor orders experience bullets by relevance.

### The proposal writer — a bid for a gig the user pasted (2026-09-28)

"Freelance, the small version" (the owner approved it on 2026-09-28 from the freelance research). Freelance marketplaces cannot be read legally (Upwork's API terms forbid monitoring, Freelancer.com's user agreement forbids automated access, Guru and Malt put up bot walls, Fiverr has no request feed) and Israeli boards carry almost no freelance tech work, so there is no feed: the user finds a gig where they already look (XPlace, Upwork, Fiverr briefs, a Facebook or WhatsApp group) and pastes it. The cover letter's twin writes a short bid for it.

- **Where.** The letter card (`components/CoverLetter.tsx`, on a job's page and a batch draft's page; `/app` has carried no letter since PLAN 31.4/4) offers **Letter / Proposal**, two 44 px options, over ONE pass per posting. Tools has **Proposal for a gig** (`/tools/proposal`, `pages/tools/ProposalToolPage.tsx`): paste the gig, type a rate if you want it in, Write my proposal. That first write sends no analysis (`jd: null`): the server reads the gig and hands the reading back, and from then on the proposal is the letter card itself, in proposal mode (`kinds={["proposal"]}`), so a change rides the pass by the card's own tested rules (check-mirrors 36). Editing the gig makes it a new gig. The page keeps the gig, the rate and the proposal in module state for the tab's life, so leaving to paste it somewhere and coming back finds it.
- **The prompt, `PROPOSAL`** (`Task: PROPOSAL.`, a `StubClient.complete_text` branch; the cover letter still has no tag and still gets the letter). 80-180 words of plain text in the GIG's language: `core/lang.prose_language` (a share of words, the resume rule, the twin of `lib/lang.ts::proseLanguage`), else the analysed posting's language, never the resume's, since a Hebrew freelancer bidding on an English Upwork post answers in English. It opens on the client's problem, names ONE past result from the resume as the resume states it, proposes ONE concrete first step, and ends with ONE question; no template phrases (XPlace itself tells freelancers to avoid "template proposals"). The gig is framed as data (a stranger's post). It never writes a rate, a price, a timeline or availability: where the gig asks for one, it writes a line of placeholders before the question ("Rate: [your rate]. Start: [your availability]. Estimate: [your timeline]."), and a rate the user typed goes there verbatim instead.
- **The floor under the prompt, `core/proposal_terms.py`**, because asked is not guaranteed. Deterministic (AST-pinned to `__future__`, `re`, `dataclasses`; one importer, `core/proposal.py`). Every money amount the user did not type becomes `[your rate]`: an amount with a time tail ("$45/hour", "250 לשעה") is a rate that only the rate box clears, and one without ("saved $200K") may be a past result, cleared when the resume carries the SAME words. Every duration becomes `[your timeline]` unless the resume carries the same words ("in 3 weeks") or the rate box its number, so "5 days" is not cleared by "5 engineers". A start or hours commitment ("available immediately", "40 hours a week", "זמין מיד", "20 שעות בשבוע") becomes `[your availability]`, the verb kept. A rate placeholder is filled with the typed rate. Hebrew placeholders for a Hebrew proposal (`[התעריף שלך]`, `[לוח הזמנים שלך]`, `[הזמינות שלך]`). Each replacement is reported (`replaced`), and so are the brackets left (`placeholders`) and every number neither the resume, the gig nor the rate carries (`unverified`, by containment).
  - **What it can say, and what it cannot.** No amount, duration or availability phrase these patterns know is left that the rate box or the resume does not carry. Never that none was invented: a commitment in words the patterns do not know passes, and `unverified` is compared by containment, the fabrication guard's weakness. The cover letter has no check of its own (it is `complete_text`, and the fabrication guard reads a ResumeModel, not prose), so this floor is the proposal's only one.
  - **False positives pinned beside each catch**: "5 years of experience", "5 daily standups", the resume's own "saved $200K a year" and "in 3 weeks" (and "תוך 3 שבועות"), and the client-facing questions "כמה שעות בשבוע אתם צריכים?" / "How many hours a week do you need?" are left word for word. `כמה` and `מספר` are not number words here for that reason.
- **On the page.** The text is an editable box in its own direction (`dir="auto"`, 16 px on a phone), grown to its text; Copy copies what is in it; Write it again, More specific and Shorter ride the pass. Under it: "Fill in before you send:" with the brackets the server reported that are still in the text; "Not in your resume, check before you send:" with the unverified numbers still in it; one quiet line when the floor took something out; and always "You send it on the platform yourself. JobFinder never signs in to or applies on Upwork, XPlace or any other marketplace." Nothing says verified. An edited letter or proposal is saved on the job's row (or the kit) when the box is left, like a written one.
- **Real-model check (2026-09-28, 6 calls, `gpt-5.4-mini`, the local `.env`'s model; a scratch script, never CI)**, on the owner's saved resume, a hand-built minimal analysis per gig: XPlace project 216056 (Hebrew, a Browser Automation Agent PoC, ₪10,000 fixed, "2-4 weeks"), a typical Upwork post (English, a Playwright scraper + FastAPI, asking for the hourly rate, a start and an estimate), and a short English React fix. Every answer was in the gig's language, 121-147 words, opened on the client's problem, named one resume project (JobFinder AI, The Daily Catch), proposed a first step and ended with one question; none wrote a rate, a timeline or a start, and the floor replaced nothing. A typed "$55/hour" came back verbatim where the gig asked; a typed "250 ₪ לשעה" was left out where the XPlace gig did not ask. **The first prompt left out the rate, start and estimate the Upwork post asked for** instead of writing placeholders; the rule was sharpened to "answer each one it asks in ONE short line before the question", and the rerun wrote "Rate: [your rate]. Start: [your availability]. Estimate: [your timeline]." 2,548-2,933 prompt tokens and 169-284 completion tokens a call (16,362 and 1,256 in all), 1.7-4.2 s. Two things the owner may want to know: a Hebrew proposal quotes the resume's English pipeline list verbatim ("parse, analyse, … and credibility review"), because the prompt asks for the resume's own words; and precision beyond six calls is not measured.
- **Measured with Playwright** (iPhone 13, stub model, a scratch copy of the local DB, a plan-free friend) at 390 × 664 and 360 × 664, en and he, and 1440: no page overflows sideways; the gig box, the rate box, the Write button, the Letter / Proposal options and every button on the card are 44 px (36 / 34 from `lg`), the boxes 16 px text. With the keyboard up (390 × 340) the gig box was 281 px down with 59 px of it in view; it now scrolls itself under the header once the keyboard is up and sits at 160-330 of 340. After Write the keyboard goes down and the proposal card is brought to the top (160 px) on every run: a frame scheduled from the write had scrolled to nothing about half the time, because React had not committed the card yet, so the scroll now runs in an effect after it renders. The Tools card reads "Proposal for a gig · A short bid for a freelance gig" in one 75 px row at both widths. A stub artifact to know about: the stub's "[stub proposal]" marker is itself a bracket, so "Fill in before you send" lists it; and the stub's analysis ignores its input, so every stub gig is one posting and shares one pass.
- **Deliberately not built**: a feed or a marketplace filter (see above), sending anything (JobFinder never logs into or applies on a marketplace, the LinkedIn rule extended), rate fields beyond the one optional box, a bid-state tracker, and XPlace as a source, which waits for XPlace's written permission (PLAN.md).

### Phase 29 (spec 07) — the Arabic preference, and numerals

Both shipped in **Phase 29** (2026-09-13) and both run inside `tailor_resume`, never touching the master. The
phase's intro, its review provenance and its deferred / known-open list are in `accounts-and-auth.md`.

**The Arabic preference** (owner request, spec 07 / R1).
- **Opt-in and OFF for every user; an unreadable preference reads as OFF**, because the switch REMOVES a true fact from a document and must fail toward the one the user uploaded. It lives in `users.resume_prefs_json` behind `GET`/`PUT /profile/resume-prefs`, and `_wipe_user_rows` clears it: it implies the user's ethnicity.
- **"Is this job in Israel?" is deterministic** (`job_market.israel_market`, AST-pinned to no model, no network, no clock): a Hebrew posting, or an Israel/city token in the location or text. **Latin tokens are bounded** (Lod is inside "lodging"); **Hebrew tokens are substrings** (`בתל אביב`); "us" the pronoun is not the US; and **a posting naming no place is UNKNOWN, never "not Israel"**. `analyze_jd` stamps `JDModel.market` (`IL` / `other` / `""`) AUTHORITATIVELY over anything the model said, `stamp_market` only upgrades, `POST /jd/analyze` takes an optional `location`, kits stamp from the stored location without changing the one-argument `AnalyzeFn`, and the Jobs page prepends `Location: <location>` to the posting text rather than adding a `tailorStore` field (check-mirrors 12/13 derive that store's reset lists).
- **It applies only when the preference is on AND the market is IL AND the job does not ask for Arabic** (any requirement, preference, keyword, qualification or responsibility naming it; "selling into Saudi Arabia" is not asking). The pref on + the job asks → kept, "Arabic kept: this job asks for it"; unknown market → kept, "Arabic kept: we couldn't tell this job is in Israel", so the owner can remove it by hand; abroad, or a resume with no Arabic → nothing is said.
- **With the decision off the TAILOR message is BYTE-IDENTICAL to the call that never passed it** (pinned, driven); when it applies the message gains one instruction and nothing else.
- **Removal is deterministic, after the model, before `score_after`**: `languages` entries, and `skills` AND `skill_groups` (the two-field write, or the union validator resurrects it). A prose LIST form is removed cleanly; any other mention is REPORTED by section ("Arabic is still mentioned in your experience; edit it before sending") and left word for word. "Arabic translation", "Judeo-Arabic" and "United Arab Emirates" are not Arabic entries. The master resume is never touched.

**Numerals, and the guard re-check** (owner request, spec 07 / R2).
- **Quantity words become digits in TAILORED prose only** (summary, headline, experience/project/military bullets, project descriptions) — never titles, companies, dates, skills or the master. English: two..ninety-nine and hyphenated compounds, "one" only before a unit noun, never before of/or/and/to/the/than; a proper noun ("Seven Bridges"), "one or two", "twenty five" and a fraction stay words. Hebrew: 2-10 only as a standalone word before an allowlisted noun — `שבע`/`שש` are ordinary words, `חמש עשרה` is fifteen, a prefixed form and `שנתיים` are untouched. Idempotent, pinned.
- **The fabrication guard reads DIGITS only, so a number the model invented in words ("fifteen engineers") passed it unseen.** After a conversion the guard is re-run against a `model_copy` of the ledger whose `numbers` also hold the ORIGINAL resume's quantity phrases, built at runtime from the original resume because the kit path passes a STORED ledger. Pinned as a triple: an invented "fifteen" flags as `15`; the candidate's own "five teams" shipped as "5 teams" raises nothing; and the unextended ledger WOULD flag it, so the extension is what clears it. The ledger itself is never mutated.
