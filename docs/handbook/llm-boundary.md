### Prompt input bounds, and honest size errors

- **`app/llm/prompts.py` is the input boundary, and that placement is measured.** All 22 `complete_json`/`complete_text` calls in `app/core` and `app/parsers` build their user message with a `*_user(...)` builder — no exceptions — so the builders are the one place unbounded text becomes prompt text. Guarding the STORED master resume is not enough: **25 request models take a `resume: ResumeModel` straight from the client body** (tailor, cover letter, every interview route, LinkedIn, the review's rewrites…), so `PUT /profile/resume` is one of twenty-six doors. The guard is a `@_bounded` decorator that discriminates by ARGUMENT NAME, which is why `resume_json` / `raw_text` / `jd_text` must stay consistent — a new builder naming its parameter something else is silently unguarded, and a smoke check pins exactly that.
- **It is NOT in `client._create`.** That sees the assembled string and would slice a resume's JSON mid-object, handing the model a truncated document at the one boundary the fabrication guard cannot see (it diffs the tailored resume against the ledger, never the prompt).
- **Never truncate the user's own document — refuse it (413). Truncate only text the user neither wrote nor saw.** A silently shortened resume is data loss in the most valuable object the user owns, and here it does not stay a warning: the parsed model is live in the store the moment it returns, `PUT /profile/resume` versions it into one of 20 evictable slots, `useSaveMasterResume` swallows every error, and nine pages read it from a module cache. By the time the notice is read, the damaged CV IS the master. Scraped page text is clipped silently at its source (`job_match._clip_jd`), so it arrives under cap and the builders' refusal never fires on it — which is also why nothing needed a "we truncated this" response field.
- **Sized in UTF-8 BYTES, never characters.** Hebrew costs ~1.9 bytes/char against English's 1.0, so a character cap silently grants the primary market roughly twice the tokens for the same number. Bytes halve that gap with no `detect_language` branch to get wrong on the mixed Hebrew-prose/Latin-skills resume that is the Israeli norm. Bytes do **not** fully normalise it, and the caps are therefore sized against the Hebrew case.
- **A cap is a guard rail, not a budget**: it must fire on a 500-page PDF and never on a real CV (`config.py` records that a master can legitimately run ~30 rendered pages). The legitimate-but-still-too-big document is caught by `ContextWindowExceeded` instead. `PUT /profile/resume` carries a load-bearing carve-out — **a save that SHRINKS an already-oversize master is always allowed**, or anyone whose resume predates the cap is locked out of the very trim that would fix it.
- **`max_upload_mb` caps COMPRESSED bytes and a .docx is a zip, so it needs a decompression twin** (`_assert_docx_expansion`, added 2026-09-02). `python-docx` expands every part into an lxml tree before a word of text exists: measured, 0.298 MB of zip is 102 MB of `document.xml` (343:1), so the 10 MB upload cap admitted ~3.4 GB of XML from unremarkable content. This matters because two routes feed a user's FILE straight into the parser — `POST /resume/upload` and `POST /tools/scan` — and **since Phase 30 / A2 neither is anonymous**: `/public/scan` and its per-instance per-IP `RateLimiter` are gone, and the scan is a gated feature with a `scan` daily cap and one monthly use. A free account still costs nothing to make, so the CPU one request can buy is the quantity being bounded (`config.py` records that derivation). The anonymous routes that remain take small form fields only, each behind the Phase 29 throttles. The guard sums `ZipInfo.file_size` over the WHOLE archive (central-directory metadata, so nothing is decompressed to read it, and a bomb parked in `styles.xml` or `word/media/` costs the same as one in `document.xml`), and raises `InputTooLarge` → the existing 413, never a 400: it is a limit the user can act on, and 413 keeps it out of Sentry.
  **The declared sum is an upper bound, not a claim we trust — that was checked, not assumed.** `ZipExtFile._read1` clamps every member to `data[:self._left]` with `_left` seeded from `file_size`, and the CRC then fails at EOF, so an under-declaring zip inflates nothing and lands on the 400 path. A second pass that re-read the archive to "verify" the sum would add no guarantee and would inflate every legitimate upload twice. Smoke-pinned in that direction too.
  **The cap's floor is DERIVED (`max(cap, 3 * max_upload_mb)`), not written down twice.** Images are already compressed, so an image-heavy .docx expands ~1:1 and `max_upload_mb` is itself the largest expansion a real CV can reach (measured 10.3 MB at the 10 MB cap) — a cap below that refuses a legitimate photo-heavy resume the upload cap just admitted. **32 MB, not 64:** `extract_text` is linear at ~1.19 s per MB of expanded XML, so 64 MB let one request buy ~76 s of an instance against Vercel's 300 s kill; 32 halves that and still leaves 3× headroom. Note the suite sets `MAX_UPLOAD_MB=1`, so an HTTP-level false-positive check must use a SMALL file — the 6 MB image fixture is refused by the upload cap before this guard is reached.
- **The output cap MAY NOT ship without the `finish_reason == "length"` check**, and that is the highest-risk part of this work. `chat.completions.create` NEVER raises on truncation — it returns partial content, and the SDK's own `LengthFinishReasonError` is reachable only through `.parse()`/`.stream()`. Without the hand-written check, a cap turns a working tailor into `json.loads` failing on half an object ("Unterminated string starting at: line 1 column 892"), which reads as our bug rather than a limit; and `complete_text` (the cover letter) has no parse step at all, so the letter just silently stops. Both entry points are pinned by DRIVING them, because a check that calls the guard directly still passes with the call site deleted.
- **A context overflow is discriminated by `code == "context_length_exceeded"`, never by exception type.** Every malformed-parameter bug is also a `BadRequestError`; reporting those as "your resume is too long" is a guard firing on legitimate input.
- **The capability probe is a LOOP over one parameter per attempt.** The original was single-shot and stripped exactly one kwarg, so a model rejecting both `temperature` and the output-cap name died on the second — which is precisely what adding a second probe to it would have caused. `max_completion_tokens` falls back to the legacy `max_tokens` on rejection.
- **413 is deliberate on both counts**: it matches the existing upload cap, and Sentry's Starlette integration captures only 5xx — so a limit the user can act on stops generating issues while a genuine 500 still does. `OutputTruncated` maps to **503** instead, because nothing about the request was too big and it is our own ceiling that was hit, so it should stay visible.
- **Known and deliberately out of scope**: the multi-turn interview transcript still grows without bound (it is re-sent in full every turn) — bounding a conversation is windowing, not a cap, and belongs in its own change.

### Metering — contexts and thread pools

- **A ContextVar cannot be bound inside a FastAPI `yield` dependency.** FastAPI runs setup and teardown through `contextmanager_in_threadpool`, so they can land in different contexts: `reset()` raises `"Token was created in a different Context"`, and — worse — the endpoint never sees the value at all. Request-scoped state that the endpoint must read gets bound in **middleware** (one context for set and reset) and handed to dependencies via `request.state`. This is why `llm_metering` lives in `app/main.py` and not in `deps.py`.
- **A `ThreadPoolExecutor` worker starts from an EMPTY context.** Any pool whose work makes LLM calls must submit through `copy_context().run` or its tokens vanish silently — `job_search`'s scoring pool is the case that matters, since it is the biggest spender in the app. The tally is a mutable object precisely so a copied context still writes to the request's instance.
