### Prompt input bounds, and honest size errors

- **`app/llm/prompts.py` is the input boundary, and that placement is measured.** All 22 `complete_json`/`complete_text` calls in `app/core` and `app/parsers` build their user message with a `*_user(...)` builder — no exceptions — so the builders are the one place unbounded text becomes prompt text. Guarding the STORED master resume is not enough: **25 request models take a `resume: ResumeModel` straight from the client body** (tailor, cover letter, every interview route, LinkedIn, the review's rewrites…), so `PUT /profile/resume` is one of twenty-six doors. The guard is a `@_bounded` decorator that discriminates by ARGUMENT NAME, which is why `resume_json` / `raw_text` / `jd_text` / `jd_json` / `question` / `answer` / `transcript` must stay consistent — a new builder naming its parameter something else measures nothing, and since P30-PASS-SIZE the smoke pin fails it until the parameter is measured or named (next section).
- **It is NOT in `client._create`.** That sees the assembled string and would slice a resume's JSON mid-object, handing the model a truncated document at the one boundary the fabrication guard cannot see (it diffs the tailored resume against the ledger, never the prompt).
- **Never truncate the user's own document — refuse it (413). Truncate only text the user neither wrote nor saw.** A silently shortened resume is data loss in the most valuable object the user owns, and here it does not stay a warning: the parsed model is live in the store the moment it returns, `PUT /profile/resume` versions it into one of 20 evictable slots, `useSaveMasterResume` swallows every error, and nine pages read it from a module cache. By the time the notice is read, the damaged CV IS the master. Scraped page text is clipped silently at its source (`job_match._clip_jd`), so it arrives under cap and the builders' refusal never fires on it — which is also why nothing needed a "we truncated this" response field.
- **Sized in UTF-8 BYTES, never characters.** Hebrew costs ~1.9 bytes/char against English's 1.0, so a character cap silently grants the primary market roughly twice the tokens for the same number. Bytes halve that gap with no `detect_language` branch to get wrong on the mixed Hebrew-prose/Latin-skills resume that is the Israeli norm. Bytes do **not** fully normalise it, and the caps are therefore sized against the Hebrew case.
- **A cap is a guard rail, not a budget**: it must fire on a 500-page PDF and never on a real CV (`config.py` records that a master can legitimately run ~30 rendered pages). The legitimate-but-still-too-big document is caught by `ContextWindowExceeded` instead. `PUT /profile/resume` carries a load-bearing carve-out — **a save that SHRINKS an already-oversize master is always allowed**, or anyone whose resume predates the cap is locked out of the very trim that would fix it.
- **`max_upload_mb` caps COMPRESSED bytes and a .docx is a zip, so it needs a decompression twin** (`_assert_docx_expansion`, added 2026-09-02). `python-docx` expands every part into an lxml tree before a word of text exists: measured, 0.298 MB of zip is 102 MB of `document.xml` (343:1), so the 10 MB upload cap admitted ~3.4 GB of XML from unremarkable content. This matters because two routes feed a user's FILE straight into the parser — `POST /resume/upload` and `POST /tools/scan` — and **since Phase 30 / A2 neither is anonymous**: `/public/scan` and its per-instance per-IP `RateLimiter` are gone, and the scan is a gated feature with a `scan` daily cap and one monthly use. A free account still costs nothing to make, so the CPU one request can buy is the quantity being bounded (`config.py` records that derivation). The anonymous routes that remain take small form fields only, each behind the Phase 29 throttles. The guard sums `ZipInfo.file_size` over the WHOLE archive (central-directory metadata, so nothing is decompressed to read it, and a bomb parked in `styles.xml` or `word/media/` costs the same as one in `document.xml`), and raises `InputTooLarge` → the existing 413, never a 400: it is a limit the user can act on, and 413 keeps it out of Sentry.
  **The declared sum is an upper bound, not a claim we trust — that was checked, not assumed.** `ZipExtFile._read1` clamps every member to `data[:self._left]` with `_left` seeded from `file_size`, and the CRC then fails at EOF, so an under-declaring zip inflates nothing and lands on the 400 path. A second pass that re-read the archive to "verify" the sum would add no guarantee and would inflate every legitimate upload twice. Smoke-pinned in that direction too.
  **The cap's floor is DERIVED (`max(cap, 3 * max_upload_mb)`), not written down twice.** Images are already compressed, so an image-heavy .docx expands ~1:1 and `max_upload_mb` is itself the largest expansion a real CV can reach (measured 10.3 MB at the 10 MB cap) — a cap below that refuses a legitimate photo-heavy resume the upload cap just admitted. **32 MB, not 64:** `extract_text` is linear at ~1.19 s per MB of expanded XML, so 64 MB let one request buy ~76 s of an instance against Vercel's 300 s kill; 32 halves that and still leaves 3× headroom. Note the suite sets `MAX_UPLOAD_MB=1`, so an HTTP-level false-positive check must use a SMALL file — the 6 MB image fixture is refused by the upload cap before this guard is reached.
- **The output cap MAY NOT ship without the `finish_reason == "length"` check**, and that is the highest-risk part of this work. `chat.completions.create` NEVER raises on truncation — it returns partial content, and the SDK's own `LengthFinishReasonError` is reachable only through `.parse()`/`.stream()`. Without the hand-written check, a cap turns a working tailor into `json.loads` failing on half an object ("Unterminated string starting at: line 1 column 892"), which reads as our bug rather than a limit; and `complete_text` (the cover letter) has no parse step at all, so the letter just silently stops. Both entry points are pinned by DRIVING them, because a check that calls the guard directly still passes with the call site deleted.
- **A context overflow is discriminated by `code == "context_length_exceeded"`, never by exception type.** Every malformed-parameter bug is also a `BadRequestError`; reporting those as "your resume is too long" is a guard firing on legitimate input.
- **The capability probe is a LOOP over one parameter per attempt.** The original was single-shot and stripped exactly one kwarg, so a model rejecting both `temperature` and the output-cap name died on the second — which is precisely what adding a second probe to it would have caused. `max_completion_tokens` falls back to the legacy `max_tokens` on rejection.
- **413 is deliberate on both counts**: it matches the existing upload cap, and Sentry's Starlette integration captures only 5xx — so a limit the user can act on stops generating issues while a genuine 500 still does. `OutputTruncated` maps to **503** instead, because nothing about the request was too big and it is our own ceiling that was hit, so it should stay visible.
- **Windowing the interview transcript was REVERSED, not deferred.** See *Every builder parameter is measured or named*.

### Every builder parameter is measured or named (P30-PASS-SIZE, 2026-09-21)

Until this change the guard read three names and **skipped every value that was not a string** (`if not isinstance(value, str): continue`), so five parameters on the session passes' builders reached the model unmeasured: the mock-interview transcript (a `list[ChatTurn]`, re-sent whole every turn, no limit on turns or length, each turn's free-string `role` formatted into the prompt), `question`, the practice `answer`, and the client-sent analysed JD (`jd_json`, which the tailor's fit, plan and tailor builders take too) — beside the cover letter's `tone`. Nothing else bounded them: no middleware limits a body, so a multi-MB transcript went to OpenAI, came back as `context_length_exceeded`, and was shown as "Your CV is too long… Trim the oldest roles". The old pin only looked for the three names and the old driven check only fed a big resume, so both were green through all of it.

- **`_bounded` is a rule table now** (`prompts._MEASURED` by parameter name, `_MEASURED_IN` by (builder, parameter)), each rule a kind, a `Settings` field for the cap, and for a transcript a per-candidate-turn cap. Measured: `resume_json`/`raw_text` (kind `resume`, 256 KB), `jd_text` (`jd`, 32 KB), **`jd_json` (`jd`, `4 × max_jd_kb`)**, **`question` (`question`, 16 KB)**, **`answer` (`answer`, 16 KB)**, **`transcript` (`transcript`, 256 KB, measured as the `_format_transcript` text the model reads, role prefixes included; each CANDIDATE turn also capped at 16 KB as kind `answer`)**, and on the scorecard **`transcript` as kind `session` at `max_transcript_kb + 2 × max_answer_kb`**. A measured parameter the guard cannot measure is a `TypeError`, never a skip — the skip is how the transcript went unmeasured.
- **Why each number, and why two are DERIVED.** `max_answer_kb` 16 is ~2,700 English words against a spoken answer's 150-400, and the extension clips a question at 500 characters, so it cannot fire on anything the installed software sends. **`max_transcript_kb` 256 is sized against the PASS it bounds, not the prompt's 6-8 question arc**: one use is 60 calls (an opener and 59 answers), and 59 ordinary Hebrew exchanges measure ~146 KB — 128 KB, the first number, fired on that honest session, and smoke 14b-6 drives it. `jd_json`'s cap is `4 × max_jd_kb`, derived from the analyser's always-on INPUT cap: a hand-built JD holding the largest ad the analyser accepts copied whole into three lists is 97 KB. It is **not** derived from `llm_max_output_tokens`, which can be 0 (off) and which the capability probe drops for a model that rejects it — so `MAX_JD_KB=0` switches both job-ad checks off together, and `LLM_MAX_OUTPUT_TOKENS=0` leaves this one on. The scorecard's allowance is 0 whenever the transcript cap is off, because otherwise switching the chat's cap off would switch ON a 32 KB cap on the scorecard. Each kill-switch case is smoke-pinned.
- **The scorecard reads more than the chat accepted, on purpose.** Its allowance is room for the interviewer's reply to the last accepted transcript plus the one answer the chat then refused (an old open tab still keeps it in the transcript), so a session the chat has just refused can be scored whenever the interviewer's last reply and the refused answer each fit in `max_answer_kb`, role prefix included, which is the ordinary case. Not always: an interviewer turn has no per-turn cap and can run to `llm_max_output_tokens` (16000, about 64 KB), and an old tab can keep a refused answer over 16 KB, so either can push the transcript past its cap plus 32 KB and draw a 413 of kind `session`. It has **its own kind, `session`**, because the chat's sentence says "end the session to get your scorecard", which would send someone whose scorecard was refused round in a loop. It applies **no per-turn cap**: nothing on a scorecard can be edited, so one could only strand a session.
- **Every kind has its own sentence** (check-mirrors 34, which reads the kinds out of `backend/app`): `resume`, `jd`, `transcript` ("this practice session is full, so your last answer was not sent — end it for your scorecard"), `session` ("too long to score — start over"), `answer` ("shorten it"), `question` ("paste just the question"), and `sizeLimit.generic` for a kind a build does not know. `apiErrorMessage` used to read the kind as `jd`-or-`resume`, so every one of those was told "That CV is too large… It was NOT saved… upload again". **A refused QUESTION is not told to shorten its answer**, and an interviewer turn is not capped per turn: it is model text, so "shorten your answer" said about it would be false.
- **The client hands a refused answer back.** `mockInterviewStore` appended the candidate turn before the call and kept it on failure, so the interviewer never answered it while every later call re-sent it — each retry after a size refusal was refused again and spent another of the pass's 60 calls. On ANY failure the turn now leaves the transcript and returns to the draft (`returned` / `takeReturnedAnswer`), and a 413 of kind `transcript` sets `full`, which disables Send and leaves End. **The page writes only the text it actually took** (`const text = takeReturnedAnswer(); if (text) setDraft(text)`), never `if (returned) setDraft(takeReturnedAnswer())`: under `React.StrictMode` (`main.tsx`) a mounting component's effects run twice over the same render, so a page that mounted with an answer waiting (the user left while the refusal landed) restored it on the first run and wiped it on the second, which still saw `returned` set and took `""`. Dev-only, but check-mirrors 34 executes the effect twice over one closure.
- **Shape refusals at the schema**: `ChatTurn.role` is `Literal["interviewer", "candidate"]` (the union `types.ts` already declared) and `CoverLetterRequest.tone` has `max_length` 200 (a closed set the UI builds; the longest is 48 characters). Both are 422s, which FastAPI raises before the handler, so they never touch a pass.
- **The refusal stays INSIDE the pass**, as 32.6 already pins for the resume: an opener gives its use straight back; a ride keeps its slot, like any failed ride. Checking sizes before `pass_charged` (the `/jobs/match` shape) was rejected: it would change a deliberate, pinned assertion to save one ride slot and no model spend — the builder refuses before any model call either way, and `/jobs/match` checks first only because it runs two calls per listing in a loop.
- **WINDOWING IS REVERSED, not deferred.** Sending only the last N turns would drop text the user wrote (candidate turns) or saw (interviewer turns), which rule 1 forbids; the scorecard would grade a session it did not read, which the UI may not claim; and it would throw away OpenAI's automatic prefix caching, which today's append-only transcript keeps across every turn. A refusal is the only bound the rules allow.
- **THE PIN IS INVERTED and walks every `*_user` builder, decorated or not.** Every parameter is either measured or named in `prompts._UNMEASURED`, **keyed by (builder, parameter)** — never by bare name, or allowing `company` for one builder would quietly cover the next builder that takes a user-typed `company` — with a reason in one of five categories: `server`, `schema`, `clipped`, `third-party`, `known open`. A builder that measures anything must carry the `__bounded__` marker, read off the function rather than the source text; one without it must be named in `_UNDECORATED` (today `inbox_classify_user` and `follow_up_user`). Stale entries are red, and the pin probes itself in both directions inside the suite.
- **The known-open parameters the pin now makes visible** (named, not fixed — each is client text that nothing bounds): `follow_up_user`'s `company`, `role`, `stage` and `extra` (the whole builder is undecorated); `outreach_user`'s `company`, `job_title`, `contact_name` and `contact_role`; `company_brief_user`'s `company` and `job_title`; and **`company_brief_user`'s `page_text`, which is user-pasted and CLIPPED to `company_brief._PAGE_TEXT_CAP` characters** — characters rather than bytes, and a clip of text the user supplied, which rule 1 says to refuse instead. So "the builders are the one place unbounded text becomes prompt text" is true of where it happens; none of these eleven parameters is refused by size yet (ten have no bound at all, and `page_text` is clipped).
- **Known open: a context overflow on an interview route still blames the CV.** `ContextWindowExceeded` becomes a 413 whose detail is `{"code": "context_exceeded"}` with no kind (`main.py`), and `apiErrorMessage` answers every such 413 with `sizeLimit.context`, "Your CV is too long for the AI to read in one go. Trim the oldest roles". On the interview routes the transcript can now be the larger part of the prompt: at its caps a chat turn sends ~544 KB, which in mostly English text can exceed a 128k-token window such as the local default `gpt-4o-mini`'s (an estimate at ~4 bytes a token, not measured). The fix is a kind on the overflow for those routes, with its own sentence; check-mirrors 34 does not see it, because it reads the kinds of `InputTooLarge`, not of this exception. (Found in P30-PASS-SIZE's review, 2026-09-21.)

### Metering — contexts and thread pools

- **A ContextVar cannot be bound inside a FastAPI `yield` dependency.** FastAPI runs setup and teardown through `contextmanager_in_threadpool`, so they can land in different contexts: `reset()` raises `"Token was created in a different Context"`, and — worse — the endpoint never sees the value at all. Request-scoped state that the endpoint must read gets bound in **middleware** (one context for set and reset) and handed to dependencies via `request.state`. This is why `llm_metering` lives in `app/main.py` and not in `deps.py`.
- **A `ThreadPoolExecutor` worker starts from an EMPTY context.** Any pool whose work makes LLM calls must submit through `copy_context().run` or its tokens vanish silently — `job_search`'s scoring pool is the case that matters, since it is the biggest spender in the app. The tally is a mutable object precisely so a copied context still writes to the request's instance.
