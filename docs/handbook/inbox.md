### Phase 29 — the inbox half

**Gmail OAuth.**
- **The connect is bound to the browser that started it** (O1). `POST /inbox/google/start` sets `jf_oauth` (random, 600 s) and the state row stores its HMAC; the callback requires it in constant time, deletes it, and checks it BEFORE the state is consumed. A connect started with a session needs that same session back (none → `/login?next=/settings`; another account → `state_mismatch`). PKCE on top.
- **The invite-code exception is deliberate and was reviewed.** `X-App-Key` is a header Google's redirect cannot carry, so a connect started by code (the admin, the friends beta) completes on the binding cookie alone. Judged not exploitable because `CORS_ORIGINS` is an explicit list and `*.vercel.app` is on the public suffix list, so a foreign page can neither send the start request nor toss the cookie. **Widening `CORS_ORIGINS` to another origin, or moving under a shared parent domain, re-opens it.**
- **The redirect URI is built from `APP_BASE_URL`, never `request.url_for`** — behind the `/api` mount and the Vite proxy a derived URI never matches the registered one — so `google_ready` is false until `APP_BASE_URL` is set.
- **Who may connect: `INBOX_ACCESS=allowlist` (default) = `users.inbox_enabled` or admin** (O2), and since FIXB B15 the sync and the cron re-check it, so clearing `inbox_enabled` stops the reading rather than only the connect button. `GOOGLE_OAUTH_TESTING=true` sets `reauth_due_at = connected_at + 7 days`: Testing-mode grants expire weekly.
- **A grant is handed back whenever we stop holding it**: a refused callback (`missing_scope`, `profile_failed`) revokes the token it just received (FIXB B16); reconnecting as a DIFFERENT address revokes the old grant and restarts the import from its own backfill depth, while the same address revokes nothing (FIXB B8); Disconnect and the wipe report `google_revoked` false instead of claiming a revoke when `INBOX_TOKEN_KEY` is missing (FIXB B17). Refresh tokens are Fernet-encrypted (`token_crypto`, key rotation supported); **losing `INBOX_TOKEN_KEY` disconnects everyone.**

**The network door.**
- **Every call to Google goes through `google_oauth._http`: https only, host in `_HOSTS` (four Google hosts), a redirect is an error, 20 s timeout, JSON.** `gmail_api` only builds requests. **This is NOT the SSRF door and must not be "fixed" into `job_match._http_get`**: nothing here takes a URL from anyone, and for a constant URL a fixed allowlist proves the host IS Google, where `net_guard` can only prove it is public. Pinned both ways: every URL literal in the module names an allowed host, and the network is opened nowhere but inside `_http`. `_transport` is the offline seam.

**Rules before the model.**
- **The Gmail query is narrowed server-side** (I1: `after:`/`before:` in epoch SECONDS, job vocabulary en+he OR an ATS/LinkedIn application sender, `-in:sent -in:drafts -in:chats`, minus the alert senders), and the deterministic stage decides next: alert digests are noise; templated confirmations and "viewed" mails are rule-classified with NO model call — **only for a job sender and never for a Re:/Fwd: subject**, because universities and landlords write the same subject lines.
- **Everything else carrying job vocabulary reaches the model, so non-job mail with a job word in it DOES go to OpenAI.** The privacy page, Settings and the landing FAQ said such mail was set aside "before any AI sees it"; that was false and was corrected in both locales (review F2, pinned by check-mirrors 30). Keep the copy and `inbox_rules.candidate_reason` telling the same story.
- **The classifier runs on its own client, `inbox_classifier.get_inbox_llm_client`** (`INBOX_MODEL_ID`, default `gpt-4.1-nano` — see `testing.md`). Patch THAT name to observe calls, not the client factory. The model is not trusted with the answer: evidence must appear verbatim (whitespace collapsed), the company is the HIRING employer or `""` when an agency hides it, and a platform or generic sender name (LinkedIn, Comeet, HR, Talent, `גיוס`, `צוות`…) is never a company.
- **Metering: every `/inbox/*` route is plain `Depends(current_user)`; the only charges are the `inbox` daily cap (`DAILY_INBOX_CAP`, charging what is left, never all-or-nothing) and tokens under `action="inbox_tokens"`** — never the `llm` cap, pinned by a capped friend whose `llm` row is unchanged by a sync. Both pools submit through `copy_context().run`.
- **One unreadable message may not stall the import** (FIXB B3). A message whose body read or model call fails stops the run the FIRST time with the cursor before it; the second time it is recorded as skipped — id and error code only, no subject, snippet or sender — the cursor moves past it, and it is not charged again. Before, one bad message was re-classified and re-charged every run, forever.

**The windowed backfill.**
- **The import walks FORWARD from the oldest day** (I2, a critique blocker). Gmail lists newest first, so "list after 60 days ago, take 500" imports the last week or two and skips exactly the confirmations that carry the real applied dates. The connection holds `window_lo_ms` (the next unfinished 7-day window) and `cursor_ms` (everything at or below it is handled); a run lists from `max(window_lo, cursor + 1)`, halves the window past 2,000 ids or past what the run can read in its budget, advances the cursor only across the CONTIGUOUS handled prefix with same-millisecond messages together, and moves the window only when all of it is done. Windows end 5 minutes before now so an unindexed message cannot fall behind the cursor. Once the windows reach the present the same arithmetic is the incremental sync.
- **A lease (`sync_lock_until`) keeps a cron run and a "Sync now" tap from classifying the same mail twice.** The UI runs at most 3 foreground rounds and says the import continues; the cron carries an unfinished backfill on.

**Spam: parked by id, never read (P29-SPAM-RESCUE, 2026-09-21).**
- **The defect.** `messages.list` leaves SPAM and TRASH out unless asked, and "Not spam" keeps a message's id AND its original `internalDate`. So a job reply Gmail filed in Spam was invisible when its window was listed, the cursor walked past its date, and once the user rescued it nothing ever listed it again — and `_handle_window` drops anything at or below the cursor even when it is listed. It is the same class of defect `SETTLE_MS` handles for an unindexed message; Spam was the member of it nobody handled. ATS no-reply rejections are often spam-filtered, so the tracker contradicted the user's own mailbox, silently.
- **Parking.** After `_list_window` has settled a window, `_park` lists the same query plus the exact token `in:spam` (`inbox_rules.build_query(..., spam=True)`, `SPAM_OPERATOR`) over the SAME, possibly halved, bounds, capped at `LIST_HARD_STOP`. Parked = the Spam listing − the default listing − every id that already has a row of any kind. A parked row is an id-only `mail_events` row: action `parked`, evidence `spam`, `received_at` = the Spam listing's lower bound (a "not before" for the release listing, never shown), `created_at` = the run's `now`. **Nothing in Spam is ever read** — no headers, no snippet, no body — **no model is called and nothing is charged**: mail that stays in Spam is never imported, exactly as before, so the privacy copy needs no change.
- **`includeSpamTrash=true` goes on the wire only for a query whose whitespace-split tokens contain `in:spam` EXACTLY** (`GmailMailbox.list_ids`). Never a substring test: `-in:spam` contains the token, and switching Spam-and-Trash on for such a query would feed Trash (and Spam, if the operator were ever dropped) into the listing the sync classifies and charges. Pinned beside the catch.
- **It fails toward today's behaviour on every piece of Gmail behaviour the offline suite cannot confirm**: if Google ignored `in:spam`, the default listing's ids are subtracted; if it ignored `includeSpamTrash`, nothing extra is listed; if the Spam listing fails outright, `_park` logs the exception TYPE, parks nothing and the window goes on — a listing Gmail refuses may never stall the import. It never fails toward classifying Spam.
- **Release, two paths, one rule.** A parked id the default listing names again was rescued. While the cursor has not reached it, the ordinary walk handles it in date order (`_unstored` treats `parked`, like `failed`, as not stored). Once the cursor has passed it, `_release_parked` — at the start of every run, only while parked rows exist — lists the DEFAULT query once over [oldest parked bound, cursor] and puts only the ids holding a parked row through the ordinary stages (metadata, rules, charge, model, `_apply`), in date order. **Either way `_apply` consumes the parked row whatever the stage and whatever the outcome, BEFORE the noise / skip / not-a-job returns, in the same commit as the tracker write.** The first plan gated it on B3's `retried`, which only a model-stage message with a `failed` row sets: a rescued rule-stage confirmation then became a second row for the id (`uq_mail_events_message` → IntegrityError → `internal` on every run after, the import stalled for good), and a rescued non-job message kept its parked row and was released, classified and charged again on every run.
- **The release pass NEVER writes `cursor_ms`** (`_process_chunk(release=True)`). `_process_chunk` ASSIGNS the cursor to the group it just applied; reused unchanged for mail below the cursor it rewinds it, and the next run lists a half-handled window again and re-classifies and re-charges its unstored mail. The smoke pin runs every case on ONE injected `now`: with the real clock the next run opens one more tiny window and a finished run heals the rewind through `max(cursor, win_hi - 1)`, so a cursor-equality check passes by never firing.
- **What the release listing reads ABOVE the cursor is left alone.** Its `before:` is widened by a second, so it can list a rescued message just above the cursor; the ordinary walk owns that one and will list it, and classifying it in both places charged a non-job message twice. A failed metadata read leaves its row untouched and uncharged for the next run; `MessageGone` deletes the row.
- **B3 on a parked row.** A first failure is charged, so it is marked IN PLACE — one row per id, one commit per row, never a batch insert over a parked row (the unique constraint refused it and the swallowed rollback took every OTHER first failure's marker in the batch with it). On the ordinary walk the parked row becomes the `failed` marker; on the release pass it stays `parked` with the error code as its evidence, because the release pass selects parked rows only and a `failed` row there would be stranded behind a cursor that has already passed it. `_charged_before` reads both shapes: `failed`, or `parked` with evidence other than `spam`, is retried free; its second failure is `skipped`. A message stopped by the daily cap was never charged, keeps evidence `spam`, and is charged once when it is retried. A release that stops — its budget, the cap, a charged failure — stops the run, with the existing `classify_failed` / `daily_limit` codes and `has_more`; no new error code or `InboxSyncResult` field.
- **Bounds.** Parked rows are pruned `PARK_DAYS` = 31 days after `created_at` — when they were PARKED, never their window's date, which during a backfill can be weeks earlier than the day the mail entered Spam (Gmail's 30-day purge clock starts then). No release listing is made while no parked row exists, or while the cursor is at or below the oldest parked bound — after a fresh or switched reconnect it is 0. Cost: one extra list call per window, always; and while parked rows exist, one release listing per run over [the oldest parked bound, the cursor] — for a row parked during a backfill that reaches back to its window, as far as the backfill itself, until the row is consumed or pruned. A reconnect as a DIFFERENT address drops the parked rows (`drop_parked`, FIXB B8's `switched` branch); a same-address reconnect keeps them.
- **Invisible and inert by construction**: every reader (`view=recent`, `view=review`, `review_count`, the card timeline, `latest_kinds`, Undo's date refresh) and every action (Undo, Dismiss, Resolve) works off an allow-list of the six user-facing actions, so a `parked` row is never shown, counted or actionable — the same as B3's `failed` / `skipped` markers. Both privacy doors and a disconnect with purge delete it with the rest of `mail_events`.
- **Two shapes were rejected, and why matters because PLAN.md's first sketch proposed them.** Importing Spam like the inbox (`includeSpamTrash` minus Trash) sends every job-word message in Spam — much of it job scams — to the model, charges the user's cap for mail they never saw, and lets a spoofed "rejection" close a tracked card. A trailing re-scan of the last ~30 days every run is NOT idempotent in cost: noise, skipped, not-a-job and unclassifiable mail is never stored, so every run would re-read and re-classify and re-charge each such message. **"`mail_events` ids make either idempotent" holds for TRACKER WRITES, never for MODEL CHARGES.**
- **Accepted edges.** A message moved INTO Spam in the moment between the default and the Spam listing of its window is in neither and is missed. A message moved into Spam weeks after it arrived and rescued after its parked row aged out is missed. A message already handled as noise or not-a-job, then moved to Spam, and falling inside the next window's one-second widening can be parked, and if rescued is classified once more. A disconnect WITHOUT purge keeps parked rows, as it keeps B3's markers. `_touch` fills `applied_at` only when it is empty, so a released confirmation OLDER than the one that set it does not lower it (Undo's `_refresh_email_dates` takes the minimum; the two can disagree by the gap between two confirmations of one application).
- **Unconfirmed until the first real connect**: that `in:spam` with `includeSpamTrash=true` lists Spam and only Spam, that "Not spam" keeps the id and `internalDate` and puts the message back in the default listing, and the 30-day purge. The design degrades to the pre-fix behaviour if either listing semantic is wrong. Pinned offline by smoke 30f (a FakeMailbox that models the labels) and one check in 30d.

**Tracker writes.**
- **Monotonic**: saved → applied → interview → offer, or rejected. An email never moves a card backwards and never changes an offer or rejected card; a different verdict waits in Needs review. Low confidence (`INBOX_REVIEW_THRESHOLD`), several candidate cards, a title similarity under 0.5, or a blank/agency company all go to review.
- **Rule 5 covers EVERY card, whoever made its last change** (I4, widened by P29-SPAM-RESCUE). `marker = status_changed_at or created_at`; an email older than the marker may still move a confirmation saved → applied, sends an interview/offer/rejection to review, and otherwise only links — whether that change was manual, a kit, the extension, a legacy `""` row or ANOTHER EMAIL. Without it a first 60-day import lands a two-month-old rejection from a PREVIOUS application on the card made today. Until P29-SPAM-RESCUE the rule read "when `status_source != "email"`", which was safe only because mail was applied in date order: a reply released from Spam is the first mail applied out of order, and under the old clause an old released rejection closed a card a NEWER email had moved to Interview (rule 6) and wrote `status_changed_at` backwards. For mail applied in order the widening changes nothing — an email-made change is never newer than the next email, and the comparison is strict — but it does now also cover the FIXB B8 switched-address re-walk and a purge-then-reconnect, where an old rejection from the new mailbox used to close an email-made Interview card and now waits in review (smoke 30f pins both). Writers stamp `status_source` and `applied_at`: POST, PATCH (`manual` only when the status changes) and `auto_submit`, which also stamps `status_changed_at` now (FIXB B13).
- **`execute` re-plans against the FRESH row** (FIXB B9). The plan was made from a card snapshot taken at the start of a run up to 240 s long, so a card the user dragged to Offer mid-sync was overwritten to rejected.
- **A short company name matches only as a WHOLE word of the longer one** (FIXB B10): IBM ~ IBM Israel, Wix ~ Wix.com, while HP never matches Hapoalim. The old ≥4-character floor created a phantom rejected card beside the tracked IBM one.
- **Honest dates** (I3): an inbox-created card is dated by its earliest email, and `applied_at` stays nullable and comes only from a confirmation — a rejection proves nobody's send date. The analytics bucket on `applied_at ?? created_at`.
- **Honest interviews** (I5): every matched interview email sets `interviewed` even when the status does not move, an assessment moves nothing, and **Undo clears `interviewed` only when no other interview email remains on the card** (FIXB B11). The header tile and the funnel read ONE definition, `interviewed || status === "interview"` (review F3).
- **Undo is exact, and it respects the user's edits**: an email-created card goes with its Undo only while untouched — stars, notes, a tailored resume or a hand-toggled Interviewed all count (FIXB B12) — and a kept Applied card keeps its `applied_at`. `DELETE /applications/{id}` unlinks that card's mail events, because SQLite can reuse the id. A card's timeline and Recent updates keep an UNDONE email, shown as "Undone" with no Undo button: Undo reverts the board change, it does not un-receive the email — filtered out, the invite that moved a card could no longer be seen anywhere (Phase 29 browser pass). "Add to tracker" on a review email with no detected company or title takes the subject as the card title, so it never creates a blank card — and never guesses the company from the sender's display name, which on a recruiter's mail is a person.

**Cron.**
- **`/api/inbox/cron` runs at 05:00 and 14:00 UTC as TWO `vercel.json` entries** — a Vercel Hobby cron entry fires at most once a day — beside the unchanged alerts (06:00) and nudges (07:00). That Vercel accepts two entries on one path is not yet confirmed on a deploy.
- **It FAILS CLOSED** (A12): gate on and `CRON_SECRET` empty is 503 `cron_unconfigured`, because an open copy would refresh every user's Gmail grant and spend model calls for anyone who found the URL. It is in `_AUTH_OPTIONAL` and checks its own Bearer secret, runs on a wall-clock budget checked before each user (`INBOX_CRON_BUDGET_S` = 240; each user gets `min(2 × INBOX_SYNC_BUDGET_S, what is left)`), and prunes the security log.
