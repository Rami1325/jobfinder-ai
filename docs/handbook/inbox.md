### Phase 29 — the inbox half

**Gmail OAuth.**
- **The connect is bound to the browser that started it** (O1). `POST /inbox/google/start` sets `jf_oauth` (random, 600 s) and the state row stores its HMAC; the callback requires it in constant time, deletes it, and checks it BEFORE the state is consumed. A connect started with a session needs that same session back (none → `/login?next=/settings`; another account → `state_mismatch`). PKCE on top.
- **The invite-code exception is deliberate and was reviewed.** `X-App-Key` is a header Google's redirect cannot carry, so a connect started by code (the admin, the friends beta) completes on the binding cookie alone. Judged not exploitable because `CORS_ORIGINS` is an explicit list and `*.vercel.app` is on the public suffix list, so a foreign page can neither send the start request nor toss the cookie. **Widening `CORS_ORIGINS` to another origin, or moving under a shared parent domain, re-opens it.**
- **The redirect URI is built from `APP_BASE_URL`, never `request.url_for`** — behind the `/api` mount and the Vite proxy a derived URI never matches the registered one — so `google_ready` is false until `APP_BASE_URL` is set.
- **Who may connect: `INBOX_ACCESS=allowlist` (default) = `users.inbox_enabled` or admin** (O2), and since FIXB B15 the sync and the cron re-check it, so clearing `inbox_enabled` stops the reading rather than only the connect button. `GOOGLE_OAUTH_TESTING=true` sets `reauth_due_at = connected_at + 7 days`: Testing-mode grants expire weekly.
- **A grant is handed back whenever we stop holding it**: a refused callback (`missing_scope`, `profile_failed`) revokes the token it just received (FIXB B16); reconnecting as a DIFFERENT address revokes the old grant and restarts the import from its own backfill depth, while the same address revokes nothing (FIXB B8); Disconnect and the wipe report `google_revoked` false instead of claiming a revoke when `INBOX_TOKEN_KEY` is missing (FIXB B17). Refresh tokens are Fernet-encrypted (`token_crypto`, key rotation supported); **losing `INBOX_TOKEN_KEY` disconnects everyone.**

**The network door.**
- **Every call to Google goes through `google_oauth._http`: https only, host in `_HOSTS` (four Google hosts), a redirect is an error, 20 s timeout, JSON.** `gmail_api` only builds requests. **This is NOT the SSRF door and must not be "fixed" into `job_match._http_get`**: nothing here takes a URL from anyone, and for a constant URL a fixed allowlist proves the host IS Google, where `net_guard` can only prove it is public. Pinned both ways: every URL literal in the module names an allowed host, and the network is opened nowhere but inside `_http`. `_transport` is the offline seam.

**Rules before the model.**
- **The Gmail query is narrowed server-side** (I1: `after:`/`before:` in epoch SECONDS, job vocabulary en+he OR an ATS/LinkedIn application sender, `-in:sent -in:drafts -in:chats`, minus the alert senders), and the deterministic stage decides next: alert digests are noise; templated confirmations and "viewed" mails are rule-classified with NO model call — **only for a job sender and never for a Re:/Fwd: subject**, because universities and landlords write the same subject lines.
- **Everything else carrying job vocabulary reaches the model, so non-job mail with a job word in it DOES go to OpenAI.** The privacy page, Settings and the landing FAQ said such mail was set aside "before any AI sees it"; that was false and was corrected in both locales (review F2, pinned by check-mirrors 30). Keep the copy and `inbox_rules.candidate_reason` telling the same story.
- **The classifier runs on its own client, `inbox_classifier.get_inbox_llm_client`** (`INBOX_MODEL_ID`, default `gpt-4.1-nano` — see `testing.md`). Patch THAT name to observe calls, not the client factory. The model is not trusted with the answer: evidence must appear verbatim (whitespace collapsed), the company is the HIRING employer or `""` when an agency hides it, and a platform or generic sender name (LinkedIn, Comeet, HR, Talent, `גיוס`, `צוות`…) is never a company.
- **Metering: every `/inbox/*` route is plain `Depends(current_user)`; the only charges are the `inbox` daily cap (`DAILY_INBOX_CAP`, charging what is left, never all-or-nothing) and tokens under `action="inbox_tokens"`** — never the `llm` cap, pinned by a capped friend whose `llm` row is unchanged by a sync. Both pools submit through `copy_context().run`.
- **One unreadable message may not stall the import** (FIXB B3). A message whose body read or model call fails stops the run the FIRST time with the cursor before it; the second time it is recorded as skipped — id and error code only, no subject, snippet or sender — the cursor moves past it, and it is not charged again. Before, one bad message was re-classified and re-charged every run, forever.

**The windowed backfill.**
- **The import walks FORWARD from the oldest day** (I2, a critique blocker). Gmail lists newest first, so "list after 60 days ago, take 500" imports the last week or two and skips exactly the confirmations that carry the real applied dates. The connection holds `window_lo_ms` (the next unfinished 7-day window) and `cursor_ms` (everything at or below it is handled); a run lists from `max(window_lo, cursor + 1)`, halves the window past 2,000 ids or past what the run can read in its budget, advances the cursor only across the CONTIGUOUS handled prefix with same-millisecond messages together, and moves the window only when all of it is done. Windows end 5 minutes before now so an unindexed message cannot fall behind the cursor. Once the windows reach the present the same arithmetic is the incremental sync.
- **A lease (`sync_lock_until`) keeps a cron run and a "Sync now" tap from classifying the same mail twice.** The UI runs at most 3 foreground rounds and says the import continues; the cron carries an unfinished backfill on.

**Spam: parked by id, read only once rescued (P29-SPAM-RESCUE, 2026-09-21).**
- **The defect.** `messages.list` leaves SPAM and TRASH out unless asked, and "Not spam" keeps a message's id AND its original `internalDate`. So a job reply Gmail filed in Spam was invisible when its window was listed, the cursor walked past its date, and once the user rescued it nothing ever listed it again — and `_handle_window` drops anything at or below the cursor even when it is listed. It is the same class of defect `SETTLE_MS` handles for an unindexed message; Spam was the member of it nobody handled. ATS no-reply rejections are often spam-filtered, so the tracker contradicted the user's own mailbox, silently.
- **Parking.** After `_list_window` has settled a window, `_park` lists the same query plus the exact token `in:spam` (`inbox_rules.build_query(..., spam=True)`, `SPAM_OPERATOR`) over the SAME, possibly halved, bounds, capped at `LIST_HARD_STOP`. Parked = the Spam listing − the default listing − every id that already has a row of any kind. **The last term is load-bearing**: a window stopped by its budget is listed again, and an insert over an id that already has a row — still parked, or imported and moved to Spam since — is refused by `uq_mail_events_message`, and the rollback takes every NEW park in the batch with it, so a reply filed in Spam since and rescued later is lost for good (smoke 30f pins it with both kinds of row in the re-listed window, and the rows they already had kept as they were). A parked row is an id-only `mail_events` row: action `parked`, evidence `spam`, `received_at` = the Spam listing's lower bound (a "not before" for the release listing, never shown), `created_at` = the run's `now`. **Parking reads nothing**: while an id stays parked, no headers, snippet or body of it is fetched, **no model is called and nothing is charged**. Mail that stays in Spam is never imported, exactly as before, so the privacy copy needs no change; a parked id is read only once it is rescued (*Release*, below). A message in Spam CAN be read in one other case: the user moved it there after its window's default listing had named it — between the two listings, or before its own read — so it is handled as inbox mail, read and classified, exactly as it was before this fix (see the accepted edges).
- **`includeSpamTrash=true` goes on the wire only for a query whose whitespace-split tokens contain `in:spam` EXACTLY** (`GmailMailbox.list_ids`). Never a substring test: `-in:spam` contains the token, and switching Spam-and-Trash on for such a query would feed Trash (and Spam, if the operator were ever dropped) into the listing the sync classifies and charges. Pinned beside the catch.
- **It fails toward today's behaviour on every piece of Gmail behaviour the offline suite cannot confirm**: if Google ignored `in:spam`, the default listing's ids are subtracted; if it ignored `includeSpamTrash`, nothing extra is listed; if the Spam listing fails outright, `_park` logs the exception TYPE, parks nothing and the window goes on — a listing Gmail refuses may never stall the import. It never fails toward classifying Spam.
- **Release, two paths, one rule.** A parked id the default listing names again was rescued. While the cursor has not reached it, the ordinary walk handles it in date order (`_unstored` treats `parked`, like `failed`, as not stored). Once the cursor has passed it, `_release_parked` — at the start of every run, only while parked rows exist — lists the DEFAULT query once over [oldest parked bound, cursor] and puts only the ids holding a parked row through the ordinary stages (metadata, rules, charge, model, `_apply`), in date order. **Either way `_apply` consumes the parked row whatever the stage and whatever the outcome, BEFORE the noise / skip / not-a-job returns, in the same commit as the tracker write.** The first plan gated it on B3's `retried`, which only a model-stage message with a `failed` row sets: a rescued rule-stage confirmation then became a second row for the id (`uq_mail_events_message` → IntegrityError → `internal` on every run after, the import stalled for good), and a rescued non-job message kept its parked row and was released, classified and charged again on every run.
- **The release pass NEVER writes `cursor_ms`** (`_process_chunk(release=True)`). `_process_chunk` ASSIGNS the cursor to the group it just applied; reused unchanged for mail below the cursor it rewinds it, and the next run lists a half-handled window again and re-classifies and re-charges its unstored mail. The smoke pin runs every case on ONE injected `now`: with the real clock the next run opens one more tiny window and a finished run heals the rewind through `max(cursor, win_hi - 1)`, so a cursor-equality check passes by never firing.
- **What the release listing reads ABOVE the cursor is left alone.** Its `before:` is widened by a second, so it can list a rescued message just above the cursor; the ordinary walk owns that one and will list it, and classifying it in both places charged a non-job message twice. A failed metadata read leaves its row untouched and uncharged for the next run; `MessageGone` deletes the row, so no later listing is spent on it. The pass checks the run's budget BEFORE its listing: a run whose time went on opening the mailbox makes no Gmail call on work it cannot finish, and says `has_more`. All three are pinned in 30f, each beside its twin.
- **B3 on a parked row.** A first failure is charged, so it is marked IN PLACE — one row per id, one commit per row, never a batch insert over a parked row (the unique constraint refused it and the swallowed rollback took every OTHER first failure's marker in the batch with it). On the ordinary walk the parked row becomes the `failed` marker; on the release pass it stays `parked` with the error code as its evidence, because the release pass selects parked rows only and a `failed` row there would be stranded behind a cursor that has already passed it. `_charged_before` reads both shapes: `failed`, or `parked` with evidence other than `spam`, is retried free; its second failure is `skipped`. A message stopped by the daily cap was never charged, keeps evidence `spam`, and is charged once when it is retried. A release that stops — its budget, the cap, a charged failure — stops the run, with the existing `classify_failed` / `daily_limit` codes and `has_more`; no new error code or `InboxSyncResult` field.
- **Bounds.** Parked rows are pruned `PARK_DAYS` = 31 days after `created_at` — when they were PARKED, never their window's date, which during a backfill can be weeks earlier than the day the mail entered Spam (Gmail's 30-day purge clock starts then). No release listing is made while no parked row exists, or while the cursor is at or below the oldest parked bound — after a fresh or switched reconnect it is 0. Cost: one extra listing for every window listed, always — at least one Gmail call, and one more per 500 Spam ids, so up to 20 at `LIST_HARD_STOP` (`_list_all`); and while parked rows exist, one release listing per run (likewise up to 20 calls) over [the oldest parked bound, the cursor] — for a row parked during a backfill that reaches back to its window, as far as the backfill itself, until the row is consumed or pruned. That listing stops at `LIST_HARD_STOP` ids, like the Spam listing, and Gmail lists newest first: past 10,000 job-vocabulary messages between the oldest parked bound and the cursor, the OLDEST parked rows are never reached and wait out their prune (accepted). A reconnect that REPLACES a connection held for a different address drops the parked rows (`drop_parked`, FIXB B8's `switched` branch); a same-address reconnect keeps them. After a Disconnect without purge the connection row is gone, so `switched` is false and connecting a different address keeps the old mailbox's parked rows too: nothing in the new mailbox can release them, and once the new cursor passes their bound each run spends one release listing on them until they are pruned (harmless, and bounded by the prune).
- **Invisible and inert by construction**: every reader (`view=recent`, `view=review`, `review_count`, the card timeline, `latest_kinds`, Undo's date refresh) and every action (Undo, Dismiss, Resolve) works off an allow-list of the six user-facing actions, so a `parked` row is never shown, counted or actionable — the same as B3's `failed` / `skipped` markers. Both privacy doors and a disconnect with purge delete it with the rest of `mail_events`.
- **Two shapes were rejected, and why matters because PLAN.md's first sketch proposed them.** Importing Spam like the inbox (`includeSpamTrash` minus Trash) sends every job-word message in Spam — much of it job scams — to the model, charges the user's cap for mail they never saw, and lets a spoofed "rejection" close a tracked card. A trailing re-scan of the last ~30 days every run is NOT idempotent in cost: noise, skipped, not-a-job and unclassifiable mail is never stored, so every run would re-read and re-classify and re-charge each such message. **"`mail_events` ids make either idempotent" holds for TRACKER WRITES, never for MODEL CHARGES.**
- **Accepted edges.** The Spam listing runs AFTER the default one, because it needs the window the halving settled on, and that order decides which move the gap between the two loses. A message RESCUED in that gap is in neither listing — not in the inbox when the inbox was listed, no longer in Spam when Spam is — so it is never parked, and once the cursor passes its date it is missed for good: a real loss, and the one this order accepts. A message moved INTO Spam in that gap is NOT missed: the default listing already named it, so it is imported as inbox mail — read and classified although it now sits in Spam, exactly as before this fix. (Listing Spam FIRST would lose the other move instead: there a message rescued in the gap is named by the default listing and imported by the walk, and one moved into Spam in the gap is in neither listing, so it is lost if it is rescued later. The first draft of this bullet, in `9c2c616`, said "a message moved INTO Spam … is in neither and is missed", which describes that order, not the one that shipped.) **Trash is never parked**: the Spam listing uses `in:spam` alone, so a job reply that was in Trash when its window was listed and is restored after the cursor passed it is still never imported. **A charged first failure moved to Spam is stranded**: a model-stage message whose first read or classify failed holds a `failed` row; if the user moves it to Spam before its free retry, the walk no longer lists it and `_park` skips it because it already has a row, and the release pass selects `parked` rows only, so if it is rescued later it is never imported (three rare events together). A message moved into Spam weeks after it arrived and rescued after its parked row aged out is missed. A message already handled as noise or not-a-job, then moved to Spam, and falling inside the next window's one-second widening can be parked, and if rescued is classified once more. A disconnect WITHOUT purge keeps parked rows, as it keeps B3's markers. `_touch` fills `applied_at` only when it is empty, so a released confirmation OLDER than the one that set it does not lower it (Undo's `_refresh_email_dates` takes the minimum; the two can disagree by the gap between two confirmations of one application).
- **Unconfirmed until the first real connect**: that `in:spam` with `includeSpamTrash=true` lists Spam and only Spam, that "Not spam" keeps the id and `internalDate` and puts the message back in the default listing, and the 30-day purge. The design degrades to the pre-fix behaviour if either listing semantic is wrong. Pinned offline by smoke 30f (a FakeMailbox that models the labels) and one check in 30d.

**Tracker writes.**
- **Monotonic**: saved → applied → interview → offer, or rejected. An email never moves a card backwards and never changes an offer or rejected card; a different verdict waits in Needs review. Low confidence (`INBOX_REVIEW_THRESHOLD`), several candidate cards, a title similarity under 0.5, or a blank/agency company all go to review.
- **Rule 5 covers EVERY card, whoever made its last change** (I4, widened by P29-SPAM-RESCUE). `marker = status_changed_at or created_at`; an email older than the marker may still move a confirmation saved → applied, sends an interview/offer/rejection to review, and otherwise only links — whether that change was manual, a kit, the extension, a legacy `""` row or ANOTHER EMAIL. Without it a first 60-day import lands a two-month-old rejection from a PREVIOUS application on the card made today. Until P29-SPAM-RESCUE the rule read "when `status_source != "email"`", which was safe only because mail was applied in date order: a reply released from Spam is the first mail applied out of order, and under the old clause an old released rejection closed a card a NEWER email had moved to Interview (rule 6) and wrote `status_changed_at` backwards. For mail applied in order the widening changes nothing — an email-made change is never newer than the next email, and the comparison is strict — but it does now also cover the FIXB B8 switched-address re-walk and a purge-then-reconnect, where an old rejection from the new mailbox used to close an email-made Interview card and now waits in review. Smoke 30f pins that with ONE check on the state both routes leave behind — a fresh import from the backfill depth (`_connect29`) walking an old rejection against a card an email moved to Interview; neither the switched reconnect nor the purge is driven end to end there. Writers stamp `status_source` and `applied_at`: POST, PATCH (`manual` only when the status changes) and `auto_submit`, which also stamps `status_changed_at` now (FIXB B13).
- **`execute` re-plans against the FRESH row** (FIXB B9). The plan was made from a card snapshot taken at the start of a run up to 240 s long, so a card the user dragged to Offer mid-sync was overwritten to rejected.
- **A short company name matches only as a WHOLE word of the longer one** (FIXB B10): IBM ~ IBM Israel, Wix ~ Wix.com, while HP never matches Hapoalim. The old ≥4-character floor created a phantom rejected card beside the tracked IBM one.
- **Honest dates** (I3): an inbox-created card is dated by its earliest email, and `applied_at` stays nullable and comes only from a confirmation — a rejection proves nobody's send date. The analytics bucket on `applied_at ?? created_at`.
- **Honest interviews** (I5): every matched interview email sets `interviewed` even when the status does not move, an assessment moves nothing, and **Undo clears `interviewed` only when no other interview email remains on the card** (FIXB B11). The header tile and the funnel read ONE definition, `interviewed || status === "interview"` (review F3).
- **Undo is exact, and it respects the user's edits**: an email-created card goes with its Undo only while untouched — stars, notes, a tailored resume or a hand-toggled Interviewed all count (FIXB B12) — and a kept Applied card keeps its `applied_at`. `DELETE /applications/{id}` unlinks that card's mail events, because SQLite can reuse the id. A card's timeline and Recent updates keep an UNDONE email, shown as "Undone" with no Undo button: Undo reverts the board change, it does not un-receive the email — filtered out, the invite that moved a card could no longer be seen anywhere (Phase 29 browser pass). "Add to tracker" on a review email with no detected company or title takes the subject as the card title, so it never creates a blank card — and never guesses the company from the sender's display name, which on a recruiter's mail is a person.

**Cron.**
- **`/api/inbox/cron` runs at 05:00 and 14:00 UTC as TWO `vercel.json` entries** — a Vercel Hobby cron entry fires at most once a day — beside the unchanged alerts (06:00) and nudges (07:00). That Vercel accepts two entries on one path is not yet confirmed on a deploy.
- **It FAILS CLOSED** (A12): gate on and `CRON_SECRET` empty is 503 `cron_unconfigured`, because an open copy would refresh every user's Gmail grant and spend model calls for anyone who found the URL. It is in `_AUTH_OPTIONAL` and checks its own Bearer secret, runs on a wall-clock budget checked before each user (`INBOX_CRON_BUDGET_S` = 240; each user gets `min(2 × INBOX_SYNC_BUDGET_S, what is left)`), and prunes the security log.

### The first real connect (2026-09-22)

The Gmail client existed only as a fake transport until this day: `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` were the
last two production variables missing (`INBOX_TOKEN_KEY`, `INBOX_ACCESS=allowlist` and `GOOGLE_OAUTH_TESTING` had been
set earlier). The owner created the Gmail Cloud project (separate from the sign-in one, Testing, `openid` + `email` +
`gmail.readonly`, redirect `/api/inbox/google/callback`), the two variables went into production, and a redeploy picked
them up. An anonymous `GET /api/inbox/google/callback` is the probe that says whether the backend is configured at all:
`?inbox=not_configured` before, `?inbox=state_invalid` after.

**What one real inbox produced**, read back from production read-only: 169 messages scanned, 70 `mail_events`. 45
confirmations created a card, 3 rejections created one, 7 confirmations and 4 interviews and 1 "viewed" linked to a card
that existed, 5 rejections and 1 interview UPDATED a card's status, and 4 went to Needs review (2 recruiter, 1
confirmation, 1 interview). The tracker went from a handful of cards to 63 (48 applied, 8 rejected, 7 saved, 1
interviewed). **106 messages were parked from Spam** — id-only rows, nothing read, nothing classified, nothing charged,
which is the P29-SPAM-RESCUE design working on a real mailbox. The model ran on 61 messages for about 125,000 tokens of
`gpt-4.1-nano`, roughly **1.3 cents** for a 30-day backfill of one real inbox.

**Two of the three unconfirmed Google behaviours are now confirmed**, and the third is still open:
- **PKCE with a client secret on the Gmail client works** — the connect completed and stored a refresh token.
- **A `format=metadata` read returns the snippet**: every imported event carries one.
- **Spam parking was observed** (106 rows), but the two behaviours the RESCUE relies on — that "Not spam" keeps a
  message's id and `internalDate` and puts it back in the default listing, and that Spam is purged after 30 days — need
  a message actually rescued, which has not happened yet.

**A read that fails twice stops the backfill, and the first real run hit it.** `_read_metas` retries a failed read once,
immediately, and a window whose read still fails ends the sync with `gmail_error` and `has_more`. On the first run that
happened around 14 days in: the cursor stopped at 2026-09-06, the card showed the error, and **the next Sync resumed
from exactly there** and finished the remaining 16 days with no error (169 scanned in total). The likely cause is
Google's per-user rate limit during a burst — a `POOL`-wide read of one window beside 61 model calls — against a retry
with no backoff, which retries straight into the same limit. It is self-healing because the window is resumable, so it
costs a sync, not data. **Open, with the data now behind it**: a short backoff before the single retry, so a
rate-limited burst reads as "more to do" rather than as an error.

### The codes the inbox sends, and the sentences that say them (P29-INBOX-CODES, 2026-09-21)

**The backend talks to the page in three families of codes, and each has a hand-written `switch` that turns a code into a sentence.**
- **Sync codes**, `InboxSyncResult.error_code` and `InboxStatus.last_error_code`, come from `inbox_sync.py` (plus the connect routes, which reset `last_error`) and are read by `useSyncErrorText` in `components/inbox/shared.tsx`.
- **Route refusals**, `HTTPException(detail={"code": …})` in `inbox_routes.py`, are read by `useInboxRefusalText`, in the same file.
- **Callback reasons**, the `/settings?inbox=<reason>` the Gmail callback redirects with, are read by `callbackMessage` in `InboxSettingsCard.tsx`.

**The drift that shipped.** Nothing compared the two sides, and they drifted where a user could read it. FIXB B15 (1836d30) made `sync_user` return `invite_only` for a connected account taken off the allowlist, three hours after the switch was written (5d7b63e), and touched no frontend file. The code fell to `default`, so someone who can never sync again was told "The last sync ran into a problem. It tries again on the next sync". The tracker's Reconnect showed the same 403 as "Couldn't start reconnecting", because it called `apiErrorMessage` directly instead of the refusal hook.

**check-mirrors 37 now reads the codes from the backend and holds the switches to them.**
- **Every code in the backend's closed set has a `case` of its own, even one that returns the generic sentence.** Such an arm makes "the generic sentence is right for this code" a decision a reviewer can see, rather than a default nobody chose. The generic groups say why they are generic: retried by the next run, or never seen by a signed-in page.
- **A `case` stacked on `default:` is not an arm of its own.** Each `default` is pinned to its generic sentence, never the code.
- **Arms are literal `t("…")` calls**, so check 29 resolves every key in both locales.
- **Google's OPEN set stays on `default` by design.** These are its own `error` strings and `http_<status>`, built by `google_oauth._error_code(…)` (the one open-set shape check 37 allows as a `GoogleAuthError` code), which reach `last_error` only through `_fail(…, e.code)` in `_open_mailbox`. A Google string mapped on purpose goes in `GOOGLE_PASSTHROUGH` in check-mirrors.js. `invalid_grant` and `admin_policy_enforced` are NOT in that open set, because `_REAUTH_CODES` names them.
- **The other direction is checked too (37(e)).** Every case literal must be a code the backend sends. So must every code a component compares with `apiErrorCode(…)`, an `error_code` / `last_error_code`, a status `reason` or a connection `.status`, and every member of `ANSWERS`. A backend rename otherwise leaves the comparison false for ever: the review sheet's `left` would put an email that was already filed back in the queue, and a renamed `needs_reauth` would take Reconnect off both surfaces. A `.status` compared with a literal under `components/inbox/` is read as the connection's; none of those files compares an application's status with a literal today.
- **Every `InboxStatus.reason` is compared in BOTH `InboxBar` and `InboxSettingsCard`.** A new reason would otherwise hide the bar and the card with no sentence.
- **No file under `components/inbox/` can reach `apiErrorMessage` except through `useInboxRefusalText`.** The name may appear only in `shared.tsx`'s plain `import { … }` and inside the hook. Any other mention fails: a call, an aliased import, or `api.apiErrorMessage(…)`. So does a namespace or dynamic import of `lib/apiError`. The hook falls back to `apiErrorMessage` for everything it does not translate, so routing a toast through the hook costs nothing for a gate or network error.

**Adding a code.** Write it as a literal, pass it to an existing emitter (`_fail`, `_note_error`), or return it as a literal from an `inbox_apply` refusal function. Then give it an arm on the page, and the build tells you which one.

The reader is text, not an AST, so its grammar is closed over the sites it knows. The check's header lists every site shape. A sync code or a connection status is read wherever it is written in `inbox_sync.py` or `inbox_routes.py`: after `if x:` or `;`, through an alias (`mc = conn; mc.status = …`), in a bulk `update(MailConnection).values(status=…)`, or in `MailConnection(…, status=…)`. At a site, a value the reader cannot read THROWS in check 37 and names the file's own line. These all throw:
- a computed sync code or connection status;
- a `GoogleAuthError` code that is neither a literal nor `_error_code(…)` (a ternary of literals is read, both branches);
- a refusal function that returns a helper's value;
- an f-string with two placeholders;
- an `HTTPException` detail that is a variable or a `dict(…)`;
- a `leave()` path built from anything but literals and one `quote(…)`;
- a callback reason held in a variable, or `reason` forwarded from outside an emitter.

Each family also has nets, which throw on every other way of writing it that they name:
- **Sync codes and connection statuses** (in `inbox_sync.py` and `inbox_routes.py`):
  - an augmented or walrus write;
  - a tuple assignment;
  - the field named in a string (`setattr(r, "error_code", …)`, `model_copy(update={"error_code": …})`, `setattr(conn, "status", …)`);
  - `**` unpacked into `InboxSyncResult(…)`, `MailConnection(…)` or `.values(…)`.
- **Refusals** (in `inbox_routes.py`):
  - a `"code":` key that is not an `HTTPException` detail;
  - a `code=` keyword of a `dict(…)`;
  - a `code=` keyword handed a string literal.
- **Callback reasons** (in `inbox_routes.py`): an `?inbox=` that no `leave()` carried.

Each net has a false-positive twin that stays quiet: a comparison, a read passed on as an argument, a local named `status` (the HTTP status in `_finish`), an application card's status inside `_Card`, and Google's OAuth code handed on as `exchange_code(code=code)`. When a net fires, teach the reader the new shape or write the code in a known one. Never leave it unread.

**What check 37 knowingly does not read.** It reads `inbox_sync.py`, `inbox_routes.py`, `inbox_apply.py`, the `google_oauth` functions `_open_mailbox` calls, and the `===` / `!==` comparisons under `components/inbox/`. It cannot see:
- a sync code or connection status written from any other module (`db/models.py`'s column defaults included), or through a name the text cannot see (`setattr` with a computed name, `model_copy(update=<variable>)`, `**` unpacked anywhere but the three calls above);
- a `GoogleAuthError` raised outside `google_oauth` (`gmail_api` raises its own, which no emitter hands on today), or in a `google_oauth` function reached other than by its plain name;
- an inbox refusal raised outside `inbox_routes.py` (a dependency, the gate), or sent from it as a `code=` keyword handed a variable outside `dict(…)`;
- a callback redirect whose `inbox=` is not written literally (`urlencode`);
- a code or status the page compares some other way: a `switch` outside the three hooks, `.includes(…)`, or a lookup table;
- a wrapper of `apiErrorMessage` defined outside `components/inbox/`.

Any of these needs the reader extended first.

**The first draft claimed more than it read, twice.** Its header said every unknown shape throws. The first review found four shapes that were silently unread:
- a ternary as a `GoogleAuthError` code (its `else` branch had no arm);
- a variable as a `GoogleAuthError` code, which was read as no code at all;

A black-formatted `error_code="…",` continuation line also went red as a false positive.

Each shape is now read or refused, with a probe twin beside it, and each net's own probe was confirmed red by weakening that net. The nets exist so that the next new shape fails loudly rather than quietly, and this list says what they do not cover.
