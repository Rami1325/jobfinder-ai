### Has anyone actually opened it? (`users.last_seen_at`, 2026-09-02)

- **Nothing could answer "has this invitee ever used the app".** `usage_log` looked like the record and is not: `check_and_count` returns early for admins, so the owner's own row reads 0 searches and 0 tailors however heavy the use; and the deterministic routes (`/tools/*`, `/render`) are deliberately uncapped, so they write no row either. Web Analytics is off, and Vercel runtime logs retain roughly **three hours**. Audited against Neon, three of five invite codes had produced literally nothing — and there was no way to tell "never opened it" from "opened it and bounced at the gate".
- **The stamp lives in the `access_gate` MIDDLEWARE, never in `current_user`, and that placement IS the feature.** The gate runs before routing, so it sees the uncapped tool routes and even paths that do not exist; a route dependency sees neither, and moving it there would silently re-open the exact blind spot the column closes. Smoke-pinned by asserting an **unrouted** path still stamps — a check a dependency-based implementation cannot pass.
- **NULL means NOT MEASURED, never "never visited"**, and `UserOut.last_seen_at` serialises that as `""`. The five codes minted before the column exists would otherwise read as confirmed no-shows — the same rule the tracker's nullable `voice_score` / `fabrication_flag_count` follow. Any UI for it has to say "unknown".
- **Reading `user.id` after `touch_last_seen` raises `DetachedInstanceError`, and it is intermittent by construction.** The stamp commits, SQLAlchemy expires every attribute on commit, and `db.close()` then detaches the instance — so the *next* attribute read tries to refresh itself against a dead session. A throttled call never commits and never expires anything, so this fires only on the first request of each `SEEN_THROTTLE` window: the shape that reaches production looking like a flake. The gate reads the id inside the session and passes an int onward.
- **Throttled at 5 minutes** (`users.SEEN_THROTTLE`), because one page load fires several API calls and each would otherwise be a write to Neon. The question needs nothing finer. Best-effort like `usage.record_tokens` — bookkeeping may never turn a served request into an error.
- The throttle check asserts `_t1 is not None` **before** comparing. Without it both reads are `None` when the stamp is dead, they compare equal, and the check passes by never firing — caught by probing the defect in, per the probe-it-in-both-directions rule in `CLAUDE.md`'s Testing section.

### Phase 29 — accounts, and a tracker that reads its own replies (2026-09-13)

The binding decisions came out of an adversarial design critique (29 issues, 5 blockers) and a five-dimension review of the build (34 findings kept: 6 high, 14 medium, 14 low, one of them a verdict that a suspected hole is not exploitable). Every fix below is smoke-pinned (`B<n>`) or check-mirrors-pinned (30, `F<n>`) with its false-positive half beside it.

*(The Gmail half of this phase — OAuth, the network door, rules before the model, the windowed backfill, tracker
writes, the cron — is in `inbox.md`. The Arabic preference and numerals are in `tailoring.md`. The phase's
deferred / known-open list, which covers all three, closes this section.)*

**The gate — still ONE middleware.**
- **Every "who is calling" decision is made in `main.access_gate`, before routing.** That is what made `users.last_seen_at` able to see unrouted paths, and it is why the stamp STAYS in the gate: moving auth into a dependency would re-open that blind spot and split one decision across two places that can disagree.
- **Precedence: `X-App-Key` strictly outranks the `jf_session` cookie.** A bad key on a protected route is a 401 even beside a good cookie. **The one exception is an `_AUTH_OPTIONAL` path**, where a stale key falls through to the cookie (A10): a friend's phone still holding a dead invite code must be able to reach `/auth/login`, or it is locked out by the credential it is trying to replace. The frontend forgets a stored code when a request that carried it 401s, when `/auth/me` does not recognise it, and on any successful sign-in.
- **`_AUTH_OPTIONAL` is compared by `get_route_path(request.scope)`; `_GATE_EXEMPT` still compares `request.url.path` and needs both spellings.** The route path is bare locally and under Vercel's `/api` mount. A forgotten `/api` twin passes every smoke check, because the suite drives the unmounted app, and 401s only in production.
- **The order is credentials (401), then CSRF (403 `csrf`), then verification (403 `email_unverified`).** Credentials first, so a protected route with no credentials still says 401 rather than a misleading 403.
- **CSRF: with the gate ON, every POST/PUT/PATCH/DELETE that does not carry `X-App-Key` needs a non-empty `X-Requested-With`, cookie or no cookie, `/auth/*` included.** SameSite=Lax is not enough on its own — a top-level cross-site form POST still carries a Lax cookie — and FastAPI refusing a form body on a JSON route is an accident, not a defence. The frontend sends `X-Requested-With: jobfinder` on axios AND on the SSE `fetch`; **a new raw `fetch()` that forgets it 403s every write from that path.** With the gate OFF it applies only to a request carrying a session cookie and to `/auth/*` (FIXB B18): a keyless local request is the dev admin, and the installed Chrome extension sends no such header, so the unconditional rule 403'd it and every local script — installed software a deploy cannot update.
- **Verification skips exactly: every `_AUTH_OPTIONAL` path, `_UNVERIFIED_OK` (`/auth/resend`, `/auth/change-email`, `/auth/extension-key` — which refuses an unverified caller itself), and `DELETE /profile/account`** (the way out). Pinned: holding an unverified cookie, `POST /auth/login` for ANOTHER, verified account returns 200. Invite codes and the admin are verified by construction, and `users.signup_source` defaults to `""` so the ADD COLUMN shim grandfathers every pre-accounts user as verified.
- **The gate decides from a plain `_Identity` tuple read INSIDE the DB session, after every commit** (A11). `touch_last_seen` AND the sliding session renewal both commit, and a commit expires every attribute — the `DetachedInstanceError` recorded under `last_seen_at`, now with two writers. Pinned by a request that triggers both writes and returns 200.
- **A renewed session re-issues its cookie** (at most every 12 h, never past `SESSION_MAX_DAYS` = 180 after sign-in) unless the route itself set or cleared the cookie — re-issuing after a logout would resurrect it.

**Cookies.**
- **`jf_session` and `jf_oauth` are HttpOnly, SameSite=Lax, `Path = root_path or "/"`** — `/api` under Vercel's mount — and **`Secure` only when the request is https** (`sessions.is_https`), or local http dev silently drops the cookie. Sessions are opaque tokens stored as sha256, revocable.
- **The smoke test's Secure-cookie probe runs on a THROWAWAY TestClient and asserts the raw `set-cookie` header** (A13): a Secure cookie in the shared jar poisons every later check. New route modules read `get_settings()` per request, never a module-level `settings`, and the blank-before-import env loop sets the bool vars to `"false"`/`"true"`, because pydantic-settings raises on `""` for a bool.

**Tokens.**
- **A mailed token is bound to the address it was sent to** (A1, the critique's blocker #1). The payload stores the normalised email; consuming requires `payload.email ==` the login's CURRENT email, unconsumed, unexpired. Issuing a token consumes every earlier one of that purpose; change-email, change-password and reset consume every outstanding verify AND reset token; a reset link is single-use. A code issued before a change-email reads `used`.
- **…except on a 1-in-10^6 repeat, and the exception is correct** (P29-SIXDIGIT-FLAKE, 2026-09-21). A fresh draw can repeat the six digits of the code it supersedes. `_verify_code` compares the typed digits with the LIVE token before `_stale_code` looks at dead ones, so the old code then IS the live code, and it verifies. That is no weaker than one blind guess, against the five a token allows, and it still needs the account's own pending session. **Never move the `_stale_code` test above the live compare** to make `used` absolute: on the same coincidence it would refuse the holder of the newest mail. The draw is ONE named function, `accounts._draw_code`, and the smoke test rebinds it at the name `_issue` looks up at call time, the way it rebinds `auth_email._resolve_sender`, so never `from app.core.accounts import _draw_code` anywhere: a second binding is one the rebinding cannot reach. Both halves are pinned in 28f. The three checks that replay a superseded code (the resend, the change-email, A3's second signup) run the superseding request through `_unlike28`, which draws from the real generator but never the spent code and asserts `drawn == [the code just mailed]`, so a seam that goes dead is red rather than green. The ordering twin forces a dead token and the live one onto the same digits and requires the newest mail's code to verify. **A new check that replays a superseded code goes through `_unlike28`**, and a new check that expects a verify to succeed reads the account's `verified` state BEFORE it: `_verify_code` answers an already-verified account 200 without comparing anything, so without that read it passes by never firing.
- **A signup over an existing UNVERIFIED login never merges** (A3): the same password signs in (and mails a fresh code when the cooldown allows); a different one is 409 `email_taken`.
- **A reset on an unverified account verifies it, revokes every session, rotates the extension key and mints one new session** (A2). The only unverified logins that can exist belong to email signups holding no other credential, which is what makes a reset a safe takeover — and why Google sign-in and `/auth/claim` were deferred rather than built.
- **A verify LINK never mints a session and verifies only from a live session of the SAME account** (FIXB B1). Mail scanners pre-fetch GETs, so the link page needs a tap; and without the session rule a squatter signs up with someone else's address, the owner clicks "Confirm", and the SQUATTER's account is verified with its extension key one call away. Opened anywhere else it is 400 `session_required` and the page says to enter the 6-digit code on the device where the account was created. A code needs that pending session too.
- **An address is ONE plain addr-spec: `parseaddr(e)[1] == e` plus the regex** (FIXB B7). `x<victim@y.com>` was a distinct login, budget key and throttle key that SMTP delivered to `victim@y.com`. A plus tag, an apostrophe and 254 characters stay valid (pinned).

**Throttles and the security log.**
- **DB-counted, write-then-count, keyed on `HMAC-SHA256(auth_key, …)[:32]` — never plain sha256** (IPv4 reverses in seconds), and email keys are HMACs too, so a closed account leaves no plain address in `auth_events`. `auth_key` derives from `AUTH_SECRET`, else `CRON_SECRET`, else `APP_ACCESS_CODE`; rotating it resets the counters and nothing else. Client IP is the first `x-forwarded-for` hop only when `VERCEL` is set (Vercel overwrites the header), otherwise the socket address; IPv6 counts per /64.
- **Closing an account cannot reset a limit** (A7). `purge_on_close` deletes logins, tokens and sessions but only NULLs `auth_events.user_id`, because those rows are keyed on an email or a network: deleting them would make "close and re-sign-up" a way to reset the 30-wrong-codes-per-address-per-day ceiling. Pinned in exactly that shape.
- **Retention is 30 days, pruned on sign-in AND by the inbox cron** (FIXB B19). Pruning only on write left a quiet instance keeping the log forever, contradicting the privacy page. A session row's network label is an IPv4 /24 (`a.b.c.x`) or an IPv6 /48, never the full address.

**Mail budgets.**
- **200 auth mails an hour across all users, and nothing is sent over budget** (503 `email_unavailable`): the owner's SMTP account also carries the job alerts. Signup preflights the sender and the budget before creating anything.
- **Per recipient, three allowances that cannot drain each other**: verification mail 3/h (resends capped below it); **reset mail its own 3/h** (FIXB B4 — a squatter polling resends held the owner's reset link out indefinitely); and **the "password changed" security notice is EXEMPT from the per-recipient cap, global cap only** (FIXB B5 — three anonymous `/auth/forgot` calls silenced the one mail that tells the owner an attacker changed the password).

**The extension key.**
- **The key IS `users.invite_code`: a full `X-App-Key` credential with no expiry that also opens the web through "Have an invite code?"** So for an email account it is rotated on EVERY reset, password change and "sign out of other devices", in the same transaction (FIXB B1) — before, a key read by an attacker outlived all three while the copy promised "every other device was signed out". The responses carry `extension_key_rotated` and the notice mail says the key was replaced. **The admin's key is never rotated**: `APP_ACCESS_CODE` is the only way back into a deployed instance (the pinned false-positive half). A device signed in by that code stores the returned key under `ACCESS_CODE_KEY`, or its next request 401s.

**Sentry.**
- **`sentry_sdk.init` is built only by `sentry_scrub.sentry_init_options`: `include_local_variables=False` plus a `before_send` that drops frame `vars` and redacts every configured secret value** (settings named key/secret/password/token/dsn/access_code/database_url, at least 6 characters), and DROPS the event if scrubbing fails. Measured before: sentry-sdk 2.x defaults to local variables, and one exception inside an inbox sync shipped `OPENAI_API_KEY`, `CRON_SECRET` and email subjects and snippets. Mail content cannot be recognised by value, so the sync logs a failure as the exception TYPE and the failing frame's location only — never its message, never a traceback (AST-pinned). The smoke test initialises the real SDK from the same function, so the options it drives are the ones production runs.

**The admin API and the sign-in address (P29-ADMIN-EMAIL, 2026-09-21).**
- **`users.email` mirrors `user_logins.email` for every account with a login, and `PATCH /admin/users` may set it freely only for an account WITHOUT one** (an invite code, or the admin while it has no login row), where it is a contact label and the pool is `u:<id>` whatever it says. Signup, Google signup and change-email each write both columns; the admin PATCH was the one writer that broke the mirror. It wrote `users.email` alone and answered 200, so its answer showed `email` and `login_email` disagreeing, and `/profile/me` and `/auth/me` gave two answers about one account, while sign-in, reset mail, token binding, the throttles, the Google link and the monthly pool all kept following the login. For an account with a login it now accepts only **the sign-in address itself** (any case or spacing; stored in the login's one spelling, which also heals a drifted label) or **the label's current value** (a client sending the list's own row back is not making an edit, and is never refused), and answers anything else 400, judged beside the B7 plan check before any field is applied.
- **The admin API never writes `user_logins.email`, and the obvious "update both" fix is the dangerous one.** It re-keys the monthly pool at the next reserve (the month restarts at 0, or joins another person's never-wiped pool: a limit reset through a door A7/B2 never considered); it keeps `email_verified_at` on an address nobody proved, so `/auth/forgot` mails a reset link to whoever owns the typed mailbox and a typo hands them the account (production's admin included, since its login row was moved in on 2026-09-17); it 500s on the unique index for a taken address; and it skips the B7 addr-spec check and the session revocation and key rotation every other credential move performs. A confirmed address has no move flow at all (`change_email` refuses it), and moving one is a new feature with owner decisions in it, not an admin edit.
- **Compared through `normalize_email`, never `quota.canonical_email`**: `firstlast@gmail.com` and `first.last@gmail.com` are one pool but two sign-in strings, so the second spelling is refused. **The 400 sentence is chosen by `email_verified_at`**: only an unconfirmed address is pointed at the verify page, because a confirmed one has no such door (the house rule about claiming more than the code does, applied to an admin API).
- **Existing drift is not repaired automatically.** A row whose `users.email` already differs from its login (an earlier PATCH, or production user 1, created by `ensure_admin` with no `users.email` and later given a login row by hand) keeps showing it in `UserOut.email` and `GET /profile/me` until a PATCH sends the sign-in address. `/auth/me` and Settings read the login first and never showed it. **A future `/auth/claim` must write both columns** the way the other three writers do, and from then on a claimed account's label is no longer admin-editable.
- Pinned in smoke 28, 32.14 and 33 (the `P29-ADMIN-EMAIL` blocks): a confirmed, an unconfirmed and a Google-only login are refused, a refusal applies nothing sent beside it, and the pool key and this month's count do not move — beside an invite-code label edit, a re-sent sign-in address and the round-trip of a drifted row, which all succeed. Probed three ways: the login predicate dropped (the two label twins go red), the unchanged-value branch dropped (the drifted round-trip goes red), and the naive move committed behind a 400 (the pool and login halves go red on their own, `used=0`).

**Deferred on purpose, and known open.**
- **Deferred** (each widened the account-takeover surface): `/auth/claim` for invite-code users, and the per-device sessions list with per-session revoke ("sign out of other devices" shipped instead). **Google sign-in is no longer deferred** — the owner reversed that on 2026-09-14 and Phase 30 built it, with the linking rules the deferral was waiting for: resolution is by Google's `sub` and nothing else, an address Google is not authoritative for is refused with `not_authoritative`, a Google sign-in over an unverified email signup supersedes it the A2 way, and an admin or invite-code account can never be linked because neither has a login row. See the Phase 30 section.
- **Known open**: a job reply first filed in Spam is never imported after it is rescued (the cursor is `internalDate`-based and `messages.list` excludes SPAM); `/auth/forgot` sends SMTP inline for a known address, so its timing can reveal which addresses have accounts; `PATCH /admin/users` email edits do not update `user_logins.email`; the real Google path has run only through a fake transport (PKCE with a client secret on a Web client, the snippet on a `format=metadata` read, and the two cron entries are unconfirmed); the frontend's sync-error and refusal codes mirror the backend's by hand with no check pinning them (an unknown code falls back to a generic sentence, never a raw code); three smoke checks compare a superseded 6-digit code with the live one and would fail on a ~1-in-a-million coincidence.

### Phase 30 — login first, Continue with Google, and the verify link (2026-09-16)

*(The sign-in half of Phase 30. The phase's intro, the monthly pool, the charging rules and the rest of its knobs
and known-open list are in `cost-and-quota.md`.)*

**No feature is anonymous any more.**
- **`POST /public/scan` is GONE**, with its per-instance per-IP `RateLimiter`. The scan is `POST /tools/scan` behind the gate, with a `scan` daily cap and one monthly use, and `/scan` is a redirect to `/signup?next=%2Ftools%2Fscan`. What replaced the limiter is the per-user pool, the daily cap, the verification gate and the signup throttles — a limiter counting per warm serverless instance was never the bound it looked like (PLAN 20.5/C4).
- **A public call to action is a sign-up door**, `signupFor(dest)`, one helper both the landing and the marketing shell import. "Open the app" links keep `/app`, because `AppLayout`'s guard sends a signed-out visitor to `/login?next=…`, which is the right door for someone coming back. check-mirrors 32(a) pins it, and it reads the helper's BODY as well as its call sites: `return dest;` would have left every CTA pointing at the bare feature route with 32(a), check 9 and `tsc` all green.

**Continue with Google, and why it is a second Google project.**
- **Sign-in has its OWN Cloud project** ("JobFinder Sign-in", In production, `openid email profile` only) with `GOOGLE_SIGNIN_CLIENT_ID` / `_SECRET` and **no fallback to the Gmail pair** — a fallback would silently put sign-in on the Gmail project. Three reasons the split is structural, not tidiness: **revocation is project-wide**, so a Gmail Disconnect or the privacy wipe's `revoke_stored_grant` would also drop the sign-in grant; the **restricted-scope user cap belongs to the project**, and exhausting it can disable Google sign-in for every user of that project; and `include_granted_scopes` would pull `gmail.readonly` into a sign-in and lose the basic-scope exemption.
- **The ID token's signature is NOT checked, and that is deliberate and bounded.** It arrives only from the token endpoint, over TLS, authenticated with the client secret — the one case Google and OIDC Core allow it — and the JWKS host is deliberately absent from `_HOSTS`. Everything else IS checked: `iss` in both spellings, `aud` as a string or a list, `azp` when present, `exp`/`iat` with 60 s and 300 s of slack, the `nonce` in constant time, `sub` as a 1-255 character string, and `email_verified is True` so the STRING `"false"` fails. **Any browser-delivered credential must verify RS256 through a deliberate `_HOSTS` change and must never reuse this function** — the docstring says so, and `_signin_claims`' only caller is AST-pinned.
- **Resolution is by `sub` and nothing else.** An address Google is not authoritative for (no `hd`, and `@googlemail.com`, which is undocumented) is refused `not_authoritative`, for existing addresses as well as new ones. A verified email login is LINKED; an unverified one is SUPERSEDED the Phase 29 A2 way, with its password cleared. Both revoke every session and rotate the extension key in the same commit, and both send a notice. **An admin or invite-code account can never be linked**, because neither has a `user_logins` row for anything to reach. **That holds for the code path and no longer for production's data**: on 2026-09-17 the owner signed in with Google, which created an empty account, and asked for it to be the admin, so its Google login row was moved onto user 1 by hand. The admin now HAS a `user_logins` row, and whoever controls that Gmail inbox can reach admin, through Continue with Google or `/auth/forgot`. The access code still works and the admin's extension key is still never rotated.
- **A Google signup is created VERIFIED with no mail**, because Google already verified the address — which is what makes a Google account 10 immediately spendable uses with no mailbox round-trip. It counts on the SAME per-network `signup` counter as the email door.
- **The connect is bound to the browser that started it** by `jf_gsi` (HttpOnly, Lax, Secure on https, 600 s) — a different cookie NAME from the Gmail flow's `jf_oauth`, so the two flows cannot overwrite each other's binding. State is single-use through a conditional UPDATE whose rowcount is the decision, and the binding is compared with `compare_digest` BEFORE the claim.
- **Static landing copy names Google in ONE place: the last sentence added to `landing.faq.a3`, in both locales, on 2026-09-21**, after production's `/auth/me` answered `google_enabled: true`. A static page cannot know whether sign-in is configured, and a Google account is created verified, so "confirm the address" is false for it — which is why the sentence waited for the button, and why it offers Google beside the email steps rather than rewriting them. **If Google sign-in is ever switched off in production, take that sentence out of both locales.** No other landing or marketing copy may name Google; `landing.hero.access` ("confirm your email and you're in") still describes the email door only.

**The verify link works on any device**, and the backend rule that made it awkward is untouched: `sessionStorage` holds the raw token (tab-scoped, shape-validated, one hour), and it is spent after a log in on that device. It is KEPT on `session_required` and on a network error and forgotten on success or a dead token, so a log-out-then-log-in can still finish. The squatter still loses: the victim cannot log in to the squatter's account, the backend refuses any other account's session, so the stored token is never spent.

**The Phase 30 knobs that belong to sign-in.**
- **`sessions.MAX_NEXT` (512) lives inside `safe_next`, not at each door**, and that placement is the fix. `/auth/google/start` is anonymous and STORES its `next` for the round trip, so an unbounded one was a credential-free write of megabytes into the production database, retained 30 days — reproduced at 4 MB in one request. A cap on the request model alone would not have closed it: the callback rebuilds its destination from the STORED row, so a row written before the cap would still emit an oversized `Location`, which breaks a completed sign-in as well as a refused one. `GoogleStartIn.next` carries the 512 too, so an oversize body is refused rather than silently rewritten to `/app`.
- **`GOOGLE_FAIL_PER_IP` (60/hour) bounds ROWS, not the sign-in.** The callback answers an anonymous caller, needs no state row to fail, and recorded one `auth_events` row per request — so anyone who found the URL could grow that table for the 30 days of retention and bury the real sign-in log. Over the allowance the attempt's own row is taken back and the redirect is unchanged, so a whole CGNAT address can still sign in; it only stops being logged. The earlier reasoning ("state and binding are 256-bit, so a throttle would guard nothing") was sound about GUESSING and silent about the write.

**Known open — the sign-in half of Phase 30's list.**
- **The real Google path first ran on 2026-09-17**, when the owner's own sign-in worked on production. Before that it had run only through the fake transport. `@googlemail.com` plus work addresses with no `hd` are refused by design. The consent screen shows the domain, not the app name, until a custom domain is brand-verified, and in-app browsers (WhatsApp) are untested.
- **Still deferred**: `/auth/claim` for invite-code users, and the per-device sessions list.

### `/auth/forgot` answers at one pace (P29-FORGOT-TIMING, 2026-09-21)

- **The body was always `{ok}`, but the time was not.** A known address ran about ten DB statements and a whole Gmail SMTP session (banner, EHLO, STARTTLS, AUTH, DATA, QUIT) inline before the answer. An unknown one ran one SELECT after the throttles. So ONE timed request per address was enough, with no statistics needed. It was also the one probe that costs the prober nothing at an address with no account (no mail goes anywhere), at 20 an hour per network. And a DB error on the known path was a 500 that only a known address could reach.
- **`accounts.forgot` now waits out a minimum response time, `AUTH_FORGOT_FLOOR_MS`, for every outcome past the throttles**: unknown, inactive, no link base, reset budget spent, global budget spent, no sender, send failed, sent. **The 3000 ms default is a PLACEHOLDER. Nobody has measured it against production's SMTP**, and until someone does, a real send slower than 3 s still reveals the address. `0` turns the floor off, which is the switch if the owner declines the wait.
- **How to measure it (NOT done: it mails a real inbox).** From outside, time `POST /api/auth/forgot` with `X-Requested-With: jobfinder` using `curl -w '%{time_total}'`. Make three calls for an address that has an account, interleaved with three made-up addresses. FORGOT_PER_EMAIL allows three an hour, and each known call mails a live reset link to that inbox, which is harmless unless clicked. Since 2026-09-17 the owner's own address is the ADMIN's login. Set the floor to about 1.5x the largest known-minus-unknown gap, then repeat the six calls after the deploy: both sets should sit at the floor. **Do not rely on an INFO log for this.** Nothing in the backend configures logging, so the root logger stays at WARNING and an INFO line never reaches Vercel's runtime logs, which keep only about three hours anyway.
- **The send stays INLINE, and nothing runs after the response.** No `BackgroundTasks`, no thread, no outbox. Nobody has measured that work after the response completes on Vercel's Python runtime (`waitUntil` is documented only for Node's `@vercel/functions`). `routes.py` already treats work done after the client leaves as unreliable, and a reset mail lost there would be invisible behind `{ok}`. So **a send slower than the floor is waited for, never cut loose**: in that tail, reliability wins over secrecy. That tail is the known residue. Each overrun logs `forgot: took N ms, over the M ms floor` at WARNING, numbers only, which does reach the runtime logs. Smoke-pinned with a 4 s send against a 2.5 s floor: the mail goes, the answer comes at 4.0, and no wait is added on top.
- **The clock starts AFTER the throttles, just before the lookup.** The two throttle writes cost the same for every address. They also carry the request's first DB round trip (the gate opens no session for an anonymous request), which is where a Neon scale-to-zero wake-up and a `pool_pre_ping` reconnect land. At this deployment's traffic Neon is usually asleep. A clock started at `valid_email` would let a cold database use up the floor on the unknown path while the known path (wake-up plus SMTP) ran past it, which is the same leak again. Pinned with a throttle that costs 5 s on the fake clock: both addresses end at 12.5, where a clock started early gives 10.0 and 10.8.
- **The transaction ends BEFORE the wait** (`_end_transaction`, a guarded rollback; every write has already committed). Otherwise the unknown path sleeps inside the read transaction autobegun by `throttle.hit`'s count and `login_by_email`. It would hold one of the instance's pooled connections for the whole floor, idle in transaction on Neon. The pool is the default QueuePool: 5 connections plus 10 overflow, with a 30 s `pool_timeout`. About fifteen concurrent padded calls would stall every route on that instance and turn them into 500s. IPv6 is throttled per /64, so one /48 holds 65,536 FORGOT_PER_IP buckets. Pinned by reading `engine.pool.checkedout()` inside the fake `_sleep`.
- **A throttled call and an invalid address are answered at once, with no wait.** Both are decided before the lookup, so they look the same for every address, and a flood of refused calls holds no thread. **The two `throttle.hit` calls must never move after the lookup**, or the throttles become the oracle. A padded call does hold one threadpool thread, because the route is a sync `def` (anyio's default is 40 threads per process); FORGOT_PER_IP bounds that. If the floor is ever raised far, the follow-up is an `async` route that `await`s the wait. At friends-beta traffic it is not needed.
- **A failure inside the flow answers `{ok}` at the floor and logs ONE `logger.error` naming the exception TYPE.** ERROR, not WARNING: Sentry's default LoggingIntegration makes an ERROR record an event and a WARNING only a breadcrumb, and a reset flow that fails in silence is what "unknown is never zero" forbids. Never `exc_info` and never `str(exc)`: a SQLAlchemy error's text carries its bound parameters, which here are the address. This is AST-pinned, and the detector is probed on six leaky variants.
- **Testing it.** `accounts._monotonic` and `accounts._sleep` are the seams, patched where `forgot` looks them up. The smoke block therefore runs on a fake clock and never really sleeps, and every sender in it moves that clock. The suite's header sets `AUTH_FORGOT_FLOOR_MS="0"`, or every forgot call in sections 28, 30 and 32 would really wait. It must be `"0"`, never `""`, which pydantic refuses for an int. A default twin pins the shipped default at 1000 ms or more. Each "ends at the floor" check sits beside a branch that must also SEND, because a pad that sends nothing passes the unknown-address check on its own. Every pin was probed red, either on the old code or with one of twelve mutations of `forgot` and its route, and no probe aborted the suite.
- **What this does NOT close.** It is not a promise that nobody can tell who has an account:
  - Signup answers 409 `email_taken` for a verified address, and for an unverified one with a different password. The page then says "An account with this email already exists" and offers "Log in instead".
  - `/auth/change-email` answers 409 for another account's address.
  - Login runs one extra SELECT for a known address. scrypt is already equalised, so the gap is DB-scale.
  - The global mail budget shows through signup's 503 at its edge.
  - Whether keeping account existence private is a product goal is a question for the owner, unanswered as of 2026-09-21. The forgot fix does not depend on the answer, and signup and change-email were left as they are.
  - Unchanged as well: probing a known address still mails its owner and consumes their previous reset link (A1).
