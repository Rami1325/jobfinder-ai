## The real-key A/B harness for the tailor

**Prompt quality — the real-key A/B harness** (`backend/tests/ab_tailor.py`, added 2026-08-30):
```powershell
cd backend
.\.venv\Scripts\python.exe -m tests.ab_tailor --stub                       # free plumbing check
.\.venv\Scripts\python.exe -m tests.ab_tailor --prepare --jobs 6           # cache fixtures, 1 call/job
.\.venv\Scripts\python.exe -m tests.ab_tailor --variants baseline,x --reps 3
```
**The smoke test cannot see prompt quality and never will** — it drives `tailor_resume` through `StubClient`, which pins the *mechanism* (routing, shapes, guards) and says nothing about whether the real model curates well. Every quality claim in this repo was unmeasured until this harness existed, and the first run it made found a defect nine months of offline checks had been green through: the tailored CV shipped **66 skills, median, against a 66-skill master** — i.e. more than it started with — with 18.3% of them terms the job named. So: **it spends real money and is never run by CI**, `tests/fixtures/ab/` is git-ignored (it holds the owner's own resume and every measured run), and `backend/tests` is already in `.vercelignore`.

Four things about it are load-bearing, each a way the measurement could have lied:
- **The JD is analysed ONCE and cached.** `analyze_jd` is itself an LLM call at temperature, so re-running it per variant varies the *input* while claiming to vary the prompt — and it moves the coverage denominator, which is the metric under test.
- **Every metric is the app's own function** (`scorer.keyword_analysis`, `keyword_guard.lost_keywords`, `voice_audit`, `page_count`). A harness that writes its own matcher grades the code with a different opinion from the one the code holds — the "one matcher, one answer" rule, applied to the grader.
- **The counterweights are not optional.** Cutting skills is trivially easy and the last release fixed the *opposite* defect, so `n_skills` is never read alone: `lost_keywords`, `coverage_after`, `fabrication_flags`, `voice_score` and `pages` sit beside it and a variant that buys a shorter list with any of them is a regression. The decision rule is written down BEFORE the run.
- **It attributes, rather than measuring the end of the pipeline.** A probe records what the MODEL returned and what `preserve_keywords` then ADDED, because "too many skills" has two possible authors and the shipped count cannot tell them apart. That probe is what killed the obvious theory: the guard added **zero** on every run, so `MAX_RESTORED` was never the cause and lowering it would only have re-opened the keyword-deletion defect. **Patch `app.core.tailor.preserve_keywords`, not `keyword_guard`'s** — the caller did `from ... import preserve_keywords`, so the name is already bound and patching the definition module is a no-op. The `max_restored` knob has to write both bindings for the same reason.

It also measures two things that had been waiting on a real key: **PLAN 20.1** (serial LLM latency — measured at **25.0 s** per tailor: TAILOR 8.7 s, CREDIBILITY 8.0 s (now removed), PLAN_CV 3.8 s, FIT_SCORE 1.6 s ×2, HUMANIZE 6.3 s when it fires) and the real per-tailor cost (**~$0.005**, 16.5k prompt + 3.8k completion tokens), which is what 19.1's price decision was waiting on.

## The inbox classifier's harness

**The inbox classifier has its own real-key harness** (`backend/tests/inbox_eval.py`, Phase 29, 2026-09-13):
```powershell
cd backend
.\.venv\Scripts\python.exe -m tests.inbox_eval --stub                                         # free plumbing check
.\.venv\Scripts\python.exe -m tests.inbox_eval --models gpt-4.1-nano,gpt-5.4-nano,gpt-4o-mini --reps 2
```
Same rules as `ab_tailor`: **it spends real money, is never run by CI, and `--stub` is the only mode an unattended run may use** (the stub's misses are canned answers, not a result). It grades the pipeline that ships — `inbox_sync._stage` decides noise and templates exactly as a sync does and only what it passes reaches `inbox_classifier.classify`, the real prompt and post-validation — and compares companies with the app's own `normalize_company`. Fixtures: 49 synthetic emails modelled on a real job-seeker inbox (22 English replies, 7 Hebrew, 10 alert digests, 6 non-job traps, 4 edge cases); the rules settled 14 per rep and 30 reached the model. **The decision rule was written before the run**: the cheapest model within 3 points of the best kind accuracy that reads NO rejection as an interview (that error moves a closed application into the Interview column). Measured, 2 reps: gpt-4.1-nano 98.5% kind / 100% company / 100% title, 0 rejections read as interviews, p50 1.07 s, $0.0059 per 60 calls; gpt-5.4-nano 100% / 93.5% / 100% (it keeps sender suffixes, "Brightline HR"); gpt-4o-mini 100% / 100% / 100% at $0.0090. **Shipped `gpt-4.1-nano`** (`inbox_classifier.DEFAULT_MODEL`, ~$0.0001 per classified email); its one miss — a Hebrew agency outreach read as "interview" — carried a BLANK company, which the apply rules send to Needs review, never onto the board. `INBOX_MODEL_ID=gpt-4o-mini` is the one-variable upgrade. 0 noise leaks and 0 job mails skipped by the rules on every arm.

## The frontend's only test suite: `check-mirrors.js`

Hand-copying had failed three times, the third leaving a second, WRONG account of who may spend the owner's money. It degrades loudly, into the summary line, only when NEITHER file is in the build: `.vercelignore` drops both from the Vercel upload, and ONE without the other is red, since that is a moved or deleted file. So **`.vercelignore` must list both or neither**, or every Vercel build fails; CI checks the whole repo out and compares them there) and **15/21**, which pin the POLARITY of a gate rather than the presence of an identifier — a one-character inversion (`!isMaster ?`) used to pass green:

1. every `ResumeModel` field appears in `mergeResumes`' returned object — the exact bug above, and the only thing that catches the next field added to the model
2. every `EditSection` has a `sections.<key>` label in BOTH locales
3. every `EditClass` has a `groups.<class>.title` in both locales
4. keyword STATUS is never computed in TypeScript (see the coverage invariant in `scoring.md`)
5. every `BlockKind` and `BLOCK_FIELD_KEYS` entry has an `edit.blocks.*` / `edit.fields.*` label in both locales
6. `dkey` has exactly ONE definition, in `lib/resumeBlocks.ts`
7. every block path `ResumeView` emits is in `BLOCK_PATTERNS` — a new section would otherwise ship a tappable block whose editor opens EMPTY, which `tsc` cannot see because paths are strings
8. en↔he locale key parity per namespace, normalising i18next plural suffixes (Hebrew has a `_two` form English does not). It walks the **union** of both directories: driving the loop off `readdirSync("en")` alone meant a namespace deleted from *that* side was never looked at, so its orphaned Hebrew twin kept shipping as a chunk nothing read
9. every nav `to:` in `AppLayout.tsx` resolves to a declared `<Route path>`, and every nav `labelKey` / `t("nav.*")` resolves in **both** locales. `tsc` sees neither — a route path is a string and a locale key is a string. A dead `to:` leaves the tab permanently unlit and the tap falls through the catch-all to the *marketing* landing, which reads as "you got logged out"; a renamed `labelKey` renders the raw key at 12 px in Hebrew, and **check 8 stays green because en and he are still in parity with each other**. Deliberately scoped to `AppLayout.tsx`. The original carve-out (`BuilderPage` called `t("nav.back")` against the *builder* namespace, so a repo-wide scrape would have fired on legitimate input) died with `/builder` in 23.4; the scope survives because it is now what makes the file boundary load-bearing — **the top menu panel and the account menu are defined INSIDE `AppLayout.tsx` for exactly this reason** (23.5). A nav label in any other file is guarded by nothing, and check 8 stays green while the raw key renders at 12 px in Hebrew
10. the keyword matcher still finds a Hebrew word behind a prefix. `countOccurrences("פייתון", "…בפייתון")` returned **0** while `scorer._keyword_present` called the same text *covered*, so a chip rendered inside the green **Matched** group carrying `משרה 2 · אתם 0`. Hebrew's inseparable prefixes (ב/ל/ה/ו/מ/ש) glue onto the noun and the boundary lookbehind counted them as word characters. Check 4 could not catch it: that check forbids computing a **status** in TypeScript and says nothing about a count. The false-positive half (`Java` ∉ `JavaScript`, `ניהו` ∉ `לניהול`) sits in the **same** table on purpose — "make the Hebrew case pass" is trivially satisfied by deleting the guards. The classes and the boundary shape are parsed out of `lib/keywords.ts` rather than restated, so the check cannot drift into testing its own copy

11. **no reveal animates its own height.** `animate={{ height: "auto" }}` tweens from 0 to a measured value, and on a page that re-renders mid-tween the element is left frozen at the interpolated px with `overflow-hidden` clipping it. This shipped SEVEN times: `Disclosure` documented the defect and was fixed, then the pattern came back in `JobsPage` (Replace froze at **80px over a 287px dropzone**, so the master resume could not be changed at all; Customize froze at **78px over 280px of fields**, so the search settings read as deleted), `AlertsCard` ×2, `TailorPage`, `MatchReport` and `marketing/FAQ`. `tsc` cannot see it — it is a string inside a prop object. Scoped to an `animate`/`initial`/`exit` prop so an ordinary CSS `height: auto` in a `className` never fires, and it probes its own detector in both directions (a check that cannot match its defect shape passes for ever)
12. **a replaced master resume reaches the DOCUMENT.** The master is cached in TWO module-level bindings — `useMasterResume`'s `cache` and `tailorStore`'s `resume` — and only the first had a way in from outside, so a CV replaced on the Jobs page never reached `/app` (see the invariant in `document-editor.md`). `tsc` is quiet because both caches are correctly typed and correctly written; the defect is that one of them is never written at all. Three assertions: `tailorStore` exports `adoptMaster`, `setMaster`'s body calls it, and — the one that will still be true in a year — **every key `applyBlockEdit` resets is also reset by `adoptMaster`**, DERIVED from `applyBlockEdit` rather than restated. Both functions answer the same question ("the document changed — what on screen now describes a resume that no longer exists?"), so a field added to one and forgotten in the other is check 1's bug in a new costume
