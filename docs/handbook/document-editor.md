### Phase 22 — the document surface

- **The tailor page IS the document.** `/app` renders the resume (`ResumeView`, `surface="sheet"`) with a toolbar over it; tailoring is an overlay (`TailorOverlay`), not a page. There is no stepper. `shown = effectiveResume ?? resume` is the whole of "the page always has a CV".
- **Editing never writes back to the MASTER from a tailored draft — AMENDED IN 23.7, read that section.** The original rule was `onEditBlock` is passed only when `!result`, because with a result up the document is a memo recomputed and discarded on every accept/decline, so writing into it needs an override layer that survives the re-merge. 23.7 BUILT that layer: the tailored document is typed on, through an anchor-keyed override map that is discarded with the result. What survives intact is the second half — tailoring is a *review layer* that never writes back to the master. So: master ⇒ edit the document; tailored ⇒ edit a per-application overlay.
- **`lib/resumeBlocks.ts` is the only reader and writer of a block.** The document addresses blocks by path (`@exp.2`, `@exp.2.b.1`, `@skills.python`) and `readBlock`/`writeBlock`/`removeBlock` resolve them. **Since 23.1 the document is TYPED ON, and the split is DERIVED.** A block that is ONE model field (`@contact.name`, `@headline`, `@summary`, every `@*.b.*`, `@skills.*`, `@cert.*`) is `contentEditable` on the paper whenever the document is the master — no editing mode, no `editingPath`; a tap places the caret, and while it is there **nothing re-renders**, which is what keeps it alive (react-dom skips a text child whose string is unchanged, so a coverage response or the spotlight timeout cannot disturb it). Commit is on blur or Enter. The split is `inlineField()`, derived from `readBlock` — one field means a caret, more means the panel — so it **cannot drift from the reader**: add a second field to a block and it stops being typed on by itself.
  `BlockEditSheet` survives for the six COMPOUND blocks only. **The sheet edits an ENTRY, not a field** — that is what dissolves the fused-text-node problem (an experience meta line is five model fields in one text node), so never "fix" it by splitting `MetaLine`: that re-opens the bidi-isolate problem and buys nothing.
  **The sheet's old justification was measurably false; it is recorded so nobody restores it.** It claimed "at 390px an A4 page renders at about 45% scale, so body text is roughly 6px". That describes the PDF `<iframe>` in `DocumentPanel`, not `ResumeView`. Measured on the running app at 390px: `.sheet` is `transform: none`, 347.3 px wide, body text 14 px. What survives from it: no hover on a phone, and a toolbar near the caret fights the on-screen keyboard — so inline editing grew **no toolbar at all**.
  Each of these is a bug avoided, not polish: both delegated handlers bail on `isContentEditable` FIRST or the `preventDefault()` on `" "` kills the **space bar** in every editable block; `contentEditable="plaintext-only"` is **probed** with `true` as fallback, because its invalid-value default is *inherit* and an unsupporting browser would render the block silently non-editable; paste is forced to plain text (a bullet is a `string` through both renderers into `_wrap_lines`); `spellCheck=false autoCapitalize="off"` or iOS rewrites "gRPC" to "GRPC"; Enter is guarded on `isComposing`; and an unchanged edit is refused **and the DOM restored by hand**, because React does not repair a browser-mutated node whose own string is unchanged.
- **Adding is one control at the foot of the paper** (23.2): seven FIXED rows — role, project, degree, military service, skill, certification, language — plus "+ Add a line" at the end of each entry's bullets. Fixed, not conditional on emptiness: creating the first project and the fourth are the same action, and a section appears when it has content exactly as both renderers do. A new item arrives **empty**, never placeholder-filled — a placeholder is a fabricated claim the moment it reaches a renderer. **That was asserted here and FALSE in the code until 2026-09-02 for three of the seven rows.** Skill, certification and language are addressed by their VALUE (`@skills.python` IS the skill), so an empty one has no path at all — `dkey("")` is `""` and `RE_KEYED` needs a character after the dot — and `insertBlock` answered that by minting the literal English strings `"New skill"` / `"New certification"` / `"New language"`. `applyBlockEdit` committed them on the same tick, so they rendered as chips, went into the DOCX and the PDF and reached the tracker with no Save; `check_fabrication` cannot see them because the ledger is built FROM the master, so the app's own truthfulness guard certified the invented string clean; and on a Hebrew CV they were untranslated English. **The fix is not a new address for a blank item — a keyed item is TYPED, never inserted blank** (`insertNamed`, the mechanism `AddSkillChip` already used: a real `<input>` whose *placeholder* is browser chrome, not a value). Inserting `""` instead would have been the same defect wearing a different hat: both renderers draw a chip for a blank skill, so there is no honest blank chip to store. check-mirrors 25 pins it by EXECUTING `resumeBlocks.ts` and measuring text over the whole model, so a placeholder in a field added years from now still fires.
  Two rules stop an abandoned add littering the document: **empty means remove** on the inline path (which `readBlock`'s `removable` comment always specified and nothing implemented), and a blank ENTRY is removed when its panel is cancelled, scoped to the entry that session created — deleting a pre-existing blank entry is the direction that loses data. The keyed kinds need neither now: nothing is written until text exists. `removeBlock` gained an `RE_ENTRY` branch at the same time: until 23.2 a job, project, degree or service **could not be deleted at all**.
- **There is ONE editor, and `/builder` is gone** (23.4). An 848-line from-scratch wizard plus two locale namespaces (fetched on every cold start — `i18n.ts` awaits all of them before first render) was a second editor for one resume, and it produced the "which one is my real CV" question it existed to avoid. It appeared in neither `primaryNav` nor `moreNav`, so it was already orphaned; its two entry points were `ResumeGate` and `TailorPage`'s empty state.
  **The cold start it existed for is preserved, on the same surface as everything else**: "Build one from scratch" on `/app` seeds a blank `ResumeModel` into the store and the document becomes a blank page you type on. Two things had to be true first, and both are: the header blocks (`@contact.name`, `@headline`, `@contact`, `@summary`) **render even when empty while editing**, or a from-scratch resume has no reachable block at all — they are unreachable otherwise, because `ResumeView` renders a section only when it has content. And an empty block shows a CSS placeholder (`[data-ph]:empty::before`), never the fallback string as text: **a placeholder rendered as text is committable**, which is how tapping the biggest target on a nameless CV could write "Resume" in as the person's name.
  **A blank page follows the UI locale, not `resumeLanguage`.** With no prose there is nothing to detect from and `resumeLanguage` returns "en" for an empty resume exactly as it does for an English one — so a Hebrew user starting from scratch would type into a left-to-right page. `ResumeView` checks whether any prose exists and falls back to `i18n.dir()`.
  Note for check-mirrors: check 9's documented carve-out ("scoped to AppLayout because BuilderPage calls `t("nav.back")` against the builder namespace") lost its only exception here. The check is deliberately left scoped anyway — widening it would be a behaviour change with no defect behind it.
- **An empty store is not "no resume" until the fetch has answered** (fixed 2026-09-22). `/app` rendered the upload card — "No resume yet? Build one from scratch" — whenever `shown` was null, and `shown` is null for the whole of `TailorPage`'s master fetch, so a person WITH a resume was told they had none for the length of the request: seconds on production, on the document load a sign-in redirect makes. A failed fetch landed on the same card, with a comment calling it "no saved resume yet", although `GET /profile/resume` answers a person with no resume with a 200 and `null` — a throw means we could not look, and the card then invited a first upload over a saved resume. `masterLoad` (`loading` / `done` / `failed`, local to the page, `done` from the first render when the store already holds a resume) picks among three things: a paper-height `Skeleton` in a `role="status"`, a failure line with Try again that re-runs the same loader, and the upload card, which appears only after a fetch that ANSWERED with nothing. It is page state, not `tailorStore` state, on purpose: a store key would be one more field for `adoptMaster` and `startTailor`'s derived reset (check-mirrors 12 and 13) to decide about, and nothing outside this page reads it. Verified at 390 px in both languages with the resume request delayed, failed and answered `null` in turn.
- **Block paths carry an `@` prefix and it is not decoration.** Without it `exp.0.b.1` is simultaneously a valid *edit id* (original indices, from `resumeDiff`) and a valid *block path* (effective indices) — string-identical, different meaning, silently swappable.
- **`mergeResumes` must return EVERY `ResumeModel` field.** It rebuilds the resume field by field; a field added to the model and forgotten here is silently DELETED the moment one edit is rejected. This shipped: `headline` and `skill_groups` vanished from the download, the tracker row and the cover letter, and `tsc` was quiet because both are optional. Check 1 exists for this.
- **Removing a skill is a TWO-FIELD write** (`skills` AND `skill_groups`). The model validator keeps `skills` as the flat union and only ever ADDS, so writing the group alone leaves the old spelling behind and the next round trip restores it — the deletion silently does nothing.
- ~~**Saving the master is EXPLICIT, never automatic**~~ **SUPERSEDED by PLAN 31.6/2 (2026-09-26): the master saves itself**, on the three backend fixes that LANDED in 31.6/1 (`data-and-privacy.md` has each: the slot, the version, the coalesced restore points), and *PLAN 31.6 — the master saves itself* below is how. Kept because the two rules at its end still hold for every save. What the three fixes were: version snapshots are per changed PUT with only 20 slots per (user, language) — 21 saves evict the uploaded original; `PUT /profile/resume` picks its row by *detected language* and carries no id, so one Hebrew word saves over the other-language CV; and there is no conflict check at any layer. Saving must also **omit the ledger** (the backend rebuilds it — the user typed these facts) and call **`resetMasterCache()`**, because `invalidateData` cannot reach `useMasterResume`'s module-level binding and nine pages read the master from it.
- **`useSaveMasterResume` swallows every error and returns `null`.** Correct for its documented best-effort use; never use it behind a Save button. It also only toasts on SUCCESS, so both upload paths must handle `null` themselves — without that, a failed save leaves the page showing a resume the server never stored and the next reload silently reverts it.
- **Every write to the master must invalidate BOTH caches.** `saveMasterResume` calls `invalidateData("master","masters")`, which clears the `dataCache` Map and *cannot* reach `useMasterResume`'s module-level `cache` binding. A caller therefore has to either call `resetMasterCache()` or push the new value through `setMaster` (which writes the binding). `TailorPage.onParsed` did neither: uploading a replacement on `/app` updated the backend while Jobs, Interview and every tool kept painting **and sending** the resume that upload had just replaced, until a full page reload. That is exactly the failure this rule was written for.
- **A replaced master resume must reach the DOCUMENT, not just the caches** (23.6). There are two module-level copies of the master — `useMasterResume`'s `cache` and `tailorStore`'s `resume` — and only the first had a way in from outside, because `TailorPage`'s loader early-returns the moment the second is set. So uploading a new CV on the Jobs page (Replace), restoring a version or saving from the skills editor left `/app` painting, TAILORING and downloading the file that had just been replaced, until a full page reload — reproduced in the browser with a no-reload sentinel, not reasoned about. `tailorStore.adoptMaster` is the one way in, and it is called from **inside `useMasterResume`'s `setMaster`**, not at the three call sites: every caller of `setMaster` is by definition a replacement of the stored master, so a fourth surface gets it for free instead of shipping the same bug again. `TailorPage.onParsed` routes through it too, so there is ONE definition of "a new master arrived" — the hand-written reset it replaced never cleared `fit` / `checkedFor` / `scoredAt`. It clears everything describing the resume being replaced (a fit reading, a tailor diff, a fabrication warning, the tracker row), clears the local draft — `draftOver` spreads the draft OVER the master, so an offered restore would undo the replacement the user just made — and bumps `seq`, cancelling an in-flight tailor whose base is gone. **The target job SURVIVES** (`jdText`, `jd`, `jobUrl`, `jobTitle`, `company`): which posting you are aiming at has nothing to do with which file your resume is in, and pressing Tailor straight afterwards on the NEW resume is the whole point. This makes `hooks/useMasterResume` ↔ `state/tailorStore` a cycle, on exactly the `api/client` terms already documented there — runtime-only calls, hoisted declarations. check-mirrors 12 pins all of it.
- **The Replace control lives on the document too** (23.6). `/app` offered the dropzone in its empty state and nowhere else, so the one page that IS the resume was the one page that could not change it — which is why the bug above was reached through the Jobs page at all. It rides `DocumentPanel`'s shared `tools` list (defined once, mounted twice — the phone row and the desktop rail, so it cannot exist in one viewport only) and is gated on `editable`, the same master ⇒ change it / tailored ⇒ review it rule as every other write on this surface. Its panel is an inline `Card` with `animate-fade-up` — never a height tween, for the reason check 11 exists.
- **On the sheet, motion may only be CAUSED by a value the backend returned or an edit the user made.** Nothing on the paper moves on hover, on scroll, or on a timer. The document is the artefact the user is about to send, and motion on it reads as precision instrumentation only while it is tied to something real — a block accepting an edit, a coverage recompute, a measured page count. Tilt, spotlight, border-glow and weighted-card physics all exist elsewhere in this app and are all wrong here. A corollary with teeth: **never animate progress that is not being measured.** `POST /tailor` is a plain synchronous handler, so the text has fully arrived before the first character could be typed — a typewriter reveal would manufacture suspense over data already in memory. `ScanPanel` is the honest counter-example and the reason the rule is expressible: it streams real per-board rows off a real SSE stream.
- **A reveal animation must END on its resting state, not on nothing.** `styles.css` collapses every animation to `0.001ms` with one iteration under `prefers-reduced-motion`, which parks an element at its `to` state — so a highlight that faded out would leave a reduced-motion user with *no* indication at all. `block-settle` ends settled; `.paper-aurora` documents the same trap from the other direction.
- **A CSS animation restarts only when its NAME changes.** Spotlighting the same block twice running produces an identical class string, so the bloom silently would not replay. `block-settle` / `block-settle-alt` are byte-identical keyframes alternated by a nonce — and the nonce is also what restarts the 2200 ms window, since React bails on an identical state value and `setSpot(samePath)` was a no-op.
- **Never animate `height: "auto"` on a click-to-open element.** It wedges at `height: 0px` with the content present underneath — reproduced on a clean load, not reduced-motion, not HMR. `Disclosure` and `BlockEditSheet` both animate transform and opacity only.
- **`.sheet` is the document's palette; `.paper` is the marketing one.** Same mechanism (re-declare tokens on a subtree), different palettes and different reasons — `.paper` would paint every section heading the marketing violet, a colour no template draws.
- **Chrome follows the UI locale; the paper computes its OWN direction, and `dir="auto"` is never used on it.** `ResumeView` derives it from `resumeLanguage(resume)` — the same function both renderers use — and applies it to the sheet root AND to every editable node. Two distinct failures ride on this. Per-node: `auto` resolves from the first strong character, so a Hebrew bullet beginning "React…" flips LTR under the caret. Per-document: the root carried `dir="auto"` until 23.1, and the first strong character in tree order is `contact.name`, which `lib/lang.ts` deliberately **excludes** (mirroring `app/core/lang.py`) — so a Hebrew CV headed with a Latin-spelled name rendered **LTR on screen and RTL in the downloaded file**. Reproduced at the DOM level before it was changed. **Since PLAN 31.6/1 `resumeLanguage` is a share of words**, not any Hebrew letter: one Hebrew word typed into an English CV no longer turns the paper right to left (`data-and-privacy.md` has the rule and its measurement; check-mirrors 76 runs this file over the backend's cases).
- **The paper's section headings are printed in the PAPER's language, not the interface's** (fixed 2026-09-23, PLAN 31.1/3). `sectionLabel` read the UI's `t`, while both renderers print `labels_for(resume_language(resume))`, so under the Hebrew UI an English CV showed "תקציר מקצועי" on screen and the PDF and Word file said "PROFESSIONAL SUMMARY": the preview disagreed with the download in the primary market's everyday case, a Hebrew interface and an English CV for a tech job. `paperLang` follows `paperDir` (rtl → "he"), the headings come from `i18n.getFixedT(paperLang, "tailor")`, and an effect loads the other language's catalogs when the paper needs them, because only the interface's language is loaded at start (i18next falls back to English until the bundle arrives, then the sheet re-renders). **Only the headings move.** The placeholders, "Add skill", "+ Add a line" and the notes under the paper stay in the interface language: they speak to the user and never reach the file. Measured at 390 px: Hebrew UI over an English CV prints the English headings, English UI over a Hebrew CV the Hebrew ones, each identical to the rendered PDF's. check-mirrors 47 pins the fixed `t`, its derivation from `paperDir`, and the loader.
- **Every box a person types or pastes into takes its own text's direction, `dir="auto"`; the paper's boxes never do** (the phone polish pass, 2026-09-28). The job-posting box (`JDPaste`, in the tailor dialog, Interview, Outreach and the company brief) had no `dir`, so an English posting under the Hebrew UI was drawn right to left with its full stops at the wrong end; so were the Jobs page's Paste / URL box, the feedback box, the search's keyword and location lines and the follow-up writer's lines. All are `dir="auto"` now. The paper keeps its rule below: `ResumeView`'s boxes inherit the direction the sheet computes and `BlockEditSheet`'s carry `dir={paperDir}`, never auto. check-mirrors 111 holds both halves (`interview.md` has the measurement).
- **A cover letter box takes the LETTER's direction, `dir="auto"`, on `/app`, on `/kits/:id` and in the tracker's card modal** (fixed 2026-09-22). The letter is written in the resume's language, and the box inherited the UI's, so an English letter under the Hebrew UI rendered right to left with its punctuation at the wrong end of every line (",Dear Hiring Manager"), seen in a 390 px Playwright screenshot. `auto` is right here and wrong on the paper: a letter is one language from its first word, while a resume mixes a Latin name, Hebrew prose and Latin skills, which is why the sheet computes its direction instead.

### Phase 23.7 — the document is the template, and the tailored draft is editable

- **The document on `/app` is the THIRD renderer of `TemplateSpec`'s presentation vocabulary**, after `pdf_renderer` and `docx_renderer`, and it reads the same table they do — `lib/templateSpecs.ts`, pinned against `templates.py` by check-mirrors 23. Until 23.7 `ResumeView`'s Props had no `template` at all: `DocumentPanel` held the choice and passed it to `usePdfPreview`, `useXray`, both downloads and `XrayResult`, but not to the page the user edits on. So picking Executive gave a serif, cream, centred-name, split-entry PDF while the document on screen stayed sans, white, left-aligned, chipped and ruled — every other surface honoured the choice and the one the user works on did not. `tsc` was quiet because the prop is optional.
- **The mirror's defaults are PYTHON's defaults, and that is load-bearing.** `entry` defaults to `"split"` and `list_cols` to 1 in the dataclass while ten and eleven templates override them, so a mirror with defaults of its own is wrong on precisely the fields nobody wrote down. Two deliberate differences, both mechanical: colours carry a leading `#` (the comparator normalises), and `serif` is DERIVED from `pdf_family` — no face `templates.py` names can be web-loaded (`fonts.css` ships Inter + Heebo; Lato and Spectral are PDF-EMBEDDED), so the screen reproduces the serif/sans CATEGORY and the exact face stays the file's. A family in neither set THROWS rather than being sorted into sans.
- **The screen abstains IN WRITING from exactly four things, and each sentence appears only where it is TRUE of that template**: the exact typeface, the PDF's contact marks (the 21.8 ornament carve-out, plus one specific to this surface — an icon element inside a `contentEditable` contact block would be typed over), `layout="sidebar"`, and `footer_name` (the screen is one continuous sheet with no page boundaries to foot, and the Word file omits it too — see **The default template** in `rendering.md`). **No sidebar is drawn**: which sections land in the rail is a reportlab MEASUREMENT with a demote pass and an early-career carve-out, so a DOM guess would show sections the real file moved out — a new lie in the same class as the one this work fixes. Six of the twelve draw no contact marks, so that sentence is gated too: a note admitting to a difference that is not there is the same defect pointing the other way.
- **Per-template geometry is an inline `style` or a custom property, NEVER a computed class.** Tailwind generates utilities by SCANNING THE SOURCE, so an arbitrary-value class assembled at runtime resolves to nothing — it fails silently, in the browser, with a green build. The palette is an inline token block on `ResumeView`'s OWN root, never an edit to `.sheet`: `.sheet` is one palette for all eleven and also carries `color-scheme`, the scrollbar thumb and `--shadow-doc`, none of which has a spec twin. `surface="panel"` (the tracker's detail modal) passes no template and gets none of it.
- **A `header="band"` wrapper carries a SECOND token block, and `--accent` is the one that is easy to miss.** `blk()`'s hover tint and focus outline are the only thing on the paper that says a block is editable, and on modern's and panel's dark navy the sheet's own navy accent is invisible. `--ink-faint` is mixed from `band_meta` over `band_fill`: a token is three channels with no alpha, and `[data-ph]:empty::before` reads it — an absent phone number is discoverable ONLY through that placeholder.
- **The bullet glyph may not be an element.** That `<li>` IS the `contentEditable` node for `@exp.i.b.j`, so a glyph `<span>` would be typed over by the first edit. It is `list-style-type`, and **a string marker needs a trailing space in the string** — it is drawn exactly as written, with none of the gap `disc` gets for free, so `executive` rendered "—Rebuilt the settlement…".
- **Editing a TAILORED document is an override layer keyed by SOURCE ANCHOR, never by block path.** Block paths are not stable: a rejected removal splices the entry back and shifts every later index, so `@exp.1` is one job with nothing rejected and a different job once a removal is declined — proven by bundling and executing the shipped `resumeDiff.ts`. A path-keyed override therefore writes the user's typed sentence onto a DIFFERENT bullet. Edit ids are stable and `resumeDiff` says so, so the merge emits a parallel `sources` map and the overrides are keyed by that.
- **`setBlockOverride` sets ONLY `tailorOverrides`.** Never `resume`, never `editUndo`, and never `writeDraft` — the local draft mirrors the MASTER and `draftOver` spreads it over the master, so an application-only edit reaching it would have `DraftRestoreBar` offer to restore a tailored CV as the user's real one. `applyBlockEdit` must never be reached from the tailored path: it nulls `result`, `tailoredFrom` and `rejectedEdits`, so one keystroke through it destroys the whole review.
- **An override OUTRANKS the accept/decline decision for its block, and toggling that decision is the only thing that discards it — explicitly.** If a later Decline silently replaced the user's typing, the app deleted text the user wrote; if the override silently won while Accept/Decline stayed live, the control would do nothing. So the row offers two labelled buttons instead, each of which clears the override AND sets the decision in one tap. An override whose anchor resolves to no path is KEPT, not deleted, and re-applies if the anchor comes back.
- **Only a WHOLE-ENTRY edit owns its subtree, and `editAnchors[id] === id` is the discriminator.** An entry-level SCALAR edit (`exp.0.title`) is anchored to the ENTRY, so an ungated prefix walk made the row about a job TITLE own every hand-edit on that job's bullets — the title change became undecidable behind a "Yours" badge, and both of that row's buttons cleared the bullet override, so one tap silently deleted a sentence typed on a different line. Only `editSrc(id, id)` at the add/remove sites registers an edit under its own id, so that identity IS "this edit is the whole entry".
- **A fabrication flag is resolved against the DOCUMENT, never against the decision.** `rejected.has(id)` was sound only while rejecting was the only way to change a line: the guard flags a value BECAUSE it is not in the original, so putting the original back removed it. A rejection and an override can now stand on the same block and overrides apply LAST, so the override won the paper while the rejection won the flag row — the panel went mint and said "All flagged claims resolved" while the invented number shipped. The containment search covers the block's SUBTREE: an added ENTRY anchors to its META path, whose fields are title/employer/dates, while the edit's text folds the entry's BULLETS in.
- **The guard's verdict describes `result.tailored_resume`, not the document on screen.** Coverage and the page count move on a hand-edit (both are live and deterministic); `fit_score` and `fabrication_flags` do not. So once any override stands, the score tile drops its mint stamp and names the exception, and the tracker row sends `fabrication_flag_count` as UNKNOWN rather than a number — a row that predates a reading means unknown, never zero.
- **Adds stay master-only on a tailored draft.** A claim typed in afterwards carries no fabrication-guard verdict while `ScoreCard` keeps rendering `result.fabrication_flags` beside it.
- **There must always be a way OUT of review mode.** `editable = !result && !!resume` gates editing AND the Replace tool, and nothing set `result` back to null — so tailoring once locked the page into read-only for the rest of the session short of a full reload. `discardTailorResult` is that exit, and it is why "just hide the Tailor button while a result is up" is the wrong fix: it would remove the last control on the surface. Both exits that destroy hand-edits arm-then-confirm and state the cost AT REST.
- **`startTailor`'s reset is `adoptMaster`'s minus the six master-identity keys**, and check-mirrors 13 DERIVES that list from `adoptMaster` so a field added there forces a decision here. It used to leave `savedAppId` set, so after a re-tailor `save()` short-circuited and toasted "Already in your tracker" while the row still held the PREVIOUS tailored resume. With a result up the overlay opens EMPTY: its cached panel measures the MASTER, and painting that beside `ScoreCard`'s tailored reading is two unlabelled recruiter-fit rings for two different documents. **Amended by PLAN 31.3/4:** `savedAppId` is now KEPT for a re-tailor of the same posting text (`savedFor`), whose new draft is written over the job's row, and `save()` no longer exists to short-circuit; any other posting still starts a row of its own.

### PLAN 31.6 — the master saves itself

- **Every edit and every undo saves itself a pause later** (2026-09-26, PLAN 31.6/2). The Save button, its unsaved count (the "1" badge) and `commitResumeEdits` are gone. `applyBlockEdit` and `undoBlockEdit`, the only writers of the master during editing, call `scheduleMasterSave`: `MASTER_PAUSE_MS` (1.2 s, the job draft's pause) after the last edit, `runMasterSave` sends `PUT /profile/resume` with the slot the document came from (`masterSlot`), the version it was made from (`masterStamp`) and `autosave: true`, one save at a time, each reading the document and the version when it RUNS, so a burst behind a slow save goes as one request made from the version that save handed back. An unchanged document sends nothing. No ledger is sent (the backend rebuilds it), and `resetMasterCache()` follows every save for the reason the two-caches bullet above gives. Undo is KEPT across saves: undoing is an edit, and it saves like one.
- **The version is the server's answer, never the clock's.** The loader records `m.updated_at` and `m.language`; a page begun from scratch records `""` (nothing saved yet); an upload records null until its save answers and then that save's stamp. `onParsed` handed `adoptMaster` `new Date().toISOString()` as the version, which the first autosave after an upload would have been refused over (`resume_stale`) as a save made from a version the server never held.
- **The server's copy is adopted only while the document is still the one sent.** The model validator can add to the flat skills union, so a baseline the document can never match would save it forever; a line typed while the save was on the wire keeps the screen, and its own save follows. `adoptMaster` moves the saver's epoch (`newMasterEpoch`) BEFORE it resets the store: an edit waiting to save, or an answer on the wire, about a resume the person just replaced (Replace, a restore, the skills editor) must not land after the replacement, which is already on the server. check-mirrors 13's master-identity list grew the four autosave keys (`masterStamp`, `masterSlot`, `masterSave`, `masterConflict`): a tailor that reset them would make the next edit's save name no version, or forget a refusal still unanswered.
- **What the toolbar says, and what it may not.** Nothing at rest (`save === "idle" && !canUndo`, check-mirrors 55): the row stays 51 px. After an edit, a status and Undo: "Saving…" while a change waits or travels, "Saved" (a check) once the server has it, "Not saved" otherwise; below `sm` the icon carries it and the words are its name. It never says Saved about a save that did not answer (check-mirrors 77). Each refusal is a panel that breaks onto its own line of the toolbar and stays until it is answered, because "your work is not saved" must not disappear while it is still not saved: a failure offers Try again; **stale** (another tab or device saved a newer version) offers Load that version or Keep mine, and no further save is sent until one is chosen, since each would be refused the same way; **slot** (the resume now reads as the other language, `data-and-privacy.md`) says nothing is saved until the person chooses, offers Undo and "Save as my Hebrew resume", and keeps saving on each edit, because undoing the change that crossed is itself an answer. Keep mine and Save as my other resume are ASKED saves (`autosave: false`), so the version they replace is always kept as a restore point. Tailor is the toolbar's one primary again on the master: nothing competes with it.
- **The local draft stays, with less to do.** `writeDraft` still mirrors every edit and a successful save clears it, so `DraftRestoreBar` now appears only for an edit whose save never landed: a tab closed inside the pause, no network, a refusal left unanswered. - `masterResumeLabel` moved to `lib/masterLabel.ts` (re-exported from `hooks/useSaveMasterResume`): the store names a resume saved from a blank page, and a store importing the hook module would drag the toast layer into every store probe.
