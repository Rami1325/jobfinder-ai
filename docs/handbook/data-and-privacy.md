### `app/db/`, and what a privacy wipe must reach

This was the `app/db/` entry of `CLAUDE.md`'s backend package layout.

- `app/db/` — SQLAlchemy + SQLite (`applications` tracker + `saved_resumes` master resume + `saved_resume_versions` undo buffer + `job_search_hits` search history + `usage_log` caps/tokens). `init_db()` is called via the FastAPI lifespan hook and includes a lightweight SQLite ADD-COLUMN shim that adds any ORM columns missing from pre-existing tables. Job-search results are auto-persisted as history via `app/db/history.py` (deduped by URL, capped at the newest 100) and exposed at `GET`/`DELETE /jobs/history`. **Anything holding user content must be wiped by `_wipe_user_rows`** — the shared helper behind BOTH `DELETE /profile/data` (wipe, code keeps working) and `DELETE /profile/account` (wipe + deactivate, code stops working). Add new tables there, or a privacy wipe silently leaves PII behind. **Two carve-outs run the other way, and both exist so that neither privacy door can reset a limit** (Phase 30 / B2). The three monthly-uses tables — `usage_months`, `usage_events`, `usage_passes` — and since PLAN 31.5 a fourth, `usage_firsts` (the pool's free first search, one row per pool and feature, which `quota.prune` never deletes either), are NEVER wiped by either door: they hold no content (a keyed hash, a user id, a month, feature names and counts), and the pool is keyed by a one-way keyed hash of the CANONICAL sign-in address, so deleting the data, closing the account and signing up again with the same address are one pool — Phase 29's A7 rule ("closing an account cannot reset a limit") applied to the free limit. An account with no sign-in address (the admin, an invite code) is its own pool, `u:<id>`, which the surviving user row preserves just the same (`quota.key_for`); `quota.prune` is what removes these rows, once they are older than the previous month. And `DELETE /profile/data` keeps TODAY's `usage_log` rows, because they are the daily caps' live counters, while `DELETE /profile/account` deletes them in the same transaction, since a deactivated id can never spend them. **Both halves are AST-pinned by smoke 32.10** — neither door may name `UsageMonth`, `UsageEvent` or `UsagePass` — so adding these tables to the wipe fails the suite instead of quietly making "Delete all my data" a free reset. Both facts are stated to the user on the privacy page (`auth.json` `privacy.store.usage`, `privacy.remove.close`), so changing either is a copy change in both locales too. It also clears the two user-content COLUMNS — `users.search_prefs_json` and `users.writing_prefs_json` — which rows-only wipes missed: they are per-column, not per-row, so they add no field to `DeleteMyDataResult` and the response shape is unchanged. Since Phase 29 it clears a third column, `users.resume_prefs_json` (the Arabic preference implies ethnicity), and wipes `mail_events` and `mail_connections` — AFTER handing the Google grant back (`inbox_sync.revoke_stored_grant`), reporting `google_revoked` honestly rather than claiming a revoke that did not happen. `DELETE /profile/account` additionally blanks `users.name` and `users.email` and runs `accounts.purge_on_close` (logins, tokens and sessions deleted; auth events kept with `user_id` NULLed — see Phase 29). The account tables are `user_logins`, `auth_sessions`, `auth_tokens`, `auth_events`; the inbox tables are `mail_connections` and `mail_events` (no body column — a full email is never stored). `DELETE /profile/account` refuses for an admin, because `admin_update_user` already refuses to deactivate one (it is the only way back into a deployed instance) and with the access gate OFF every local request IS the admin.

### The master resume's rows

- **"Most recently updated" must be a TOTAL order, and the clock does not give one.** `_master_rows` sorts on `updated_at` alone and the column's `onupdate` reads the system clock — which ticks about every **15.6 ms on Windows**, so three consecutive `datetime.now()` calls return the identical value. Two saves inside one tick tied, and SQLite was then free to return them in either order: `GET /profile/resume` with no `lang` answered with whichever it liked, and the paired he/en master the user had just written was not necessarily the one they got back. It surfaced as a smoke check that was red on one run and green on the next — the shape of thing this repo's own note says never to re-run away. **A tiebreak in the `ORDER BY` cannot fix it**: `id` is creation order and the row being written is usually the OLDER one (the save upserts by language), so `id DESC` breaks the tie deterministically *wrong*. `save_master_resume` stamps `updated_at` one microsecond past the newest row for that user instead, and the pin FORCES the tie rather than waiting for one.
- **Overwriting the master resume snapshots it first** (`db/resume_versions.snapshot`, called from `PUT /profile/resume` and from restore). The dedupe compares the incoming content against the **current row**, not against the newest stored version — the latter looks right and lets an unchanged save through whenever the previous save did change something.

### The Chrome extension on the privacy page, and the Web Store (2026-09-22)

- **`/privacy` is the Chrome Web Store listing's privacy policy, so its "If you use the Chrome extension" section (`privacy.extension.*` in both `auth.json` files) is held to `extension/popup.js` and `options.js`**, sentence by sentence: what the popup reads (the clicked tab's job posting, only after a click), what it sends and to whom (the JobFinder server in its options, with the extension key; open questions go on to OpenAI through JobFinder's AI), what it stores (its three options, in `chrome.storage.sync`), what it writes into a page (the approved kit's details and drafted answers, never overwriting typed text, never submitting), no analytics, and how to remove it. It ends with the Limited Use statement the Store requires on a site belonging to the extension. A change to what the extension reads, sends or stores is a change to that section in both locales, to `docs/chrome-web-store.md`'s data-usage table, and to the popup's own wording.
- **The Store requires every data collection to be disclosed inside the extension's own UI, whether or not it is related to the single purpose** (Disclosure Requirements policy, in force since 2026-08-01; the listing and the privacy page do not count). That is why 0.4.1's Assisted apply hint (`applyHint`) says the form's open questions go to JobFinder's AI (OpenAI). The clip form discloses itself: every field is shown, editable, before Save.
- **The Store zip is built by `extension/pack_store.py` into `extension-dist/`**, which is git-ignored AND listed in `.vercelignore` (which supersedes `.gitignore` for CLI uploads). It is a sibling of `extension/`, never a path inside it, because check-mirrors 35 needs `extension/` in the upload whole or not at all.

### What a tracker row records

- **One posting, one tracker row** (2026-09-23, PLAN 31.1/5). A saved job reaches `/app` with its URL but not its row id (the extension's `?tailor_app=`, "Use a job you saved", a saved Jobs card), and `startTailor` deliberately clears `savedAppId`, so "Save to tracker" and "Yes, applied" POSTed a second row for a job already tracked. `POST /applications` now UPDATES this user's newest row with the same trimmed `job_url` (`routes._tracked_job`): a tailored resume replaces the stored one together with its three what-was-sent signals (a `None` stays unknown, never a stale value), a letter / JD / title / company only fills a blank, and the status only moves forward, `saved` → `applied` (with `applied_at`), never back, since everything past Applied belongs to the user's own moves and the inbox. A post with no URL is a new row, and one user's URL never touches another's (smoke 31.1/5, both halves). **Still open:** a row with no URL (a pasted posting saved earlier and re-tailored through the picker) still gets a second row, until a tailor started from the job's own page carries its row id (31.4). ~~Kit approval writes its row directly in `kits.py`, not through this route.~~ **Closed 2026-09-23 (PLAN 31.4/1):** `approve_kit` finds the row through the same lookup, `db/applications.tracked_job` (moved out of `routes.py` so both writers share it), and merges by the same rules; see the next bullet.
- **A tailored draft is saved WITH its job, as it is reviewed** (2026-09-23, PLAN 31.3/4, owner decision 2). A finished tailor makes the job's row in Saved with the draft on it, through `POST /applications` (so a URL already tracked is updated, as above), and every later accept, decline, typed line, design and letter updates that row a short pause later through `PUT /applications/{id}/draft` (`ApplicationDraft`, `extra="forbid"`). The PUT writes the resume and its three what-was-sent signals TOGETHER, `None` included, so a draft the user typed on carries an unknown fabrication count, never the AI version's number; the letter is the one field it leaves alone when absent, so a draft saved before any letter cannot erase one. It never touches the status. The page decides WHICH row: a re-tailor of the same posting TEXT keeps the row (the tailor store's `savedFor`), any other posting, target or master gets its own, and a change still waiting is sent to the row it was typed for first (check-mirrors 61, executed). That closes the no-URL half of the open item above within a tab; a pasted posting tailored again after a reload still makes a second row, since `savedFor` lives in module memory, until 31.4's job page carries the row id. A 404 (the row was deleted in the tracker meanwhile) makes a new row rather than losing the draft. smoke 31.3/4 pins the route: typed resume, template and an unknown count written together, the letter kept, another account's row a 404, an unknown field a 422.
- **A row carries what the job page shows, so viewing it never runs a model** (2026-09-23, PLAN 31.4/1). Three columns, each `""` for unknown through the ADD-COLUMN shim: `location` and `posted_at` (the board's own string, the `job_search_hits.posted_at` shape, `String(32)`), which fill only a blank on a repeat save like a title does, and `jd_json`, the analysed posting a fit check, tailor or kit already ran, which REPLACES the stored one when sent, because it is the analysis the draft beside it was tailored against and the cover letter's pass is keyed by it. `POST`, `PATCH` (the job page's letter and analysis) and the draft `PUT` each write it when sent and leave it alone when absent; a JD over `max_jd_json_kb` is refused whole as a 413 of kind `jd` BEFORE anything is written (never truncated), and a place over 255 characters or a date over 32 is a 422, since Postgres refuses a longer value and takes the whole save with it. A stored analysis that no longer parses reads as none, never a 500. The detail also hands back `status_changed_at` / `status_source` (the ONE status change a row records: there is no history table, so the timeline never invents one), the what-was-sent signals, and `pending_kit`: this user's newest kit for the same URL that nobody has decided yet (queued, running or done; `db/applications.pending_kit`). **Kit approval merges by URL** into the row the user already tracks: the draft replaces the stored one with its signals (`template` unknown, since kit review has no picker), a letter replaces it when there is one, the kit's analysis replaces it, a title, company, description, place or date fills only a blank, and the status is left alone, so an approval never pulls an applied row back to Saved; a row it makes itself is stamped `status_source = "created"` with the time, as a save stamps one. smoke 31.4/1 (10 checks) pins each rule beside its false-positive twin: another account's row for the same URL is never merged into or named, and a rejected kit is never named.
- **A row keeps the REVIEW behind its draft, so the document can open it again** (2026-09-23, PLAN 31.4/4). `review_json` holds what the tailor page needs to show the draft exactly as it was left: the tailor's result, the resume it was tailored from (the diff baseline, whatever the master is now), the changes declined (`lib/resumeDiff` ids), the lines typed over it (source anchor → field → text) and the minute its recruiter-fit reading was taken. **It is written TOGETHER with `tailored_resume_json`, never apart**: `POST /applications` and the draft `PUT` write the review they are sent beside the draft, and a draft written WITHOUT one clears it, since a review of the previous draft would reopen the wrong document (an old tab across a deploy, a kit approval, which leaves the kit's own review on the kit). The result and base ride only a result's first save to a row (`leanDraft` in `tailorStore`); every later save carries the decisions alone and the server keeps the result it has (`_next_review`). A review past four times the resume cap is a 413 of kind `resume` before anything is written, never truncated. It is read back on its own route, `GET /applications/{id}/review` (plain `current_user`, classed `free` in smoke 32.13 and driven in its sweep), never on the detail, which carries only `has_review`, because every page that reads a job would otherwise carry a whole tailored result. A review that no longer parses, or lacks its result or base, is a 404. `_wipe_user_rows` deletes it with its row. smoke 31.4/4 pins each rule, the kit approval's clearing included.
- **A Comeet send reads the job's draft as it is NOW** (2026-09-23, PLAN 31.4/5). The detail names `send_kit`, the approved kit this row was approved from (`TailorKit.application_id`), while Comeet's apply API may still send the row's draft: approved and not yet sent, a Comeet posting, no flags on the kit, and the row's `fabrication_flag_count` exactly 0 (`db/applications.sendable_kit`, `draft_guard_clean`). `auto_submit.submit_kit` refuses that last case too, before the daily cap and the network. The kit's flags were read when it was approved, but the draft it approved is not the last word on the row: the job's page can tailor the job again onto the same row (31.4/4), and a line typed on the draft stores an unknown count (31.3/4), which is never clean. The job's page offers the send only from `send_kit`, where the Jobs page's Kits tab offered it on every approved Comeet kit. smoke 31.4/5 (+4) pins the kit named, a sent kit no longer named, and a typed draft neither named nor sent, each beside its twin.
- Tracker rows record what was sent (`template`, `voice_score`, `fabrication_flag_count`). All three are nullable/`""` — a row that predates the field means **unknown**, never zero, and the analytics drops it from that dimension instead of scoring it. When reading these off a stored kit, parse the RAW result JSON: validating through `TailorResult` silently substitutes schema defaults.
