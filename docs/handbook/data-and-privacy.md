### `app/db/`, and what a privacy wipe must reach

This was the `app/db/` entry of `CLAUDE.md`'s backend package layout.

- `app/db/` — SQLAlchemy + SQLite (`applications` tracker + `saved_resumes` master resume + `saved_resume_versions` undo buffer + `job_search_hits` search history + `usage_log` caps/tokens). `init_db()` is called via the FastAPI lifespan hook and includes a lightweight SQLite ADD-COLUMN shim that adds any ORM columns missing from pre-existing tables. Job-search results are auto-persisted as history via `app/db/history.py` (deduped by URL, capped at the newest 100) and exposed at `GET`/`DELETE /jobs/history`. **Anything holding user content must be wiped by `_wipe_user_rows`** — the shared helper behind BOTH `DELETE /profile/data` (wipe, code keeps working) and `DELETE /profile/account` (wipe + deactivate, code stops working). Add new tables there, or a privacy wipe silently leaves PII behind. **Two carve-outs run the other way, and both exist so that neither privacy door can reset a limit** (Phase 30 / B2). The three monthly-uses tables — `usage_months`, `usage_events`, `usage_passes` — and since PLAN 31.5 a fourth, `usage_firsts` (the pool's free first search, one row per pool and feature, which `quota.prune` never deletes either), are NEVER wiped by either door: they hold no content (a keyed hash, a user id, a month, feature names and counts), and the pool is keyed by a one-way keyed hash of the CANONICAL sign-in address, so deleting the data, closing the account and signing up again with the same address are one pool — Phase 29's A7 rule ("closing an account cannot reset a limit") applied to the free limit. An account with no sign-in address (the admin, an invite code) is its own pool, `u:<id>`, which the surviving user row preserves just the same (`quota.key_for`); `quota.prune` is what removes these rows, once they are older than the previous month. And `DELETE /profile/data` keeps TODAY's `usage_log` rows, because they are the daily caps' live counters, while `DELETE /profile/account` deletes them in the same transaction, since a deactivated id can never spend them. **Both halves are AST-pinned by smoke 32.10** — neither door may name `UsageMonth`, `UsageEvent` or `UsagePass` — so adding these tables to the wipe fails the suite instead of quietly making "Delete all my data" a free reset. Both facts are stated to the user on the privacy page (`auth.json` `privacy.store.usage`, `privacy.remove.close`), so changing either is a copy change in both locales too. It also clears the user-content COLUMNS — `users.search_prefs_json`, `users.writing_prefs_json`, and since PLAN 31.5/4 `users.hidden_jobs_json` (the "Not for me" set: companies and the user's choices about them) — which rows-only wipes missed: they are per-column, not per-row, so they add no field to `DeleteMyDataResult` and the response shape is unchanged. Since Phase 29 it clears a third column, `users.resume_prefs_json` (the Arabic preference implies ethnicity), and wipes `mail_events` and `mail_connections` — AFTER handing the Google grant back (`inbox_sync.revoke_stored_grant`), reporting `google_revoked` honestly rather than claiming a revoke that did not happen. `DELETE /profile/account` additionally blanks `users.name` and `users.email` and runs `accounts.purge_on_close` (logins, tokens and sessions deleted; auth events kept with `user_id` NULLed — see Phase 29). The account tables are `user_logins`, `auth_sessions`, `auth_tokens`, `auth_events`; the inbox tables are `mail_connections` and `mail_events` (no body column — a full email is never stored). `DELETE /profile/account` refuses for an admin, because `admin_update_user` already refuses to deactivate one (it is the only way back into a deployed instance) and with the access gate OFF every local request IS the admin.

### The first steps (PLAN 31.8, 2026-09-26)

- **`funnel_steps` records the first time each person reached a step, and nothing else**: a user id, a step name and the time (`db/funnel.py`, `STEPS`: uploaded, searched, tailored, downloaded, application, returned; "signed up" is `users.created_at`). One row per (user, step), ever: `INSERT … ON CONFLICT DO NOTHING`, best-effort (bookkeeping never fails a request), on its own commit after the route's own work. A NEW table, so `create_all` makes it with its unique constraint. Each step is written where it happens and after it succeeded: the master's first save, a search and a tailor on both doors (the streams on the worker, on a session of their own, `note_apart`), an application saved in any status, and a DOWNLOAD, `POST /render?download=1`, which the download button alone sends: the previews call the same route, and a preview counted as a download would say people downloaded who only looked. "Came back within 7 days" is stamped in the gate's own `touch_last_seen`, on its throttled write, because only the gate sees every request (`accounts-and-auth.md`).
- **Both privacy doors delete a person's steps** (`_wipe_user_rows`, reported as `steps` in `DeleteMyDataResult`): they describe what that person did. The privacy page says what is recorded and that deleting the data deletes it (`privacy.store.steps`, both locales).
- **The admin reads it** in Settings (`components/FunnelCard`, mounted for `is_admin` alone) through `GET /admin/funnel` (`admin_user`, read-only, classed `free` in 32.13 and driven in its sweep): each person's name, signup date and the date each step was first reached, a step not reached drawn faint, never a zero.
- Smoke 31.8 (+4): each step once and never again, a preview recording nothing; the two streams recording theirs; the admin's alone and the wipe's count; "returned" on day 3 and not on the first day or the ninth. Each probed red with its defect planted (a preview counted, a stream's note missing, the wipe skipping the table, a return never recorded). check-mirrors 80 pins the client half.

### The devices an alert is pushed to (PLAN 32, 2026-09-27)

- **`push_subscriptions` holds one row per device that turned the morning alert on**: the user id, the push service's
  endpoint for that browser, the two keys the message is encrypted to (`p256dh`, `auth`), the device's language, when
  it was turned on, the last push that reached it (NULL = none yet, never "failed") and a consecutive-failure count.
  A NEW table, so `create_all` makes it with its unique constraint on `endpoint_key` (a sha256 of the endpoint:
  unique across users, because a browser holds one subscription and the account that turned it on last owns it).
- **Both privacy doors delete a user's rows** (`_wipe_user_rows`, reported as `push_devices` in
  `DeleteMyDataResult`): a wiped account's phone must stop receiving its alerts, not only forget them. The privacy
  page says a device's notification address is kept and that the browser's push service delivers the notifications,
  encrypted (`privacy.store.push`, both locales). Rows also go when the user turns the device off, when the push
  service answers 404/410, and after five failures in a row (`notifications.md`). smoke 34c pins both doors.
- **`whatsapp_contacts` holds at most one row per user: the WhatsApp number** (E.164, personal data), its template
  language, when the explicit opt-in was ticked, when the number was proven by the code WhatsApp delivered, the code's
  HMAC with its expiry and wrong tries (never the code), the last delivery and the last failure reason. A NEW table
  with a unique constraint on `user_id`. Both privacy doors delete it (reported as `whatsapp`), "Stop and remove"
  deletes it, and the privacy page says the number goes to WhatsApp (Meta) with each alert (`privacy.store.whatsapp`).
  `users.whatsapp_enabled` is the admin's grant, not content, and neither door clears it. smoke 35b pins both doors.

### The master resume's rows

- **"Most recently updated" must be a TOTAL order, and the clock does not give one.** `_master_rows` sorts on `updated_at` alone and the column's `onupdate` reads the system clock — which ticks about every **15.6 ms on Windows**, so three consecutive `datetime.now()` calls return the identical value. Two saves inside one tick tied, and SQLite was then free to return them in either order: `GET /profile/resume` with no `lang` answered with whichever it liked, and the paired he/en master the user had just written was not necessarily the one they got back. It surfaced as a smoke check that was red on one run and green on the next — the shape of thing this repo's own note says never to re-run away. **A tiebreak in the `ORDER BY` cannot fix it**: `id` is creation order and the row being written is usually the OLDER one (the save upserts by language), so `id DESC` breaks the tie deterministically *wrong*. `save_master_resume` stamps `updated_at` one microsecond past the newest row for that user instead, and the pin FORCES the tie rather than waiting for one.
- **Overwriting the master resume snapshots it first** (`db/resume_versions.snapshot`, called from `PUT /profile/resume` and from restore). The dedupe compares the incoming content against the **current row**, not against the newest stored version — the latter looks right and lets an unchanged save through whenever the previous save did change something.
- **Which slot a save lands in is the resume's language, and since PLAN 31.6/1 that is a share of its words** (2026-09-26). `resume_language` said "he" for ANY Hebrew letter in the prose, so one Hebrew word in an English master (an organisation, a pasted degree, one typed word) routed the save over the person's Hebrew resume and left the English one as it was, and turned the paper right to left. It now says "he" when at least one prose word in five is Hebrew (`HEBREW_SHARE_DEN`, integers so `lib/lang.ts` computes the identical answer; a word is one script's run, so "ב-Python" is one of each), and skills vote only while there is no prose, because they are English terms in most Hebrew resumes. The threshold was chosen on `tests/fixtures/lang_cases.json` BEFORE it was written: Hebrew resumes carrying English titles, skills and tech terms, the common Israeli shape, sit at 46-100% Hebrew words, and English resumes with a Hebrew trace at 0-7%. **A plain majority was the plan's wording, and the data rejected it**: the QA-automation case (English headline and titles, Hebrew bullets) is 46% Hebrew and read as English. The cases are constructed, not production rows, so the rule records its margin rather than claiming a rate. The smoke test runs them through `core/lang.py` and check-mirrors 76 through `lib/lang.ts`, and both show the old rule misreading them. This one function also sets every prompt's language note and both renderers' direction, which is the point: the save, the file and the paper agree. `detect_language` (a posting's language, any Hebrew letter) is unchanged, and so is the CV scan's reading of a raw file (`free_scan`), which still uses it.
- **A read relabels a row without moving its version, and never into a slot another row holds** (PLAN 31.6/1). `_master_rows` heals `row.language` from the content on every read (for the rows saved before the column existed). It wrote through the ORM, whose `onupdate` stamps `updated_at`, and `updated_at` is now the version an autosave's conflict check compares, so a read that relabelled would refuse every open tab's next save. It writes through a Core UPDATE that sets `updated_at` to itself. And because the detector changed under rows the old one labelled, a row whose content now reads as a language ANOTHER row holds keeps its label: an English resume with one Hebrew word, stored as the "he" row beside a real "en" one, would otherwise become a second "en" row, and `GET ?lang=he` would answer null. A save into it is then asked about (`resume_slot`), never routed silently.
- **What an autosave tells the save route** (PLAN 31.6/1, the prerequisites PLAN 22's *next up* 5 listed). `MasterResumeIn` takes three optional fields, and a save without them behaves as before, so a tab older than the deploy keeps working. `slot`: the language slot the document was loaded from; a resume that now reads as the other language is a 409 `{"kind": "resume_slot", "slot", "language"}` and writes nothing, where it used to land on the other resume (the page asks, in 31.6/2). `base_updated_at`: the version the document was made from, the `updated_at` string this route or `GET /profile/resume` handed out, compared as naive UTC to the microsecond (SQLite and Neon both hand the column back naive), with `""` meaning no saved resume in this slot; a newer version on the server is a 409 `{"kind": "resume_stale", "language", "updated_at"}` carrying the version the server holds, so the page can offer to load it, and a stamp that is not one is a 422. Two tabs were last-write-wins, which an autosave turns into a quiet loss. `autosave`: coalesce the restore point (next bullet). The slot check runs before the size check, the version check after it. A restore is not checked: it is the user's explicit choice, and it hands back the new version.
- **An autosave keeps one restore point per half hour of editing** (`resume_versions.COALESCE_WINDOW`, 30 minutes, measured on nothing: a round number for "a while ago"). A snapshot per changed PUT spent the twenty slots in minutes of typing, the uploaded original first. `saved_resumes.autosaved` (shim column, default false, not user content) says whether the content now in the row came from an autosave, and an autosave over autosaved content takes no snapshot while the slot's newest one is younger than the window. Content that arrived any other way, an upload, a restore or a save the user asked for, is always kept on its way out, so the first keystroke after an upload records the upload itself, the restore point that matters most. smoke 31.6/1 (12 checks, each probed red in a copy of the backend with its defect planted): twenty-five autosaves after an upload add one restore point, the upload; past the window the next autosave keeps what it overwrites; a save the user asked for is always one, and so is its content when the next autosave overwrites it; plus the language cases, the slot, the version, and the relabel's two limits.

### The Chrome extension on the privacy page, and the Web Store (2026-09-22)

- **`/privacy` is the Chrome Web Store listing's privacy policy, so its "If you use the Chrome extension" section (`privacy.extension.*` in both `auth.json` files) is held to `extension/popup.js` and `options.js`**, sentence by sentence: what the popup reads (the clicked tab's job posting, only after a click), what it sends and to whom (the JobFinder server in its options, with the extension key; open questions go on to OpenAI through JobFinder's AI), what it stores (its three options, in `chrome.storage.sync`), what it writes into a page (the approved kit's details and drafted answers, never overwriting typed text, never submitting), no analytics, and how to remove it. It ends with the Limited Use statement the Store requires on a site belonging to the extension. A change to what the extension reads, sends or stores is a change to that section in both locales, to `docs/chrome-web-store.md`'s data-usage table, and to the popup's own wording.
- **The Store requires every data collection to be disclosed inside the extension's own UI, whether or not it is related to the single purpose** (Disclosure Requirements policy, in force since 2026-08-01; the listing and the privacy page do not count). That is why 0.4.1's Assisted apply hint (`applyHint`) says the form's open questions go to JobFinder's AI (OpenAI). The clip form discloses itself: every field is shown, editable, before Save.
- **The Store zip is built by `extension/pack_store.py` into `extension-dist/`**, which is git-ignored AND listed in `.vercelignore` (which supersedes `.gitignore` for CLI uploads). It is a sibling of `extension/`, never a path inside it, because check-mirrors 35 needs `extension/` in the upload whole or not at all.

### What a tracker row records

- **One posting, one tracker row** (2026-09-23, PLAN 31.1/5). A saved job reaches `/app` with its URL but not its row id (the extension's `?tailor_app=`, "Use a job you saved", a saved Jobs card), and `startTailor` deliberately clears `savedAppId`, so "Save to tracker" and "Yes, applied" POSTed a second row for a job already tracked. `POST /applications` now UPDATES this user's newest row with the same trimmed `job_url` (`routes._tracked_job`): a tailored resume replaces the stored one together with its three what-was-sent signals (a `None` stays unknown, never a stale value), a letter / JD / title / company only fills a blank, and the status only moves forward, `saved` → `applied` (with `applied_at`), never back, since everything past Applied belongs to the user's own moves and the inbox. A post with no URL is a new row, and one user's URL never touches another's (smoke 31.1/5, both halves). **Still open:** a row with no URL (a pasted posting saved earlier and re-tailored through the picker) still gets a second row, until a tailor started from the job's own page carries its row id (31.4). ~~Kit approval writes its row directly in `kits.py`, not through this route.~~ **Closed 2026-09-23 (PLAN 31.4/1):** `approve_kit` finds the row through the same lookup, `db/applications.tracked_job` (moved out of `routes.py` so both writers share it), and merges by the same rules; see the next bullet.
- **A tailored draft is saved WITH its job, as it is reviewed** (2026-09-23, PLAN 31.3/4, owner decision 2). A finished tailor makes the job's row in Saved with the draft on it, through `POST /applications` (so a URL already tracked is updated, as above), and every later accept, decline, typed line, design and letter updates that row a short pause later through `PUT /applications/{id}/draft` (`ApplicationDraft`, `extra="forbid"`). The PUT writes the resume and its three what-was-sent signals TOGETHER, `None` included, so a draft the user typed on carries an unknown fabrication count, never the AI version's number; the letter is the one field it leaves alone when absent, so a draft saved before any letter cannot erase one. It never touches the status. The page decides WHICH row: a re-tailor of the same posting TEXT keeps the row (the tailor store's `savedFor`), any other posting, target or master gets its own, and a change still waiting is sent to the row it was typed for first (check-mirrors 61, executed). That closes the no-URL half of the open item above within a tab; a pasted posting tailored again after a reload still makes a second row, since `savedFor` lives in module memory, until 31.4's job page carries the row id. A 404 (the row was deleted in the tracker meanwhile) makes a new row rather than losing the draft. smoke 31.3/4 pins the route: typed resume, template and an unknown count written together, the letter kept, another account's row a 404, an unknown field a 422.
- **A row carries what the job page shows, so viewing it never runs a model** (2026-09-23, PLAN 31.4/1). Three columns, each `""` for unknown through the ADD-COLUMN shim: `location` and `posted_at` (the board's own string, the `job_search_hits.posted_at` shape, `String(32)`), which fill only a blank on a repeat save like a title does, and `jd_json`, the analysed posting a fit check, tailor or kit already ran, which REPLACES the stored one when sent, because it is the analysis the draft beside it was tailored against and the cover letter's pass is keyed by it. `POST`, `PATCH` (the job page's letter and analysis) and the draft `PUT` each write it when sent and leave it alone when absent; a JD over `max_jd_json_kb` is refused whole as a 413 of kind `jd` BEFORE anything is written (never truncated), and a place over 255 characters or a date over 32 is a 422, since Postgres refuses a longer value and takes the whole save with it. A stored analysis that no longer parses reads as none, never a 500. The detail also hands back `status_changed_at` / `status_source` (the ONE status change a row records: there is no history table, so the timeline never invents one), the what-was-sent signals, and `pending_kit`: this user's newest kit for the same URL that nobody has decided yet (queued, running or done; `db/applications.pending_kit`). **Kit approval merges by URL** into the row the user already tracks: the draft replaces the stored one with its signals (`template` unknown, since kit review has no picker), a letter replaces it when there is one, the kit's analysis replaces it, a title, company, description, place or date fills only a blank, and the status is left alone, so an approval never pulls an applied row back to Saved; a row it makes itself is stamped `status_source = "created"` with the time, as a save stamps one. smoke 31.4/1 (10 checks) pins each rule beside its false-positive twin: another account's row for the same URL is never merged into or named, and a rejected kit is never named.
- **A row keeps the REVIEW behind its draft, so the document can open it again** (2026-09-23, PLAN 31.4/4). `review_json` holds what the tailor page needs to show the draft exactly as it was left: the tailor's result, the resume it was tailored from (the diff baseline, whatever the master is now), the changes declined (`lib/resumeDiff` ids), the lines typed over it (source anchor → field → text) and the minute its recruiter-fit reading was taken. **It is written TOGETHER with `tailored_resume_json`, never apart**: `POST /applications` and the draft `PUT` write the review they are sent beside the draft, and a draft written WITHOUT one clears it, since a review of the previous draft would reopen the wrong document (an old tab across a deploy, a kit approval, which leaves the kit's own review on the kit). The result and base ride only a result's first save to a row (`leanDraft` in `tailorStore`); every later save carries the decisions alone and the server keeps the result it has (`_next_review`). A review past four times the resume cap is a 413 of kind `resume` before anything is written, never truncated. It is read back on its own route, `GET /applications/{id}/review` (plain `current_user`, classed `free` in smoke 32.13 and driven in its sweep), never on the detail, which carries only `has_review`, because every page that reads a job would otherwise carry a whole tailored result. A review that no longer parses, or lacks its result or base, is a 404. `_wipe_user_rows` deletes it with its row. smoke 31.4/4 pins each rule, the kit approval's clearing included.
- **A Comeet send reads the job's draft as it is NOW** (2026-09-23, PLAN 31.4/5). The detail names `send_kit`, the approved kit this row was approved from (`TailorKit.application_id`), while Comeet's apply API may still send the row's draft: approved and not yet sent, a Comeet posting, no flags on the kit, and the row's `fabrication_flag_count` exactly 0 (`db/applications.sendable_kit`, `draft_guard_clean`). `auto_submit.submit_kit` refuses that last case too, before the daily cap and the network. The kit's flags were read when it was approved, but the draft it approved is not the last word on the row: the job's page can tailor the job again onto the same row (31.4/4), and a line typed on the draft stores an unknown count (31.3/4), which is never clean. The job's page offers the send only from `send_kit`, where the Jobs page's Kits tab offered it on every approved Comeet kit. smoke 31.4/5 (+4) pins the kit named, a sent kit no longer named, and a typed draft neither named nor sent, each beside its twin.
- Tracker rows record what was sent (`template`, `voice_score`, `fabrication_flag_count`). All three are nullable/`""` — a row that predates the field means **unknown**, never zero, and the analytics drops it from that dimension instead of scoring it. When reading these off a stored kit, parse the RAW result JSON: validating through `TailorResult` silently substitutes schema defaults.
