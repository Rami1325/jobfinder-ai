
**Frontend (React/Vite):**
```powershell
cd frontend
npm install
npm run dev   # http://localhost:5173
```
Vite proxies `/api/*` → `127.0.0.1:8000` during dev (see `vite.config.ts`). **127.0.0.1, not `localhost`** — Node resolves `localhost` to `::1` first while uvicorn binds `127.0.0.1`, which surfaces as a misleading ECONNREFUSED. The same trap applies to anything else you point at the dev servers, `vite preview` included.

**Offline mode (no API key needed):**
Set `USE_STUB_LLM=true` in `.env`. The entire pipeline (parse, score, tailor, render, tracker) works with canned LLM responses.

## Architecture

The pipeline flows strictly left to right — each step's output is the next step's input:

```
File upload → resume_parser (DOCX/PDF → raw text)
           → structurer (LLM → ResumeModel JSON + FactsLedger)
           → jd_analyzer (LLM → JDModel JSON)
           → scorer (deterministic keyword coverage + LLM fit score → Score before)
           → tailor (LLM → tailored ResumeModel + changelog)
           → fabrication_guard (diff tailored facts vs. ledger → FabricationFlags)
           → scorer again (Score after)
           → docx_renderer / pdf_renderer (bytes)
```

Beyond the core pipeline, the backend also exposes standalone feature modules (each reuses the pipeline where possible and routes through the stub):
- **Interview prep** (`app/core/interview.py`): questions, model answers (STAR, resume-grounded), and feedback on a practice answer.
- **Job match** (`app/core/job_match.py`): rank multiple pasted/URL-fetched listings by fit against the master resume, reusing `jd_analyzer` + `scorer`.
- **Job search** (`app/core/job_search.py`): multi-board fan-out over the provider registry (`app/core/providers/` — LinkedIn, Drushim, Comeet, JobMaster, Greenhouse; per-board failure isolation) for jobs matching the resume (context auto-derived via the `SEARCH_CONTEXT` LLM task, user-overridable: title/location/work mode/limit/sources), then fetch + score each posting like job match. Every provider parser is a pure function pinned by a smoke-test fixture — if a board changes its markup/API shape, fix the parser and keep the fixture green. Worldwide-remote hits are additionally read by `app/core/geo_restriction.py` — see `docs/handbook/job-search.md`. **Work mode is read from what each posting SAYS** (`app/core/work_mode.py`), because LinkedIn's logged-out search ignores its own `f_WT` filter (measured 2026-09-22) — see *Work mode* in the same file.
- **Auto-submit** (`app/core/auto_submit.py`, PLAN 8.4): sends an approved, guard-clean Comeet kit's application through Comeet's public careers-api apply endpoint (the same wire call the board's own Apply button makes). Every guardrail is server-side: approved + guard-clean + Comeet-only, per-company dedupe, `DAILY_SUBMIT_CAP`, audit trail on the tracker application. LinkedIn is never automated.
- **Tools**: `app/core/resume_review.py` (26 deterministic checks, `POST /tools/review`, uncapped and uncharged — it superseded `ats_scan.py` and `resume_health.py`, both deleted in Phase 28), `app/core/free_scan.py` (the CV scan: deterministic, zero model calls, but since Phase 30 an app feature behind the gate at `POST /tools/scan`, with a daily cap and one monthly use), `app/core/ats_xray.py` (**ATS X-ray**: render the resume, read it back with our own parser, and report every protected fact as clean / split / polluted / missing — see `docs/handbook/rendering.md`), `app/core/linkedin.py`, `app/core/follow_up.py`.
- **Shared resume logic**: `app/core/dates.py` (resume date parsing, the ATS-safe rewrite, and years-of-experience over the *union* of role spans), `app/core/section_order.py` (Education above Experience for early-career resumes) and `app/core/skills.py` (`skill_blocks()` — how a grouped skills list becomes rendered blocks). Both renderers and `ResumeView` read the section order, so preview and download always agree; both renderers read `skill_blocks`, so they can never describe the Skills section differently, and `ResumeView` mirrors it in TypeScript for the same reason it mirrors the section order — a preview that groups the Skills section differently from the downloaded file is the one place a user can catch us contradicting ourselves.
- **Master resume** (`app/db/models.py::SavedResume`): persisted once, reused across Tailor / Interview / Job Match via `GET`/`PUT /profile/resume`. One row per language (paired he/en). Every overwrite is versioned — see `app/db/resume_versions.py`.
- **Cost control** (`app/core/quota.py` + `app/core/usage.py` + `app/llm/metering.py`). `quota.py` is the MONTHLY pool (Phase 30): one shared allowance per person, keyed by a one-way hash of the canonical sign-in address, spent by every AI feature, refunded when a call fails, atomic on the caller's own session, and AST-pinned to reach no model, no network and no borrowed clock. `usage.py` is the per-user DAILY caps — `search`, `tailor`, `llm`, `submit`, `inbox`, and since Phase 30 `upload`, `jd_analyze`, `search_context`, `scan` and `fetch` — plus the real prompt/completion token totals under the reserved `action="tokens"` and `action="inbox_tokens"` rows. The daily caps count requests and are never refunded; the monthly pool is the number the user sees, and a route checks its daily cap FIRST so a daily 429 never spends a use.
- **Accounts** (Phase 29; `app/core/accounts.py`, `sessions.py`, `passwords.py`, `auth_throttle.py`, `auth_email.py`, routes in `app/api/auth_routes.py`): email signup that must verify its address (6-digit code or a tapped link), login, logout, forgot/reset, change password, change email while unverified, "sign out of other devices", and the extension key. Invite codes keep working beside it and are grandfathered as verified. Every decision about who is calling is made in ONE middleware — see **Phase 29** in `docs/handbook/accounts-and-auth.md`.
- **Inbox scanner** (Phase 29; `app/core/google_oauth.py`, `gmail_api.py`, `inbox_rules.py`, `inbox_classifier.py`, `inbox_sync.py`, `inbox_apply.py`, routes in `app/api/inbox_routes.py`): Gmail over OAuth `gmail.readonly` fills the tracker from the replies — deterministic rules first, a cheap model (`INBOX_CLASSIFY`) only for the rest, and every tracker write monotonic, reviewable and undoable.
- **Resume preferences** (spec 07; `app/core/resume_prefs.py`, `job_market.py`, `arabic_omit.py`, `numerals.py`): an opt-in "leave Arabic off tailored resumes for jobs in Israel", and quantity words written as digits in tailored prose. Both run inside `tailor_resume` and never touch the master.

**Backend package layout:**
- `app/models/__init__.py` — all Pydantic schemas (`ResumeModel`, `JDModel`, `TailorResult`, `Score`, `FactsLedger`, plus interview/job-match/tools/master-resume schemas). Edit this when adding fields.
- `app/llm/client.py` — `OpenAIClient` and `StubClient`. The stub routes on `Task: <TOKEN>.` tags at the top of each system prompt — don't remove those tags or the stub misroutes. **Every new LLM task needs a matching `if "<TOKEN>" in head` branch here.**
- `app/llm/prompts.py` — every prompt template. LLM behavior tuning happens here.
- `app/core/fabrication_guard.py` — builds a new ledger from the tailored resume, diffs against the original; flags anything that wasn't in the original. Tolerates containment matches to avoid false positives on light rephrasing.
- `app/core/scorer.py` — keyword coverage is pure Python (deterministic, explainable); `fit_score` is the only part that calls the LLM. Both combined into `overall`.
- `app/core/net_guard.py` — SSRF guard. **Every outbound fetch goes through `job_match._http_get`, which calls `assert_fetchable` and uses `guarded_opener`.** Do not add a bare `urllib`/`requests` call: two routes take a caller-supplied URL and return the body, so a fetch that skips this can be aimed at cloud metadata or a loopback port. The predicate is `is_global`, not `is_private` (the latter misses CGNAT `100.64/10`), and redirects are re-checked per hop. **There is exactly one other outbound door, and it is deliberately NOT this one: `google_oauth._http`** (Phase 29), a fixed four-host Google allowlist for the OAuth and Gmail calls, where no URL comes from a caller. Do not route it through `_http_get` — see "The network door" in `docs/handbook/inbox.md` for why the allowlist is the stronger guard there.
- `app/core/keyword_guard.py` — deterministic post-tailor keyword preservation, and the floor under the tailor's own curation. Like `geo_restriction.py` it may never reach the model or the network, and that is source-pinned — through the AST, because a grep cannot tell an import from a mention. See `docs/handbook/tailoring.md`.
- `app/llm/metering.py` — per-request token tally. `OpenAIClient` reports `resp.usage` into it; the `metered_user`/`llm_user` dependencies write it to `usage_log`. Two non-obvious constraints live here, both learned the hard way — see `docs/handbook/llm-boundary.md`.
- `app/api/routes.py` — thin FastAPI handlers that wire the pipeline. No business logic here. **A route that calls the model takes `Depends(llm_user)`** (daily cap + token row) — and **since Phase 30 that is NOT a charge**; routes with their own specific cap (tailor, search, kit drain) take `Depends(metered_user)` instead so they meter without a second charge. **A route that spends the owner's money must also charge the MONTHLY pool**: wrap the work in `quota.charged(db, user, "<feature>")`, or `quota.pass_charged(...)` for a session pass, so a failure gives the use back — and check the DAILY cap FIRST (`app/core/usage.py` records why: a daily 429 must never spend a monthly use, and a daily count is never refunded). Every mounted route is classed by what it costs in smoke 32.13's `_ROUTE_COST`, so a new route fails the suite until it is added there — but note the suite only forces a LABEL, not a charge: `free_capped:<action>` is a legitimate class for a model route kept off the pool, so it passes green on a route that should have charged. **Deciding that a new model route does not charge is a decision to make here, not a default to fall into.** Deterministic routes (`/tools/review`, `/tools/ats-xray`, `/tools/coverage`, `/tools/page-count`, `/render`, `/render/pages`, `/jobs/fetch`) stay uncapped and uncharged, and that exclusion is smoke-pinned — `/jobs/fetch` with the exception of its own `fetch` daily cap, which bounds the outbound GET rather than a model call. `/tools/ats-scan` (Phase 28) and the anonymous `/public/scan` (Phase 30) no longer exist; the scan's successor `/tools/scan` sits behind the gate, costs one monthly use, and with no file scans the saved resume (PLAN 31.7). The account routes (`GET /profile/me`, `DELETE /profile/account`, `GET`/`PUT /profile/resume-prefs`) take plain `Depends(current_user)` for the same reason: they reach no model, so a cap would only be theatre. The `/auth/*` routes (`app/api/auth_routes.py`) take no user dependency at all — the gate resolves the caller — and every `/inbox/*` route takes plain `Depends(current_user)` even though a sync spends model calls, because it bills itself (the `inbox` cap and the `inbox_tokens` row — `docs/handbook/inbox.md`).
- `app/db/` — SQLAlchemy + SQLite (the `applications` tracker, the master resume and its versions, search history, `usage_log`, the monthly-uses tables, the account tables and the inbox tables). `init_db()` is called via the FastAPI lifespan hook and includes a lightweight ADD-COLUMN shim that adds any ORM columns missing from pre-existing tables. **Anything holding user content must be wiped by `_wipe_user_rows`** — the shared helper behind BOTH privacy doors, `DELETE /profile/data` and `DELETE /profile/account` — or a privacy wipe silently leaves PII behind. **The monthly-uses tables (`usage_months`, `usage_events`, `usage_passes`, and since PLAN 31.5 the free-first-search marker `usage_firsts`) run the other way and are NEVER wiped by either door**, AST-pinned by smoke 32.10, so that neither door can reset a limit. The full rule, both carve-outs, the user-content columns, and the master resume's ordering and version snapshots are in `docs/handbook/data-and-privacy.md`.
- `app/render/` — `docx_renderer.py` (python-docx) and `pdf_renderer.py` (reportlab), both driving one shared design system out of `templates.py` and `labels.py`. ATS-safe: no tables/images/headers/footers, and single column everywhere except the two PDF-only sidebar templates. The PDF has its own layout engine, an RTL contract that reverses every Hebrew heading when it is broken, and a list of reportlab traps that each reached production once — **read `docs/handbook/rendering.md` before touching anything in this directory**, `core/ats_xray.py` or `lib/templateSpecs.ts`.

## LLM configuration

The model is provider-agnostic. To swap the model, change `MODEL_ID` in `.env`. The `get_llm_client()` factory in `app/llm/client.py` returns `StubClient` when `USE_STUB_LLM=true` or the API key is empty, and `OpenAIClient` otherwise. All JSON tasks use `response_format: json_object` (JSON mode) for structured outputs.

Default `MODEL_ID` is **`gpt-4o-mini`** — cheap, fast, and strong at this JSON-extraction/rewrite work. Step up to `gpt-4.1-mini` or `gpt-4o` if you want higher-stakes tailoring quality. (Do not use unverified ids like `gpt-5.5`.)

It was 243 KB until 2026-09-21, when every invariant, every measured dead end and every "do not fix this" moved out **verbatim** into the department it belongs to. **Before the first edit, read the handbook file for every department the task touches — the whole file.** The third column is the trigger. Record anything new you learn in the department's file, not here; a new department gets a new file and a row in this table. Keep this file under 40,000 characters, and never pull a handbook file in with an `@`-import: an import is loaded eagerly into every session, which is the cost the split exists to avoid. After editing `CLAUDE.md`, regenerate `AGENTS.md` with the recipe in the header of `AGENTS.md` (check-mirrors 33 fails the build until you do) — the handbook is shared by both, so `CLAUDE.md` is the only part that can drift.

### House rules — true in every department

Each is stated in full, with the defect that produced it, in the file named.

- **Hebrew is the primary market, and its prefixes are word characters.** ב/ל/ה/ו/מ/ש glue onto the noun, so a Hebrew token is matched as a bare substring while a Latin one needs a boundary (`lod` is inside "lodging"). A symmetric boundary passes every Latin test and silently deletes Hebrew coverage, so test any new matcher in both scripts, with the false-positive case beside the catch. (`scoring.md`, `job-search.md`)
- **One matcher, one answer.** "Does this resume carry this keyword" is `scorer._keyword_present`, for every caller; a second matcher is a second opinion about the same document. Keyword STATUS is never computed in TypeScript (check-mirrors 4). (`scoring.md`, `tailoring.md`)
- **Deterministic modules stay deterministic.** `geo_restriction`, `pay_market`, `work_mode`, `hidden_jobs`, `job_market`, `keyword_guard`, `resume_review` and `quota` may never reach the model or the network, and `ghost_signals` may never read the clock. Most of those pins parse the AST, because a grep cannot tell an import from a mention. Read the module's department before adding an import to one.
- **Unknown is never zero, and never clean.** A nullable field on a row that predates the feature means *not measured* (`voice_score`, `fabrication_flag_count`, `last_above_min`, `last_seen_at`), and a check that could not run is `skipped`, never `passed`.
- **Never truncate the user's own document — refuse it (413).** Truncate only text the user neither wrote nor saw. (`llm-boundary.md`)
- **Tailoring never writes to the master resume.** A tailored draft is edited only through the override layer, and every write to the master must reach both module-level caches and the document (`setMaster` or `resetMasterCache()`, and through them `adoptMaster`). (`document-editor.md`)
- **`mergeResumes` must return EVERY `ResumeModel` field, and removing a skill is a two-field write** (`skills` AND `skill_groups`). A section that is printed must be read by both renderers, `scorer._resume_text` and `resume_review._corpus` alike. (`document-editor.md`, `scoring.md`)
- **The UI may not claim more than the code proves.** The fabrication guard says "no new claims detected", never "verified"; the keyword report never says "guaranteed" or "all keywords preserved"; a changelog may not describe a document that does not exist. (`tailoring.md`, `skills.md`)
- **Threads and contexts.** A pool submit whose work calls the model goes through `copy_context().run`, and a ContextVar is never bound inside a FastAPI `yield` dependency — bind it in middleware. Get either wrong and tokens vanish from `usage_log` while every response stays perfect. (`llm-boundary.md`, `tailoring.md`)
- **In a test, patch the name where it is BOUND.** `from x import f` binds `f` in the caller, so patching the defining module is a no-op that reads as a pass. (`testing.md`, `skills.md`, `review.md`, `inbox.md`)
- **Never animate `height: "auto"`** (check-mirrors 11), never assemble a Tailwind class at runtime, and on the sheet nothing moves unless a backend value or a user edit caused it. (`document-editor.md`)
- **The phone is the primary screen.** Verify UI at a real 390 px viewport in both languages, with Playwright — the Chrome extension cannot resize its viewport, so a "mobile" reading taken through it describes a desktop page. (`review.md`)
- **Do not re-litigate a measured dead end.** Prompt rewrites of the skills count, re-ranking the shortlist, a deterministic minting screen, gpt-5.6-luna, per-task model routing, trimming before the page budget and both `cv_planner` count fixes were each measured and rejected, with the decision rule written before the data. Bring new data or leave them. (`skills.md`)
