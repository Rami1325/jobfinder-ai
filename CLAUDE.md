## Running the app

**Python is NOT on the system PATH.** Use the full path:
```
C:\Users\RAMI_\AppData\Local\Programs\Python\Python312\python.exe
```

**Backend (FastAPI):**
```powershell
cd backend
# First time only:
python.exe -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env   # then fill in OPENAI_API_KEY and MODEL_ID

.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```
API docs at `http://localhost:8000/docs`. DB auto-creates at `backend/jobfinder.db` on first start.

**Frontend (React/Vite):**
```powershell
cd frontend
npm install
npm run dev   # http://localhost:5173
```
Vite proxies `/api/*` → `127.0.0.1:8000` during dev (see `vite.config.ts`). **127.0.0.1, not `localhost`** — Node resolves `localhost` to `::1` first while uvicorn binds `127.0.0.1`, which surfaces as a misleading ECONNREFUSED. The same trap applies to anything else you point at the dev servers, `vite preview` included.

**Offline mode (no API key needed):**
Set `USE_STUB_LLM=true` in `.env`. The entire pipeline (parse, score, tailor, render, tracker) works with canned LLM responses.

## Testing

**Offline end-to-end smoke test** — exercises the full pipeline without an API key:
```powershell
cd backend
.\.venv\Scripts\python.exe -m tests.smoke_test
```
Exit 0 = all pass (**1358 checks as of Phase 29**: 1033 before it, +113 accounts, +120 inbox scanner, +54 review fixes, +34 Arabic preference and numerals, +4 browser-pass fixes; 942 as of `users.last_seen_at`). **CI runs it exactly once — there is NO `|| retry`.** There used to be one, for an `updated_at` ordering flake that has since been fixed at the point of writing; it outlived its cause and became a liability, because this file is straight-line top-level code with no top-level `try`, so an exception at check 50 aborts the process and checks 51+ never run. Under `A || A` a nondeterministic crash landed as a GREEN build with ~865 checks silently unexecuted. An `atexit` hook now prints `ABORTED after N checks` so a crash says how much never ran. Run this after any backend change. It is the only file that runs offline and the only one CI runs; the smoke test covers parsing, ledger building, JD analysis, tailoring, fabrication guard, DOCX/PDF rendering, cover letter, the SSRF guard, upload caps, LLM cost caps + token metering, the alerts-cron budget, resume version history, skill normalisation, keyword preservation (the deterministic post-tailor restore), the accounts gate (sessions, CSRF, verification, tokens, throttles, mail budgets), the Gmail inbox scanner (against a fake transport and a `FakeMailbox` — the real Google side is never reached offline), the Arabic preference and numerals — **plus every LLM task** (interview questions/answer/feedback, job match, ATS scan, LinkedIn optimizer, follow-up email). **Any new LLM task must add a stub branch and a smoke-test check** — the smoke test is what guards the stub-routing invariant.

Two habits this suite has repaid, both from real misses: **pin the false-positive case next to the catch** (a guard that fires correctly and also fires on legitimate input is worse than no guard), and when a change alters observable behaviour, **fix the assertion rather than weaken it** — the 20.5/C2 reordering broke a check that identified cron runs by list position, and the right answer was to give the result a `user_id`, not to loosen the test.

**Prompt quality — the real-key A/B harness** (`backend/tests/ab_tailor.py`, added 2026-08-30):
```powershell
cd backend
.\.venv\Scripts\python.exe -m tests.ab_tailor --stub                       # free plumbing check
.\.venv\Scripts\python.exe -m tests.ab_tailor --prepare --jobs 6           # cache fixtures, 1 call/job
.\.venv\Scripts\python.exe -m tests.ab_tailor --variants baseline,x --reps 3
```
**The smoke test cannot see prompt quality and never will** — it drives `tailor_resume` through `StubClient`, which pins the *mechanism* (routing, shapes, guards) and says nothing about whether the real model curates well. Every quality claim in this repo was unmeasured until this harness existed, and the first run it made found a defect nine months of offline checks had been green through: the tailored CV shipped **66 skills, median, against a 66-skill master** — i.e. more than it started with — with 18.3% of them terms the job named. So: **it spends real money and is never run by CI**, `tests/fixtures/ab/` is git-ignored (it holds the owner's own resume and every measured run), and `backend/tests` is already in `.vercelignore`.

Four things about it are load-bearing, each a way the measurement could have lied:
- **The JD is analysed ONCE and cached.** `analyze_jd` is itself an LLM call at temperature, so re-running it per variant varies the *input* while claiming to vary the prompt — and it moves the coverage denominator, which is the metric under test.
- **Every metric is the app's own function** (`scorer.keyword_analysis`, `keyword_guard.lost_keywords`, `voice_audit`, `page_count`). A harness that writes its own matcher grades the code with a different opinion from the one the code holds — the "one matcher, one answer" rule, applied to the grader.
- **The counterweights are not optional.** Cutting skills is trivially easy and the last release fixed the *opposite* defect, so `n_skills` is never read alone: `lost_keywords`, `coverage_after`, `fabrication_flags`, `voice_score` and `pages` sit beside it and a variant that buys a shorter list with any of them is a regression. The decision rule is written down BEFORE the run.
- **It attributes, rather than measuring the end of the pipeline.** A probe records what the MODEL returned and what `preserve_keywords` then ADDED, because "too many skills" has two possible authors and the shipped count cannot tell them apart. That probe is what killed the obvious theory: the guard added **zero** on every run, so `MAX_RESTORED` was never the cause and lowering it would only have re-opened the keyword-deletion defect. **Patch `app.core.tailor.preserve_keywords`, not `keyword_guard`'s** — the caller did `from ... import preserve_keywords`, so the name is already bound and patching the definition module is a no-op. The `max_restored` knob has to write both bindings for the same reason.

**The tailor runs one pair of LLM calls concurrently** (`score_before` ∥ `plan_cv`) — they read the same inputs and neither reads the other. There used to be a second pair, `review_credibility` ∥ `score_after`; **CREDIBILITY was removed** (below), so `score_after` runs inline — a one-member pool is a thread spawn and a context copy for zero concurrency, and an inline call is natively visible to `metering`. Both surviving submits go through **`copy_context().run`, never a bare `pool.submit`** — a worker starts from an EMPTY context, so two of the four calls would become invisible to `metering` and their tokens would vanish from `usage_log` silently, with the tailor still returning a perfect result. **Behaviour cannot pin that**: this suite runs on `StubClient` and only `OpenAIClient` calls `metering.record()`, so a driven assertion reads 0 calls whether the submits are right or wrong — it is pinned by parsing the AST instead. The same trap bit the A/B harness's own latency probe, which stored call timings in a `threading.local()`: `copy_context` propagates contextvars and knows nothing about thread-locals, so the probe lost the pooled calls and reported a 7.3 s pipeline the wall clock measured at 14.4 s. It is a `ContextVar` now.

**`CREDIBILITY` IS GONE — removed 2026-08-31, not deferred.** It produced **7–18 advisory flags per tailor** (mean ~13 over 12 real runs) for **31% of the wall clock**, and the owner's answer to "do you ever read them" was no. Removal beat deferral on the very rule that made deferral awkward: a deferral needs a TRI-STATE (after it, an empty list means both *reviewed, nothing flagged* and *not yet reviewed*), and a deletion has no third state. **Keeping the field defaulting to `[]` would have MANUFACTURED that ambiguity** — `[]` on a new result meaning "we no longer do this" and the identical `[]` on last week's kit meaning "reviewed, nothing flagged", rendering the same blank for two different facts. So the field is gone from `TailorResult` entirely. That is safe because **`TailorResult` carries no `model_config`, so Pydantic v2's default `extra="ignore"` applies** — an old stored kit whose `result_json` still holds `credibility_flags` validates cleanly and the key is dropped (verified, not assumed). Nothing rewrites `tailor_kits.result_json`, so the historical flags survive byte-for-byte in the column and are recoverable if this is ever reversed; they simply stop rendering.

## Architecture

The pipeline flows strictly left to right — each step's output is the next step's input:

```
File upload → resume_parser (DOCX/PDF → raw text)
           → structurer (LLM → ResumeModel JSON + FactsLedger)
           → jd_analyzer (LLM → JDModel JSON)
           → scorer (deterministic keyword coverage + LLM fit score → Score before)
           → tailor (LLM → tailored ResumeModel + changelog)
           → fabrication_guard (diff tailored facts vs. ledger → FabricationFlags)
           → scorer again (Score after)
           → docx_renderer / pdf_renderer (bytes)
```

Beyond the core pipeline, the backend also exposes standalone feature modules (each reuses the pipeline where possible and routes through the stub):
- **Interview prep** (`app/core/interview.py`): questions, model answers (STAR, resume-grounded), and feedback on a practice answer.
- **Job match** (`app/core/job_match.py`): rank multiple pasted/URL-fetched listings by fit against the master resume, reusing `jd_analyzer` + `scorer`.
- **Job search** (`app/core/job_search.py`): multi-board fan-out over the provider registry (`app/core/providers/` — LinkedIn, Drushim, Comeet, JobMaster, Greenhouse; per-board failure isolation) for jobs matching the resume (context auto-derived via the `SEARCH_CONTEXT` LLM task, user-overridable: title/location/work mode/limit/sources), then fetch + score each posting like job match. Every provider parser is a pure function pinned by a smoke-test fixture — if a board changes its markup/API shape, fix the parser and keep the fixture green. Worldwide-remote hits are additionally read by `app/core/geo_restriction.py` — see the invariants below.
- **Auto-submit** (`app/core/auto_submit.py`, PLAN 8.4): sends an approved, guard-clean Comeet kit's application through Comeet's public careers-api apply endpoint (the same wire call the board's own Apply button makes). Every guardrail is server-side: approved + guard-clean + Comeet-only, per-company dedupe, `DAILY_SUBMIT_CAP`, audit trail on the tracker application. LinkedIn is never automated.
- **Tools**: `app/core/ats_scan.py` (11 deterministic format/content checks + optional keyword coverage — dates, acronym pairing, pronouns, bullet length, length vs. experience), `app/core/ats_xray.py` (**ATS X-ray**: render the resume, read it back with our own parser, and report every protected fact as clean / split / polluted / missing — see below), `app/core/linkedin.py`, `app/core/follow_up.py`.
- **Shared resume logic**: `app/core/dates.py` (resume date parsing, the ATS-safe rewrite, and years-of-experience over the *union* of role spans), `app/core/section_order.py` (Education above Experience for early-career resumes) and `app/core/skills.py` (`skill_blocks()` — how a grouped skills list becomes rendered blocks). Both renderers and `ResumeView` read the section order, so preview and download always agree; both renderers read `skill_blocks`, so they can never describe the Skills section differently, and `ResumeView` mirrors it in TypeScript for the same reason it mirrors the section order — a preview that groups the Skills section differently from the downloaded file is the one place a user can catch us contradicting ourselves.
- **Master resume** (`app/db/models.py::SavedResume`): persisted once, reused across Tailor / Interview / Job Match via `GET`/`PUT /profile/resume`. One row per language (paired he/en). Every overwrite is versioned — see `app/db/resume_versions.py`.
- **Cost control** (`app/core/usage.py` + `app/llm/metering.py`): per-user daily caps on `search` / `tailor` / `llm` / `submit`, plus real prompt/completion token totals under the reserved `action="tokens"` row. The caps count requests; the token columns are what they actually cost.
- **Accounts** (Phase 29; `app/core/accounts.py`, `sessions.py`, `passwords.py`, `auth_throttle.py`, `auth_email.py`, routes in `app/api/auth_routes.py`): email signup that must verify its address (6-digit code or a tapped link), login, logout, forgot/reset, change password, change email while unverified, "sign out of other devices", and the extension key. Invite codes keep working beside it and are grandfathered as verified. Every decision about who is calling is made in ONE middleware — see **Phase 29** below.
- **Inbox scanner** (Phase 29; `app/core/google_oauth.py`, `gmail_api.py`, `inbox_rules.py`, `inbox_classifier.py`, `inbox_sync.py`, `inbox_apply.py`, routes in `app/api/inbox_routes.py`): Gmail over OAuth `gmail.readonly` fills the tracker from the replies — deterministic rules first, a cheap model (`INBOX_CLASSIFY`) only for the rest, and every tracker write monotonic, reviewable and undoable.
- **Resume preferences** (spec 07; `app/core/resume_prefs.py`, `job_market.py`, `arabic_omit.py`, `numerals.py`): an opt-in "leave Arabic off tailored resumes for jobs in Israel", and quantity words written as digits in tailored prose. Both run inside `tailor_resume` and never touch the master.

**Backend package layout:**
- `app/models/__init__.py` — all Pydantic schemas (`ResumeModel`, `JDModel`, `TailorResult`, `Score`, `FactsLedger`, plus interview/job-match/tools/master-resume schemas). Edit this when adding fields.
- `app/llm/client.py` — `OpenAIClient` and `StubClient`. The stub routes on `Task: <TOKEN>.` tags at the top of each system prompt — don't remove those tags or the stub misroutes. **Every new LLM task needs a matching `if "<TOKEN>" in head` branch here.**
- `app/llm/prompts.py` — every prompt template. LLM behavior tuning happens here.
- `app/core/fabrication_guard.py` — builds a new ledger from the tailored resume, diffs against the original; flags anything that wasn't in the original. Tolerates containment matches to avoid false positives on light rephrasing.
- `app/core/scorer.py` — keyword coverage is pure Python (deterministic, explainable); `fit_score` is the only part that calls the LLM. Both combined into `overall`.
- `app/core/net_guard.py` — SSRF guard. **Every outbound fetch goes through `job_match._http_get`, which calls `assert_fetchable` and uses `guarded_opener`.** Do not add a bare `urllib`/`requests` call: two routes take a caller-supplied URL and return the body, so a fetch that skips this can be aimed at cloud metadata or a loopback port. The predicate is `is_global`, not `is_private` (the latter misses CGNAT `100.64/10`), and redirects are re-checked per hop. **There is exactly one other outbound door, and it is deliberately NOT this one: `google_oauth._http`** (Phase 29), a fixed four-host Google allowlist for the OAuth and Gmail calls, where no URL comes from a caller. Do not route it through `_http_get` — see the Phase 29 section for why the allowlist is the stronger guard there.
- `app/core/keyword_guard.py` — deterministic post-tailor keyword preservation, and the floor under the tailor's own curation. Like `geo_restriction.py` it may never reach the model or the network, and that is source-pinned — through the AST, because a grep cannot tell an import from a mention. See the invariants below.
- `app/llm/metering.py` — per-request token tally. `OpenAIClient` reports `resp.usage` into it; the `metered_user`/`llm_user` dependencies write it to `usage_log`. Two non-obvious constraints live here, both learned the hard way — see **Key invariants**.
- `app/api/routes.py` — thin FastAPI handlers that wire the pipeline. No business logic here. **A route that calls the model takes `Depends(llm_user)`** (daily cap + token metering); routes with their own specific cap (tailor, search, kit drain) take `Depends(metered_user)` instead so they meter without a second charge. Deterministic routes (`/tools/ats-scan`, `/tools/ats-xray`, `/public/scan`, `/render`) are deliberately uncapped, and that exclusion is smoke-pinned. The account routes (`GET /profile/me`, `DELETE /profile/account`, `GET`/`PUT /profile/resume-prefs`) take plain `Depends(current_user)` for the same reason: they reach no model, so a cap would only be theatre. The `/auth/*` routes (`app/api/auth_routes.py`) take no user dependency at all — the gate resolves the caller — and every `/inbox/*` route takes plain `Depends(current_user)` even though a sync spends model calls, because it bills itself (the `inbox` cap and the `inbox_tokens` row, below).
- `app/db/` — SQLAlchemy + SQLite (`applications` tracker + `saved_resumes` master resume + `saved_resume_versions` undo buffer + `job_search_hits` search history + `usage_log` caps/tokens). `init_db()` is called via the FastAPI lifespan hook and includes a lightweight SQLite ADD-COLUMN shim that adds any ORM columns missing from pre-existing tables. Job-search results are auto-persisted as history via `app/db/history.py` (deduped by URL, capped at the newest 100) and exposed at `GET`/`DELETE /jobs/history`. **Anything holding user content must be wiped by `_wipe_user_rows`** — the shared helper behind BOTH `DELETE /profile/data` (wipe, code keeps working) and `DELETE /profile/account` (wipe + deactivate, code stops working). Add new tables there, or a privacy wipe silently leaves PII behind. It also clears the two user-content COLUMNS — `users.search_prefs_json` and `users.writing_prefs_json` — which rows-only wipes missed: they are per-column, not per-row, so they add no field to `DeleteMyDataResult` and the response shape is unchanged. Since Phase 29 it clears a third column, `users.resume_prefs_json` (the Arabic preference implies ethnicity), and wipes `mail_events` and `mail_connections` — AFTER handing the Google grant back (`inbox_sync.revoke_stored_grant`), reporting `google_revoked` honestly rather than claiming a revoke that did not happen. `DELETE /profile/account` additionally blanks `users.name` and `users.email` and runs `accounts.purge_on_close` (logins, tokens and sessions deleted; auth events kept with `user_id` NULLed — see Phase 29). The account tables are `user_logins`, `auth_sessions`, `auth_tokens`, `auth_events`; the inbox tables are `mail_connections` and `mail_events` (no body column — a full email is never stored). `DELETE /profile/account` refuses for an admin, because `admin_update_user` already refuses to deactivate one (it is the only way back into a deployed instance) and with the access gate OFF every local request IS the admin.
- `app/render/` — `docx_renderer.py` (python-docx) and `pdf_renderer.py` (reportlab), both driving one shared design system out of `templates.py` (palette, type, rhythm, page size, **presentation**) and `labels.py` (section names, EN/HE, in two SETS chosen per template by `TemplateSpec.label_set`). ATS-safe: no tables/images/headers/footers, and single column everywhere except the two PDF-only sidebar templates.
  - **The PDF has its own layout engine.** Every run is line-broken by `_wrap_lines` and drawn with a text object, so Hebrew (bidi-reordered per line, right-to-left) and English share one set of flowables — `_Text`, `_Row` (title + flush-far-edge dates), `_Segments` (inline list with per-item colour/link/icon), `_Heading`, `_BarHeading`, `_Chips`, `_Cols`. reportlab's `Paragraph` is deliberately unused: its wrapping is direction-blind.
  - **The RTL contract — get this wrong and every Hebrew heading reverses.** `_draw_line` calls `_visual()` **itself**. A flowable drawing through it passes **logical** text (`_wrap_lines` returns logical lines on purpose); a flowable drawing with a raw `canv.drawString` applies `_visual()` itself (`_Chips` does). Pre-reordering before `_draw_line` double-reverses: תקציר renders as ריצקת while body text stays correct, so it is easy to miss.
  - **Every bare Flowable that can exceed a page needs `split()`.** reportlab cannot place one that doesn't and raises `LayoutError` — which reached production as a 500 from `POST /render` for any resume with a long summary. `_Text.split()` pins its already-computed line break onto each half (`_pinned`) because re-wrapping the re-joined text can break differently and drop a word; the head keeps the bullet glyph, the tail must not grow a second one. Smoke-pinned per template.
  - **Icons are drawn paths, never glyphs** (`_draw_icon`, `_ICONS`). No bundled face has an envelope or a map pin, so a glyph would print a tofu box *and* land in the extracted text — on the exact line an ATS parses as the email address. A path emits no text operators, which is the whole reason this is safe. Each icon is defined in a **unit box** and drawn through a scaled CTM (stroke weight included), so one definition serves every size. In RTL the icon leads its label from the **right** — it sits at the far end of the item's own box in `_Segments` — and a directional shape (`_ICON_MIRRORED`: the handset, the link) is mirrored with it.
  - **A two-column template's sidebar must be incapable of overflowing.** reportlab reacts to a full frame by advancing to the NEXT one — which is the main column — so sidebar overflow lands there, and the `FrameBreak` that follows then pushes the real main content onto page 2, *into page 2's side frame*. That shipped: a 138-skill resume rendered its Summary and Experience inside the 30%-wide rail. `_flow` now measures each sidebar section at the rail's width and DEMOTES any that will not fit into the main column, and page 2+ is a single full-width frame because the rail is a page-1 device like the header band. Both halves are needed; either alone still breaks. Smoke-pinned positionally — the old checks rendered every template but never asserted *where* content landed, which is exactly why the bug survived them.
  - **A chip may not be wider than its column — and that is `_Chips`' job, not the demotion pass's.** `_pack` broke to a new row only when the current one already held something, so a single item wider than the whole column was appended to an EMPTY row unconditionally; `wrap()` then reported `avail_w` regardless of what it had packed, and nothing clips. Measured on `split` (rail 148.58pt at [48.0, 196.6]): one 60-character skill packed a 253.00pt row and was drawn to x=301.0, 84pt past the gutter; a 147-character one packed 616.13pt. The damage is not cosmetic — the chip overprints the main column at the same y and pdfminer y-sorts, so extraction returned `"Designing and operating distributed backeEnXd PsyEstRemIEs NatC scEale"` and **`"EXPERIENCE" in extract_text(...)` was False**: one long skill deleted a standard section name from the file we tell the user is ATS-safe. An over-wide item now takes a row of its own and is line-broken by **`_wrap_lines`**, whose hard-break loop already survives a token longer than the column — which is why every `inline`-skills template was always clean; the correct behaviour existed in the file and `_Chips` did not use it. `_Chips` draws **LANGUAGES too**, so this was never skills-only. Three consequences: `_visual()` is applied **per LINE** after `_wrap_lines` has broken LOGICAL text (pre-reordering stacks the lines backwards); each line is positioned through `_place`, since a single-line chip only right-aligns in RTL by accident (its box width is derived from its own advance); and `split()` **accumulates per-row heights** instead of dividing by a fixed `chip_h + gap`, or a two-line row is counted as one and the head handed to the frame is taller than the room it was given. The sidebar demotion pass stays **height-only**: a wrapped chip is genuinely taller, so `_content_height` already demotes on it, and a width gate there would be a second classifier answering the same question from a different gate — the correction the geo-restriction work paid for once. An ordinary skills list renders **byte-identically** before and after (all templates × 2 languages, modulo reportlab's per-render `/ID` digest — the only non-deterministic bytes in a PDF), and that half is smoke-pinned beside the catch, because "make the long skill fit" is trivially satisfied by wrapping every chip.
  - **`KeepTogether` and `keepWithNext` both REFUSE to split**, and reportlab implements the latter *as* the former. So neither may wrap a run that can grow page-sized: it moves whole to the next frame and leaves the column it came from empty. `KeepTogether` is for gluing a heading to its FIRST item only. The skills block is the one section that can be page-sized, so it is emitted bare and `_Chips.split()` breaks it at a row boundary — verified by probe, since with either wrapper in place `split` is never called at all.
  - **Never nest `KeepTogether`.** It reports a sentinel height, so a nested one pushes every section onto its own page.
  - `_flow` returns **`(header, main, side)`**. `side` is non-empty only for a sidebar template; `header` is split out so a `header="band"` template can put it in its own frame *inside* the painted rectangle. A `_Band` spacer in the body frame does **not** work — it pushes the reversed-out white name below the band, where it renders white on white.
  - **Two-column is PDF-only, and that is a measured decision, not caution.** PDF text extraction y-sorts across the full page width, so a sidebar glues itself to the front of the main-column line at the same height (`"Python Go PostgreSQL Senior Backend Engineer"`). Individual bullets always survive intact — keyword matching is unaffected — but title/employer attribution is polluted. Ordering the content stream main-column-first does **not** help; pdfminer y-sorts regardless. So `split`/`panel` set `docx_fallback` and the Word file renders the named single-column sibling. Both facts are smoke-pinned.
  - **`pdf_family` is Latin-only.** RTL reads `he_family`; before that split every template resolved to the same Hebrew face and `executive` silently lost its serif in our primary market. In DOCX, Word formats Hebrew through `w:cs`, so `docx_font_he` must name a family that *has* Hebrew glyphs — pinning the Latin `docx_font` there asked Word for Georgia on a Hebrew resume and it substituted something else.
  - reportlab gotchas, both learned the hard way: **`FrameBreak` is not a class** in 4.2.5 (`isinstance` raises `TypeError` — track the header block by index), and a page template **repeats itself** unless you set `autoNextPageTemplate`, so without it page 2 of a band template paints the band again.
  - `fit_squeeze()` decides one page vs. two by measuring the built flow, and compresses the vertical rhythm (never the type size) when the resume overflows by a little. The DOCX renderer calls the same function so both downloads agree.
  - Hebrew DOCX must mirror `w:b`/`w:sz` onto `w:bCs`/`w:szCs` — Word formats Hebrew through the complex-script properties and ignores the plain ones.
  - Fonts are bundled under OFL (see `fonts/README.md`); a missing file degrades to base-14 rather than failing the download.
  - **`_wrap_lines` is memoized** (`_wrap_cached`, LRU 4096) because the page budget is allowed 60 real reportlab builds per tailor and every one re-wraps the same bullets. It must stay pure in `(text, font, size, width, tracking)`; it returns a fresh list of a cached tuple so a caller that mutates its lines can't poison the next render. Keying on the font NAME is what makes it safe — a missing-file fallback registers under a different name.

## LLM configuration

The model is provider-agnostic. To swap the model, change `MODEL_ID` in `.env`. Default `MODEL_ID` is **`gpt-4o-mini`** — cheap, fast, and strong at this JSON-extraction/rewrite work. Step up to `gpt-4.1-mini` or `gpt-4o` if you want higher-stakes tailoring quality. (Do not use unverified ids like `gpt-5.5`.)

## Key invariants

### Phase 22 — the document surface

- **The tailor page IS the document.** `/app` renders the resume (`ResumeView`, `surface="sheet"`) with a toolbar over it; tailoring is an overlay (`TailorOverlay`), not a page. There is no stepper. `shown = effectiveResume ?? resume` is the whole of "the page always has a CV".
- **Editing never writes back to the MASTER from a tailored draft — AMENDED IN 23.7, read that section.** The original rule was `onEditBlock` is passed only when `!result`, because with a result up the document is a memo recomputed and discarded on every accept/decline, so writing into it needs an override layer that survives the re-merge. 23.7 BUILT that layer: the tailored document is typed on, through an anchor-keyed override map that is discarded with the result. What survives intact is the second half — tailoring is a *review layer* that never writes back to the master. So: master ⇒ edit the document; tailored ⇒ edit a per-application overlay.
- **`lib/resumeBlocks.ts` is the only reader and writer of a block.** The document addresses blocks by path (`@exp.2`, `@exp.2.b.1`, `@skills.python`) and `readBlock`/`writeBlock`/`removeBlock` resolve them. **Since 23.1 the document is TYPED ON, and the split is DERIVED.** A block that is ONE model field (`@contact.name`, `@headline`, `@summary`, every `@*.b.*`, `@skills.*`, `@cert.*`) is `contentEditable` on the paper whenever the document is the master — no editing mode, no `editingPath`; a tap places the caret, and while it is there **nothing re-renders**, which is what keeps it alive (react-dom skips a text child whose string is unchanged, so a coverage response or the spotlight timeout cannot disturb it). Commit is on blur or Enter. The split is `inlineField()`, derived from `readBlock` — one field means a caret, more means the panel — so it **cannot drift from the reader**: add a second field to a block and it stops being typed on by itself.
  `BlockEditSheet` survives for the six COMPOUND blocks only. **The sheet edits an ENTRY, not a field** — that is what dissolves the fused-text-node problem (an experience meta line is five model fields in one text node), so never "fix" it by splitting `MetaLine`: that re-opens the bidi-isolate problem and buys nothing.
  **The sheet's old justification was measurably false; it is recorded so nobody restores it.** It claimed "at 390px an A4 page renders at about 45% scale, so body text is roughly 6px". That describes the PDF `<iframe>` in `DocumentPanel`, not `ResumeView`. Measured on the running app at 390px: `.sheet` is `transform: none`, 347.3 px wide, body text 14 px. What survives from it: no hover on a phone, and a toolbar near the caret fights the on-screen keyboard — so inline editing grew **no toolbar at all**.
  Each of these is a bug avoided, not polish: both delegated handlers bail on `isContentEditable` FIRST or the `preventDefault()` on `" "` kills the **space bar** in every editable block; `contentEditable="plaintext-only"` is **probed** with `true` as fallback, because its invalid-value default is *inherit* and an unsupporting browser would render the block silently non-editable; paste is forced to plain text (a bullet is a `string` through both renderers into `_wrap_lines`); `spellCheck=false autoCapitalize="off"` or iOS rewrites "gRPC" to "GRPC"; Enter is guarded on `isComposing`; and an unchanged edit is refused **and the DOM restored by hand**, because React does not repair a browser-mutated node whose own string is unchanged.
- **Adding is one control at the foot of the paper** (23.2): seven FIXED rows — role, project, degree, military service, skill, certification, language — plus "+ Add a line" at the end of each entry's bullets. Fixed, not conditional on emptiness: creating the first project and the fourth are the same action, and a section appears when it has content exactly as both renderers do. A new item arrives **empty**, never placeholder-filled — a placeholder is a fabricated claim the moment it reaches a renderer. **That was asserted here and FALSE in the code until 2026-09-02 for three of the seven rows.** Skill, certification and language are addressed by their VALUE (`@skills.python` IS the skill), so an empty one has no path at all — `dkey("")` is `""` and `RE_KEYED` needs a character after the dot — and `insertBlock` answered that by minting the literal English strings `"New skill"` / `"New certification"` / `"New language"`. `applyBlockEdit` committed them on the same tick, so they rendered as chips, went into the DOCX and the PDF and reached the tracker with no Save; `check_fabrication` cannot see them because the ledger is built FROM the master, so the app's own truthfulness guard certified the invented string clean; and on a Hebrew CV they were untranslated English. **The fix is not a new address for a blank item — a keyed item is TYPED, never inserted blank** (`insertNamed`, the mechanism `AddSkillChip` already used: a real `<input>` whose *placeholder* is browser chrome, not a value). Inserting `""` instead would have been the same defect wearing a different hat: both renderers draw a chip for a blank skill, so there is no honest blank chip to store. check-mirrors 25 pins it by EXECUTING `resumeBlocks.ts` and measuring text over the whole model, so a placeholder in a field added years from now still fires.
  Two rules stop an abandoned add littering the document: **empty means remove** on the inline path (which `readBlock`'s `removable` comment always specified and nothing implemented), and a blank ENTRY is removed when its panel is cancelled, scoped to the entry that session created — deleting a pre-existing blank entry is the direction that loses data. The keyed kinds need neither now: nothing is written until text exists. `removeBlock` gained an `RE_ENTRY` branch at the same time: until 23.2 a job, project, degree or service **could not be deleted at all**.
- **There is ONE editor, and `/builder` is gone** (23.4). An 848-line from-scratch wizard plus two locale namespaces (fetched on every cold start — `i18n.ts` awaits all of them before first render) was a second editor for one resume, and it produced the "which one is my real CV" question it existed to avoid. It appeared in neither `primaryNav` nor `moreNav`, so it was already orphaned; its two entry points were `ResumeGate` and `TailorPage`'s empty state.
  **The cold start it existed for is preserved, on the same surface as everything else**: "Build one from scratch" on `/app` seeds a blank `ResumeModel` into the store and the document becomes a blank page you type on. Two things had to be true first, and both are: the header blocks (`@contact.name`, `@headline`, `@contact`, `@summary`) **render even when empty while editing**, or a from-scratch resume has no reachable block at all — they are unreachable otherwise, because `ResumeView` renders a section only when it has content. And an empty block shows a CSS placeholder (`[data-ph]:empty::before`), never the fallback string as text: **a placeholder rendered as text is committable**, which is how tapping the biggest target on a nameless CV could write "Resume" in as the person's name.
  **A blank page follows the UI locale, not `resumeLanguage`.** With no prose there is nothing to detect from and `resumeLanguage` returns "en" for an empty resume exactly as it does for an English one — so a Hebrew user starting from scratch would type into a left-to-right page. `ResumeView` checks whether any prose exists and falls back to `i18n.dir()`.
  Note for check-mirrors: check 9's documented carve-out ("scoped to AppLayout because BuilderPage calls `t("nav.back")` against the builder namespace") lost its only exception here. The check is deliberately left scoped anyway — widening it would be a behaviour change with no defect behind it.
- **Block paths carry an `@` prefix and it is not decoration.** Without it `exp.0.b.1` is simultaneously a valid *edit id* (original indices, from `resumeDiff`) and a valid *block path* (effective indices) — string-identical, different meaning, silently swappable.
- **`mergeResumes` must return EVERY `ResumeModel` field.** It rebuilds the resume field by field; a field added to the model and forgotten here is silently DELETED the moment one edit is rejected. This shipped: `headline` and `skill_groups` vanished from the download, the tracker row and the cover letter, and `tsc` was quiet because both are optional. Check 1 exists for this.
- **Removing a skill is a TWO-FIELD write** (`skills` AND `skill_groups`). The model validator keeps `skills` as the flat union and only ever ADDS, so writing the group alone leaves the old spelling behind and the next round trip restores it — the deletion silently does nothing.
- **Keyword coverage is computed server-side, on `POST /tools/coverage`, and NEVER in TypeScript.** `scorer._keyword_present` tries the verbatim phrase FIRST, which is what makes Hebrew work: prefixes glue to the word (ב/ל/ה/ו/מ/ש), so `פייתון` must match inside `בפייתון`. Check 4 fails the build if any `lib/*.ts` starts returning `covered`/`partial`/`missing`. **The stated reason for that rule was corrected in 2026-09-02** — it used to be "`lib/keywords.ts`'s boundary guard makes exactly that case miss, so a second matcher shows a different number". The two matchers now AGREE on the Hebrew case, because the Python side was given the same asymmetry the TS side already had (below). The rule stands on its real reason: `countOccurrences` answers "how many times does this phrase appear", while STATUS also carries the token fallback and the `partial` tier, which TS does not implement and must not start to.
- **The coverage corpus is EVERY PRINTED SECTION, and `_keyword_present` matches only at token boundaries. Both were wrong until 2026-09-02, in opposite directions, on the same function pair.** (a) `scorer._resume_text` omitted `headline`, `military_service` and `languages` while both renderers draw all three — so an Israeli CV whose Kubernetes/Terraform evidence lived in a unit bullet scored them `missing`, and `/tools/coverage` advised "surface real experience using the term 'Terraform'" about a page that printed it twice. (b) the verbatim branch was a bare `kw in resume_text` with no boundary, so `Go` matched inside "django", `ORM` inside "terraform", and `R`/`C` matched almost anything — all ordinary `jd.hard_skills` values. Coverage is half of `overall`, so both moved search ranking, History, the fit ring and the 75% alert bar; and because four call sites share this one function, a false `covered` also shielded a skills entry from the page-budget trim and could make a restore look successful when nothing was carried.
  Three things about the fix are load-bearing. **The boundary is ASYMMETRIC** — a Latin-only lookbehind so Hebrew's ב/ל/ה/ו/מ/ש still glue on, a full-class lookahead so a longer word that merely starts with the keyword does not match. A symmetric boundary passes every Latin test and silently deletes Hebrew coverage in the primary market. **`.` needs its own clause**: it is a word character only so `.NET` and `node.js` hold together, but a keyword at the end of a sentence is followed by one too, so the lookahead rejects `.` only when a word character follows it — otherwise `SQL` is invisible inside "…ו-SQL." (that is how this change first came back red, and `lib/keywords.ts` still has the flat class and the same blind spot). **A longer term that STARTS with the keyword is `partial`, never `covered`** — `PostgreSQL` is evidence for `Postgres`, not the term. Dropping it outright was the first attempt and it broke a pinned invariant one file over: `length_budget._drop_unmatched_skill` protects any entry the scorer reads as not-`missing` and removes the LONGEST unmatched one, so a strict boundary would have deleted "PostgreSQL administration and replication tuning at scale" from a CV applying to a job that says Postgres. The `_PREFIX_MIN = 5` floor under that rule is **TUNED, NOT MEASURED**, and is recorded that way: it sits above `Java` (the case `lib/keywords.ts` names in its own comment) and below `Postgres`.
  **`ats_scan._resume_text` is a DELIBERATE second corpus, not a duplicate to merge**: it joins skills with `", "` and parts with `" \n"`, filters empties and preserves case, because it feeds prose checks (`_has_term`, the one-page word count) rather than matching. The two may differ in punctuation; they may NOT read a different set of sections, and a smoke check pins exactly that with a sentinel per section — nothing pinned it before, which is how they disagreed about military service for as long as they did.
- **The skills space-join is load-bearing and must not become `", "`.** `order_skills`' acceptance gate measures coverage either side of the reorder, and a multi-word JD keyword matching ACROSS the join between two adjacent entries is the behaviour that gate was calibrated on. Smoke-pinned.
- **The ATS x-ray must search the VISUAL form of a fact as well as the logical one.** `pdf_renderer._draw_line` draws bidi-reordered glyphs, so pdfminer returns visual text while a fact from `ResumeModel` is logical. Before `_candidates()` existed, a correctly rendered Hebrew PDF reported 14 of 16 facts `missing`. `ats_xray` imports the renderer's own `_visual` on purpose — if the renderer's `base_dir` changes, the x-ray follows it.
- **The fabrication guard can say "no new claims detected". It can never say "verified".** `_known` is containment in *either* direction, so a ledger holding `"5"` clears an invented `"250"`, and skills are unchecked by design. Nineteen strings claimed otherwise until Phase 22.
- **"Save for later" writes a tracker row, it does not invent a new store.** The Jobs card's Save button posts `ApplicationCreate` with `status: "saved"` and NO tailored resume and NO cover letter — that is what saving a job you have not acted on yet means, and `ApplicationCreate` already allowed it while the `saveApplication` TS wrapper typed both as required, over-constraining the schema it wraps. `hideApplied` deliberately does not hide `saved` (saving IS "come back to this"), so the shortlist survives the filter. The button reads `justSaved || appStatus`: the page's status map is rebuilt per SEARCH, not per click, so without the local override a freshly saved job keeps offering "Save" until the next search. Once a job carries ANY tracker status the button is replaced by a disabled one naming that status — offering Save on a job already applied to would write a second row.

### Prompt input bounds, and honest size errors

- **`app/llm/prompts.py` is the input boundary, and that placement is measured.** All 22 `complete_json`/`complete_text` calls in `app/core` and `app/parsers` build their user message with a `*_user(...)` builder — no exceptions — so the builders are the one place unbounded text becomes prompt text. Guarding the STORED master resume is not enough: **25 request models take a `resume: ResumeModel` straight from the client body** (tailor, cover letter, every interview route, LinkedIn, resume health…), so `PUT /profile/resume` is one of twenty-six doors. The guard is a `@_bounded` decorator that discriminates by ARGUMENT NAME, which is why `resume_json` / `raw_text` / `jd_text` must stay consistent — a new builder naming its parameter something else is silently unguarded, and a smoke check pins exactly that.
- **It is NOT in `client._create`.** That sees the assembled string and would slice a resume's JSON mid-object, handing the model a truncated document at the one boundary the fabrication guard cannot see (it diffs the tailored resume against the ledger, never the prompt).
- **Never truncate the user's own document — refuse it (413). Truncate only text the user neither wrote nor saw.** A silently shortened resume is data loss in the most valuable object the user owns, and here it does not stay a warning: the parsed model is live in the store the moment it returns, `PUT /profile/resume` versions it into one of 20 evictable slots, `useSaveMasterResume` swallows every error, and nine pages read it from a module cache. By the time the notice is read, the damaged CV IS the master. Scraped page text is clipped silently at its source (`job_match._clip_jd`), so it arrives under cap and the builders' refusal never fires on it — which is also why nothing needed a "we truncated this" response field.
- **Sized in UTF-8 BYTES, never characters.** Hebrew costs ~1.9 bytes/char against English's 1.0, so a character cap silently grants the primary market roughly twice the tokens for the same number. Bytes halve that gap with no `detect_language` branch to get wrong on the mixed Hebrew-prose/Latin-skills resume that is the Israeli norm. Bytes do **not** fully normalise it, and the caps are therefore sized against the Hebrew case.
- **A cap is a guard rail, not a budget**: it must fire on a 500-page PDF and never on a real CV (`config.py` records that a master can legitimately run ~30 rendered pages). The legitimate-but-still-too-big document is caught by `ContextWindowExceeded` instead. `PUT /profile/resume` carries a load-bearing carve-out — **a save that SHRINKS an already-oversize master is always allowed**, or anyone whose resume predates the cap is locked out of the very trim that would fix it.
- **`max_upload_mb` caps COMPRESSED bytes and a .docx is a zip, so it needs a decompression twin** (`_assert_docx_expansion`, added 2026-09-02). `python-docx` expands every part into an lxml tree before a word of text exists: measured, 0.298 MB of zip is 102 MB of `document.xml` (343:1), so the 10 MB upload cap admitted ~3.4 GB of XML from unremarkable content. This matters because **`POST /public/scan` takes no access code** — it is the one door that feeds a stranger's FILE straight into the parser. (Since Phase 29 the anonymous `/auth/signup`, `/auth/login`, `/auth/verify`, `/auth/forgot` and `/auth/reset` take a stranger's input too, but only small form fields, each behind the throttles described there.) The guard sums `ZipInfo.file_size` over the WHOLE archive (central-directory metadata, so nothing is decompressed to read it, and a bomb parked in `styles.xml` or `word/media/` costs the same as one in `document.xml`), and raises `InputTooLarge` → the existing 413, never a 400: it is a limit the user can act on, and 413 keeps it out of Sentry.
  **The declared sum is an upper bound, not a claim we trust — that was checked, not assumed.** `ZipExtFile._read1` clamps every member to `data[:self._left]` with `_left` seeded from `file_size`, and the CRC then fails at EOF, so an under-declaring zip inflates nothing and lands on the 400 path. A second pass that re-read the archive to "verify" the sum would add no guarantee and would inflate every legitimate upload twice. Smoke-pinned in that direction too.
  **The cap's floor is DERIVED (`max(cap, 3 * max_upload_mb)`), not written down twice.** Images are already compressed, so an image-heavy .docx expands ~1:1 and `max_upload_mb` is itself the largest expansion a real CV can reach (measured 10.3 MB at the 10 MB cap) — a cap below that refuses a legitimate photo-heavy resume the upload cap just admitted. **32 MB, not 64:** `extract_text` is linear at ~1.19 s per MB of expanded XML, so 64 MB let an anonymous request buy ~76 s of an instance against Vercel's 300 s kill; 32 halves that and still leaves 3× headroom. Note the suite sets `MAX_UPLOAD_MB=1`, so an HTTP-level false-positive check must use a SMALL file — the 6 MB image fixture is refused by the upload cap before this guard is reached.
- **The output cap MAY NOT ship without the `finish_reason == "length"` check**, and that is the highest-risk part of this work. `chat.completions.create` NEVER raises on truncation — it returns partial content, and the SDK's own `LengthFinishReasonError` is reachable only through `.parse()`/`.stream()`. Without the hand-written check, a cap turns a working tailor into `json.loads` failing on half an object ("Unterminated string starting at: line 1 column 892"), which reads as our bug rather than a limit; and `complete_text` (the cover letter) has no parse step at all, so the letter just silently stops. Both entry points are pinned by DRIVING them, because a check that calls the guard directly still passes with the call site deleted.
- **A context overflow is discriminated by `code == "context_length_exceeded"`, never by exception type.** Every malformed-parameter bug is also a `BadRequestError`; reporting those as "your resume is too long" is a guard firing on legitimate input.
- **The capability probe is a LOOP over one parameter per attempt.** The original was single-shot and stripped exactly one kwarg, so a model rejecting both `temperature` and the output-cap name died on the second — which is precisely what adding a second probe to it would have caused. `max_completion_tokens` falls back to the legacy `max_tokens` on rejection.
- **413 is deliberate on both counts**: it matches the existing upload cap, and Sentry's Starlette integration captures only 5xx — so a limit the user can act on stops generating issues while a genuine 500 still does. `OutputTruncated` maps to **503** instead, because nothing about the request was too big and it is our own ceiling that was hit, so it should stay visible.
- **Known and deliberately out of scope**: the multi-turn interview transcript still grows without bound (it is re-sent in full every turn) — bounding a conversation is windowing, not a cap, and belongs in its own change.

### Geographic hiring restrictions — the worldwide-remote fix

- **`geo_restriction.py` is deterministic and MAY NEVER reach the model or the network**, and both are source-pinned (the 22.10 `/tools/ats-scan` shape: behaviour alone cannot pin this, since an LLM-backed classifier also returns a verdict). Two reasons it is not a field on the JD_FIT call it would ride for free: `complete_json` runs at `temperature=0.3`, so a boolean that REMOVES a job would have no error bar the user can see; and the verdict is recomputed on read (below), which a model call cannot be.
- **It is gated on `JobHit.origin_market`**, stamped by `_search_board` from `_board_queries`' fourth element — `""` for the user's own location, the market name for each worldwide query. So with `include_worldwide` off the classifier is never called, and every Israeli-board posting is structurally out of its reach rather than merely unlikely to trip it. The stamp is carried, never inferred: with several keywords the local location recurs at index 0, `len(locations)`, `2*len(locations)`…, so a positional test is wrong, and a `location != ctx.location` test misfires the moment a user types "United States" as their location. A URL the LOCAL query also returned has its stamp cleared (`_search_board`'s local-wins pass) — it is visible from Israel by construction.
- **The verdict is a VALUE, never an exception.** `_score_hit`'s contract is "never raises for a per-job problem"; a raise lands in `score_errors` and surfaces as "found N jobs but couldn't score any of them", blaming the boards for a posting we deliberately dropped. `_build_match` returns `(match, geo)`.
- **BOTH `_build_match` branches must classify, and the cache branch is the one that gets forgotten** — it skips the fetch AND the LLM, so nothing in it looks like work, and a posting scored last week would launder straight through. Smoke-pinned with the fetch made observable (with inline descriptions `fetches` is 0 either way and the check passes without the branch doing anything).
- **The local-wins pass is keyed by URL *and* by content.** `_interleave_into` dedupes both ways and keeps whichever hit sorted first, so a company posting the same role twice — Tel Aviv and US-remote, different URLs, identical title+company — had the worldwide twin win the merge, keep its stamp, get filtered, and take the Tel Aviv URL with it. `FilteredJob` carries no `also_on`, so the posting the user's own query returned vanished from the response entirely.
- **The all-filtered early return re-attributes `score_errors`.** Its guard is `filtered`, not "everything was filtered", so postings that genuinely broke can ride along — and skipping the raise below would drop their diagnostic. Each is attributed to the board it came from. The frontend's "every job" copy is likewise gated on `skipped === 0`, or it contradicts the "N skipped" line directly above it.
- **`filtered` is its own list and MUST NOT fold into `skipped`**, whose user-facing string means "not fetchable/scorable". A filtered posting was perfectly fetchable. It is RETURNED rather than discarded — count, quoted sentence, one-tap reveal — because the objection to hiding is to SILENT hiding, and returning the list removes the silence while still skipping the LLM call.
- **An all-filtered search returns a 200 with `matches: []`**, the one existing contract this changes ("a 200 always carries at least one match"). Raising would destroy the filtered list in the maximum-suspicion case and send the user to re-run a search that fails identically.
- **Nothing else re-derives the verdict, and that is the correction that matters most.** Two extra call sites were written and REMOVED after review, because each classified on a DIFFERENT gate from the search and so contradicted it about the same posting. `kits.enqueue_kits` classified every job ungated: a LinkedIn posting the user's own location query returned is ranked with no badge, and "Application kit" on it returned a 400 saying it states a hiring restriction abroad — an Israeli-board job needing an Israeli clearance failed identically. `GET /jobs/history` gated on `source == "linkedin"`, strictly wider than the origin stamp, so History badged "Likely US-only" on a posting the search had shown clean — and it cost up to ~1.6 s of regex per request over 100 rows. `search_jobs` is the only caller that acts on `blocking`; `job_match` attaches the label and never filters. A smoke check greps `kits.py` for the import and the call.
- **The classifier is fast-pathed on a marker set** (`_MARKERS`): a posting containing none of the rule vocabulary returns None without scanning. A clean posting is otherwise the WORST case, since every rule runs to completion. Keep it a superset of the rule table — a stem missing there silently disables its rule, and that rule's own check is the alarm.
- **It can say a posting STATES a restriction. It can never say the user cannot work it** — the sponsorship question usually lives in the application FORM, and an Israeli with a second EU passport reads "EU work permit required" as a green light. This is why the UI quotes the sentence (`raw`, the `SalaryInfo.raw` shape) instead of asserting a verdict, and why the copy never implies the list is complete: **precision is high, recall is roughly a third to a half**.
- **Every Tier-1 rule needs a false-positive guard, and the ones without them shipped green.** An adversarial review found eight, each hiding a real job: a bare clearance vocabulary with no polarity check, so "a security clearance is **not** required" — the sentence a commercial US team writes to welcome international candidates — blocked; `public trust` / `top secret` / `federal contract` matching ordinary prose; `<PLACE>-based **employees**` matching the BENEFITS clause that proves global hiring ("US-based employees are eligible for our 401(k); employees elsewhere receive a local equivalent"), so the person words are now `candidates|applicants` only; a bare `registered to employ in` matching an employer-of-record's *reach* statement; relocation assistance suppressing the whole `work_auth` family, so a benefits paragraph cancelled a real sponsorship refusal; `GCC` read as the Gulf Cooperation Council in "systems based on GCC"; `raw` head-sliced so the quote could omit the phrase that fired; and — worst — **R0 reading an Israel-ONLY posting as excluding Israel** ("unable to employ candidates *outside of* Israel"), deleting the single most desirable posting category for this user. Each is now pinned beside the positive it must still catch, in the same `check()`.
- **Order is the algorithm** (`_strip_boilerplate` → Israel-ONLY veto → R0 Israel-excluded → R1 Israel-open → suppressors → Tier 1 → Tier 2), and three guards in it are counter-intuitive enough to be worth naming. The US **EEO block ships on ~100% of US postings and contains "citizenship status"**, so it is truncated first — pinned in BOTH directions, since suppressing it is trivially satisfied by truncating everything. **Hebrew** Israel tokens match as bare substrings, never ``: `re.search(r"ישראל", "…בישראל…")` is `False` because ב/ל/ה/ו/מ/ש are word characters — the Python twin of check-mirrors check 10. The **Latin** ones must have the boundary, and that asymmetry is load-bearing in the other direction: `lod` (Lod) is a substring of *lodging*, *exploded* and *melody*, and one hit clears the posting outright, so a US-only ad whose benefits mentioned lodging was unclassifiable. And **a suppressor only suppresses when nothing negates it**: "No visa sponsorship **is available**" contains the allow phrase verbatim, so a bare match reads the commonest US-only phrasing exactly backwards.
- **Deliberately absent, each for a stated reason.** No timezone rules — Israel is UTC+2/+3 inside any ±2/±3 CET window, and a schedule constraint is not a legal one. No Hebrew restriction patterns — the worldwide pass is LinkedIn-only and LinkedIn hits are `language="en"`, so they would buy zero recall while `אזרחות ישראלית` and `סיווג ביטחוני` are INCLUSION signals wearing exclusion grammar; Hebrew appears only as an openness clear. No `EMEA`/`Middle East`/`MENA`/`EU or associated country` in the region table — **Israel is inside all four**, and firing there inverts the verdict. No JSON-LD `applicantLocationRequirements` — LinkedIn emits none on either reachable surface. No backfill of the freed slots in v1: the shortfall is reported instead, and the two-round variant would break `fetch_locks`, `matches_by_hit` and the SSE `total` all at once.
- **`SearchContext` gained no field and there is no checkbox.** It is serialised into `job_alerts.context_json` and fed straight to the cron, so a new field with a hiding default silently changes every saved alert on deploy; it also has three traps invisible to `tsc` and to all ten check-mirrors checks (`contextKey` in `jobs/shared.ts`, the hand-written per-field copy block in `_resolve_context`, and three hand-built literals). The reveal is client-side ephemeral state, reset per result.

- **Two numbers on two clocks, never a blended one.** Keyword coverage is live and deterministic; recruiter fit is ONE timestamped model reading with no before/after, because two samples at `temperature=0.3` are not a measurement of improvement. `overall` (`0.5*coverage + 0.5*fit`) is off the live surface entirely — half of it is stale by construction. It still exists on the type and in the tracker, where historical rows were scored that way.
- **Deterministic routes stay uncapped and smoke-pinned**: `/render`, `/tools/ats-scan`, `/tools/ats-xray`, `/tools/page-count`, `/tools/coverage`. **`/tools/coverage` AND `/tools/ats-scan` take `jd: JDModel`, never `jd_text`** — a route that accepted job-ad text would have to reach the model to use it, and an uncapped door onto the model is the thing that rule exists to prevent. Both pinned at 422.
  `/tools/ats-scan` broke that rule until 22.10 and is the case worth remembering: it carried **no `Depends` at all** while `jd_text` flowed into `analyze_jd`, so anyone past the shared access-code gate spent the account's OpenAI budget with no cap and no token row — thirty lines above the docstring stating the rule. Its guard could not fail in either direction: it posted `jd_text: ""`, the one value that never enters the branch, under a label asserting the route calls no model. Behaviour alone still cannot pin this (a re-introduced analyser also returns 200, there being no cap to trip), so the **shape** (`jd_text` → 422, via `extra="forbid"`) and the **source** (the module is grepped for the analyser and the client factory) are pinned too. `extra="forbid"` is load-bearing on its own: without it a stale caller gets a silent format-only scan and a coverage number that quietly became zero.
- **Saving the master is EXPLICIT, never automatic**, until three backend fixes land: version snapshots are per changed PUT with only 20 slots per (user, language) — 21 saves evict the uploaded original; `PUT /profile/resume` picks its row by *detected language* and carries no id, so one Hebrew word saves over the other-language CV; and there is no conflict check at any layer. Saving must also **omit the ledger** (the backend rebuilds it — the user typed these facts) and call **`resetMasterCache()`**, because `invalidateData` cannot reach `useMasterResume`'s module-level binding and nine pages read the master from it.
- **`useSaveMasterResume` swallows every error and returns `null`.** Correct for its documented best-effort use; never use it behind a Save button. It also only toasts on SUCCESS, so both upload paths must handle `null` themselves — without that, a failed save leaves the page showing a resume the server never stored and the next reload silently reverts it.
- **Every write to the master must invalidate BOTH caches.** `saveMasterResume` calls `invalidateData("master","masters")`, which clears the `dataCache` Map and *cannot* reach `useMasterResume`'s module-level `cache` binding. A caller therefore has to either call `resetMasterCache()` or push the new value through `setMaster` (which writes the binding). `TailorPage.onParsed` did neither: uploading a replacement on `/app` updated the backend while Jobs, Interview and every tool kept painting **and sending** the resume that upload had just replaced, until a full page reload. That is exactly the failure this rule was written for.
- **A replaced master resume must reach the DOCUMENT, not just the caches** (23.6). There are two module-level copies of the master — `useMasterResume`'s `cache` and `tailorStore`'s `resume` — and only the first had a way in from outside, because `TailorPage`'s loader early-returns the moment the second is set. So uploading a new CV on the Jobs page (Replace), restoring a version or saving from the skills editor left `/app` painting, TAILORING and downloading the file that had just been replaced, until a full page reload — reproduced in the browser with a no-reload sentinel, not reasoned about. `tailorStore.adoptMaster` is the one way in, and it is called from **inside `useMasterResume`'s `setMaster`**, not at the three call sites: every caller of `setMaster` is by definition a replacement of the stored master, so a fourth surface gets it for free instead of shipping the same bug again. `TailorPage.onParsed` routes through it too, so there is ONE definition of "a new master arrived" — the hand-written reset it replaced never cleared `fit` / `checkedFor` / `scoredAt`. It clears everything describing the resume being replaced (a fit reading, a tailor diff, a fabrication warning, the tracker row), clears the local draft — `draftOver` spreads the draft OVER the master, so an offered restore would undo the replacement the user just made — and bumps `seq`, cancelling an in-flight tailor whose base is gone. **The target job SURVIVES** (`jdText`, `jd`, `jobUrl`, `jobTitle`, `company`): which posting you are aiming at has nothing to do with which file your resume is in, and pressing Tailor straight afterwards on the NEW resume is the whole point. This makes `hooks/useMasterResume` ↔ `state/tailorStore` a cycle, on exactly the `api/client` terms already documented there — runtime-only calls, hoisted declarations. check-mirrors 12 pins all of it.
- **The Replace control lives on the document too** (23.6). `/app` offered the dropzone in its empty state and nowhere else, so the one page that IS the resume was the one page that could not change it — which is why the bug above was reached through the Jobs page at all. It rides `DocumentPanel`'s shared `tools` list (defined once, mounted twice — the phone row and the desktop rail, so it cannot exist in one viewport only) and is gated on `editable`, the same master ⇒ change it / tailored ⇒ review it rule as every other write on this surface. Its panel is an inline `Card` with `animate-fade-up` — never a height tween, for the reason check 11 exists.
- **A resume swap must not clear the search context.** `JobsPage.onResumeUploaded` used to `setCtx(null)` to drop a stale title prefill — but `ctx` also carries location, work mode, result count, boards, "posted within" and the worldwide opt-in, none of which depend on which file was uploaded. Wiping six user settings to freshen one derived field reads, correctly, as "replacing my resume deleted my search settings".
- **On the sheet, motion may only be CAUSED by a value the backend returned or an edit the user made.** Nothing on the paper moves on hover, on scroll, or on a timer. The document is the artefact the user is about to send, and motion on it reads as precision instrumentation only while it is tied to something real — a block accepting an edit, a coverage recompute, a measured page count. Tilt, spotlight, border-glow and weighted-card physics all exist elsewhere in this app and are all wrong here. A corollary with teeth: **never animate progress that is not being measured.** `POST /tailor` is a plain synchronous handler, so the text has fully arrived before the first character could be typed — a typewriter reveal would manufacture suspense over data already in memory. `ScanPanel` is the honest counter-example and the reason the rule is expressible: it streams real per-board rows off a real SSE stream.
- **A reveal animation must END on its resting state, not on nothing.** `styles.css` collapses every animation to `0.001ms` with one iteration under `prefers-reduced-motion`, which parks an element at its `to` state — so a highlight that faded out would leave a reduced-motion user with *no* indication at all. `block-settle` ends settled; `.paper-aurora` documents the same trap from the other direction.
- **A CSS animation restarts only when its NAME changes.** Spotlighting the same block twice running produces an identical class string, so the bloom silently would not replay. `block-settle` / `block-settle-alt` are byte-identical keyframes alternated by a nonce — and the nonce is also what restarts the 2200 ms window, since React bails on an identical state value and `setSpot(samePath)` was a no-op.
- **Never animate `height: "auto"` on a click-to-open element.** It wedges at `height: 0px` with the content present underneath — reproduced on a clean load, not reduced-motion, not HMR. `Disclosure` and `BlockEditSheet` both animate transform and opacity only.
- **`.sheet` is the document's palette; `.paper` is the marketing one.** Same mechanism (re-declare tokens on a subtree), different palettes and different reasons — `.paper` would paint every section heading the marketing violet, a colour no template draws.
- **Chrome follows the UI locale; the paper computes its OWN direction, and `dir="auto"` is never used on it.** `ResumeView` derives it from `resumeLanguage(resume)` — the same function both renderers use — and applies it to the sheet root AND to every editable node. Two distinct failures ride on this. Per-node: `auto` resolves from the first strong character, so a Hebrew bullet beginning "React…" flips LTR under the caret. Per-document: the root carried `dir="auto"` until 23.1, and the first strong character in tree order is `contact.name`, which `lib/lang.ts` deliberately **excludes** (mirroring `app/core/lang.py`) — so a Hebrew CV headed with a Latin-spelled name rendered **LTR on screen and RTL in the downloaded file**. Reproduced at the DOM level before it was changed.


### Phase 23.7 — the document is the template, and the tailored draft is editable

- **The document on `/app` is the THIRD renderer of `TemplateSpec`'s presentation vocabulary**, after `pdf_renderer` and `docx_renderer`, and it reads the same table they do — `lib/templateSpecs.ts`, pinned against `templates.py` by check-mirrors 23. Until 23.7 `ResumeView`'s Props had no `template` at all: `DocumentPanel` held the choice and passed it to `usePdfPreview`, `useXray`, both downloads and `XrayResult`, but not to the page the user edits on. So picking Executive gave a serif, cream, centred-name, split-entry PDF while the document on screen stayed sans, white, left-aligned, chipped and ruled — every other surface honoured the choice and the one the user works on did not. `tsc` was quiet because the prop is optional.
- **The mirror's defaults are PYTHON's defaults, and that is load-bearing.** `entry` defaults to `"split"` and `list_cols` to 1 in the dataclass while ten and eleven templates override them, so a mirror with defaults of its own is wrong on precisely the fields nobody wrote down. Two deliberate differences, both mechanical: colours carry a leading `#` (the comparator normalises), and `serif` is DERIVED from `pdf_family` — no face `templates.py` names can be web-loaded (`fonts.css` ships Inter + Heebo; Lato and Spectral are PDF-EMBEDDED), so the screen reproduces the serif/sans CATEGORY and the exact face stays the file's. A family in neither set THROWS rather than being sorted into sans.
- **The screen abstains IN WRITING from exactly four things, and each sentence appears only where it is TRUE of that template**: the exact typeface, the PDF's contact marks (the 21.8 ornament carve-out, plus one specific to this surface — an icon element inside a `contentEditable` contact block would be typed over), `layout="sidebar"`, and `footer_name` (the screen is one continuous sheet with no page boundaries to foot, and the Word file omits it too — see **The default template**). **No sidebar is drawn**: which sections land in the rail is a reportlab MEASUREMENT with a demote pass and an early-career carve-out, so a DOM guess would show sections the real file moved out — a new lie in the same class as the one this work fixes. Six of the twelve draw no contact marks, so that sentence is gated too: a note admitting to a difference that is not there is the same defect pointing the other way.
- **Per-template geometry is an inline `style` or a custom property, NEVER a computed class.** Tailwind generates utilities by SCANNING THE SOURCE, so an arbitrary-value class assembled at runtime resolves to nothing — it fails silently, in the browser, with a green build. The palette is an inline token block on `ResumeView`'s OWN root, never an edit to `.sheet`: `.sheet` is one palette for all eleven and also carries `color-scheme`, the scrollbar thumb and `--shadow-doc`, none of which has a spec twin. `surface="panel"` (the tracker's detail modal) passes no template and gets none of it.
- **A `header="band"` wrapper carries a SECOND token block, and `--accent` is the one that is easy to miss.** `blk()`'s hover tint and focus outline are the only thing on the paper that says a block is editable, and on modern's and panel's dark navy the sheet's own navy accent is invisible. `--ink-faint` is mixed from `band_meta` over `band_fill`: a token is three channels with no alpha, and `[data-ph]:empty::before` reads it — an absent phone number is discoverable ONLY through that placeholder.
- **The bullet glyph may not be an element.** That `<li>` IS the `contentEditable` node for `@exp.i.b.j`, so a glyph `<span>` would be typed over by the first edit. It is `list-style-type`, and **a string marker needs a trailing space in the string** — it is drawn exactly as written, with none of the gap `disc` gets for free, so `executive` rendered "—Rebuilt the settlement…".
- **Editing a TAILORED document is an override layer keyed by SOURCE ANCHOR, never by block path.** Block paths are not stable: a rejected removal splices the entry back and shifts every later index, so `@exp.1` is one job with nothing rejected and a different job once a removal is declined — proven by bundling and executing the shipped `resumeDiff.ts`. A path-keyed override therefore writes the user's typed sentence onto a DIFFERENT bullet. Edit ids are stable and `resumeDiff` says so, so the merge emits a parallel `sources` map and the overrides are keyed by that.
- **`setBlockOverride` sets ONLY `tailorOverrides`.** Never `resume`, never `editUndo`, and never `writeDraft` — the local draft mirrors the MASTER and `draftOver` spreads it over the master, so an application-only edit reaching it would have `DraftRestoreBar` offer to restore a tailored CV as the user's real one. `applyBlockEdit` must never be reached from the tailored path: it nulls `result`, `tailoredFrom` and `rejectedEdits`, so one keystroke through it destroys the whole review.
- **An override OUTRANKS the accept/decline decision for its block, and toggling that decision is the only thing that discards it — explicitly.** If a later Decline silently replaced the user's typing, the app deleted text the user wrote; if the override silently won while Accept/Decline stayed live, the control would do nothing. So the row offers two labelled buttons instead, each of which clears the override AND sets the decision in one tap. An override whose anchor resolves to no path is KEPT, not deleted, and re-applies if the anchor comes back.
- **Only a WHOLE-ENTRY edit owns its subtree, and `editAnchors[id] === id` is the discriminator.** An entry-level SCALAR edit (`exp.0.title`) is anchored to the ENTRY, so an ungated prefix walk made the row about a job TITLE own every hand-edit on that job's bullets — the title change became undecidable behind a "Yours" badge, and both of that row's buttons cleared the bullet override, so one tap silently deleted a sentence typed on a different line. Only `editSrc(id, id)` at the add/remove sites registers an edit under its own id, so that identity IS "this edit is the whole entry".
- **A fabrication flag is resolved against the DOCUMENT, never against the decision.** `rejected.has(id)` was sound only while rejecting was the only way to change a line: the guard flags a value BECAUSE it is not in the original, so putting the original back removed it. A rejection and an override can now stand on the same block and overrides apply LAST, so the override won the paper while the rejection won the flag row — the panel went mint and said "All flagged claims resolved" while the invented number shipped. The containment search covers the block's SUBTREE: an added ENTRY anchors to its META path, whose fields are title/employer/dates, while the edit's text folds the entry's BULLETS in.
- **The guard's verdict describes `result.tailored_resume`, not the document on screen.** Coverage and the page count move on a hand-edit (both are live and deterministic); `fit_score` and `fabrication_flags` do not. So once any override stands, the score tile drops its mint stamp and names the exception, and the tracker row sends `fabrication_flag_count` as UNKNOWN rather than a number — a row that predates a reading means unknown, never zero.
- **Adds stay master-only on a tailored draft.** A claim typed in afterwards carries no fabrication-guard verdict while `ScoreCard` keeps rendering `result.fabrication_flags` beside it.
- **There must always be a way OUT of review mode.** `editable = !result && !!resume` gates editing AND the Replace tool, and nothing set `result` back to null — so tailoring once locked the page into read-only for the rest of the session short of a full reload. `discardTailorResult` is that exit, and it is why "just hide the Tailor button while a result is up" is the wrong fix: it would remove the last control on the surface. Both exits that destroy hand-edits arm-then-confirm and state the cost AT REST.
- **`startTailor`'s reset is `adoptMaster`'s minus the six master-identity keys**, and check-mirrors 13 DERIVES that list from `adoptMaster` so a field added there forces a decision here. It used to leave `savedAppId` set, so after a re-tailor `save()` short-circuited and toasted "Already in your tracker" while the row still held the PREVIOUS tailored resume. With a result up the overlay opens EMPTY: its cached panel measures the MASTER, and painting that beside `ScoreCard`'s tailored reading is two unlabelled recruiter-fit rings for two different documents.

### Keyword preservation — the floor under the tailor

- **The tailor deletes JD keywords the candidate genuinely has, and until 23.7 nothing repaired it.** `score_after` MEASURED the drop and reported it. Five independent mechanisms, four reproduced: the model's own skills shortlist (TAILOR rule 2 orders curation — "drop irrelevant noise", "DROP whole areas it never mentions" — and every one of those rules runs ONE WAY; the self-check verified output ⊆ original and nothing verified the reverse); `length_budget` removing the prose that carried the only occurrence; `cv_planner` dropping the carrier project before the budget runs; `drop_invented_roles` cutting a promoted row; and the humanizer, whose acceptance gate weighed fabrication, voice and pages but never coverage. Measured: coverage fell **60.0 → 40.0**, deleting Kubernetes and Terraform from a candidate who lists both. The prompt work and the humanizer gate narrow the two biggest mechanisms; neither is a guarantee — "the LLM is *asked* to curate, but asked is not guaranteed".
- **It may only ever write a string that already exists byte-for-byte in `original.skills`.** Never synthesizes, never adopts the JD's spelling for something the candidate lacks, never writes prose. A keyword whose only home was a sentence is REPORTED, never repaired: re-inserting a sentence either duplicates a claim or grafts a token into the model's own prose, which the fabrication guard structurally cannot see. The argument is provable rather than argued — `build_facts_ledger` never reads `resume.skills`, so a restore cannot create a flag. **If anyone extends the guard to restore a bullet, that argument collapses and `check_fabrication` must be re-run for the restore too.**
- **A REPAIR IS NOT A MEASUREMENT.** Three functions, three jobs: `preserve_keywords` REPAIRS (its lists describe the resume IT returned, which the caller then trims), `lost_keywords` MEASURES (a rank comparison — no `model_copy`, no budget, no carrier search), and `report_restore` describes what SHIPPED, after the refit and the back-off. Driving the changelog off the repairer told two lies at once: "Put back: X" for keywords a later trim removed again, and — because the caller took only the repairer's *unrepairable* list — a keyword the refit deleted that the repairer had just proved it COULD restore landing in NEITHER list. Measured: 57 JD hard skills all in the master, 25 restored, 32 still lost, changelog naming 7.
- **One matcher, one answer, on BOTH sides of the trade.** `length_budget._drop_unmatched_skill` protects an entry when `scorer._keyword_present` reads it as carrying a JD keyword — the SAME call the carrier search selects with. It used to protect on whole-token overlap, which is a different question: every carrier matched through the substring branch — i.e. every Hebrew one, since ב/ל/ה/ו/מ/ש are word characters, and `Postgres` is inside `PostgreSQL` — shared no token with the JD and was fully eligible for a trim that removes the LONGEST unmatched entry. Measured on a Hebrew master: 10 carriers restored, 9 removed again under "dropped skills the job never asked for", the changelog still claiming they had been put back. **The honest guarantee is NOT "the budget cannot undo the restore":** the entries the guard writes are the entries the skills trim refuses to touch, and anything the budget removes anyway is REPORTED as `trimmed`, because the report is measured on what ships.
- **A keyword may not be bought with the page limit.** When the post-restore refit cannot get under `hard_max_pages` and the pre-restore CV was inside it, `shed_restored` hands entries back — longest first, stopping the moment the budget holds. `length_budget.OVERFLOW_NOTE` is public so that note can be RETRACTED when the back-off makes it false: a report carrying both "could not get below 3 pages" and a 3-page CV is worse than either. `shed_restored` takes its page measurement as a CALLABLE — the guard stays free of the renderer for the same reason it stays free of the LLM.
- **Four loss classes, because one sentence cannot be true of all of them.** `prose` (the original said it in wording this module does not rewrite), `partial` (the skills list holds part of the phrase; those entries ARE put back and the job's phrase still is not covered), `cap` (`MAX_RESTORED` spent — the only class a bigger number fixes) and `trimmed` (the page budget took it back — the only class WE caused rather than the user's wording).
- **The report goes through the CHANGELOG, never a new `TailorResult` field.** A changelog is a log of ACTIONS TAKEN, so its absence on a row written before this guard existed means "no such action", which is TRUE. A `kept_back: []` field would mean "nothing was lost" on every one of those rows, which is FALSE. "Put back:" names the ENTRIES, not the JD's phrase — they are different strings, and `REST APIs` restored from `['REST','APIs']` named something that appears nowhere in the shipped CV. The copy may never say "guaranteed", "verified" or "all keywords preserved" — smoke-pinned.
- **ONE call site, inside `tailor_resume`, and its POSITION is load-bearing.** After the humanizer (the last stage that can delete a keyword) and before `score_after`, so it describes the resume that ships. A second site would classify on a DIFFERENT gate and contradict this one about the same resume — the geo-restriction correction in a new costume. A smoke check walks every module under `app/` and asserts `core/tailor.py` is the only importer.
- **A source pin that greps cannot tell an import from a mention.** `keyword_guard` imports from `app.core.scorer`, and `scorer` imports `get_llm_client` — so appending `fit_score` to that existing import line puts the model in charge of the CV while every substring pin stays green. Both pins parse the AST: the imported-from-scorer set must be EXACTLY `_keyword_present`, `_resume_text`, `_tokens`.
- **It measures a WIDER set than the score does, deliberately.** `_jd_keywords` reads `hard_skills + keywords + preferred_skills`; `scorer.keyword_analysis` reads the first two. A preferred skill the candidate HAS and we deleted is still a deletion — but widening `keyword_analysis` would change the visible coverage denominator everywhere, a behaviour change with no defect behind it. The consequence to keep: a restored preferred-skill raises no visible number.
- **On a clean pair it returns the SAME OBJECT.** The caller keys the refit, the voice re-audit and the changelog entry off a non-empty `restored`, so the identity check pins all four at once.
- **`voice_report` describes what SHIPPED, so a restore forces a re-audit** — carrying the humanizer's `revised`/`fixed` across by hand, or the record of the only stage that rewrote anything is silently erased.

### The skills ceiling — the other half of the trade (2026-08-30)

- **`keyword_guard` is the floor; `app/core/skills_shortlist.py` is the ceiling, and they run one line apart in `tailor_resume` on purpose.** The floor guarantees a JD keyword the candidate's own skills list carried is not deleted; the ceiling guarantees the section is a shortlist rather than the master's inventory. Same matcher, adjacent call sites, so nothing between them can see a list only one of them has finished with. `resume_max_skills` (default 20) is the cap; `<= 0` disables it.
- **This is CODE because the prompt was measured and found insufficient — that is the whole justification.** The TAILOR prompt has always asked for "roughly 15-25 INDIVIDUAL skills". Measured on the owner's real 66-skill master across 6 real job ads × 3 reps × 2 independent runs (`tests/ab_tailor.py`): the shipped CV carried a **median of 63.5 skills — more than the master it was cut from** — at **18.6% precision**. Every other size promise in this pipeline is already code (`length_budget` guarantees the page count the prompt asks for; `keyword_guard` guarantees the keyword floor it asks for); this was the one the prompt asked for and no code made.
- **The result, paired per job over 12 job-pairs: 63.5 → 20 skills, better on 12 of 12; entries the job never names 48.5 → 7.5; precision 18.6% → 55.0%; and coverage, lost keywords, fabrication flags, voice score and page count ALL UNCHANGED** (coverage delta median 0.0, lost keywords tied 12/12). Five independently-designed prompt-only variants were measured beside it and **every one that cut the count paid for it in coverage** — up to −13.2 points, with `lost_keywords` going from 0 to 3.
- **The mechanism behind that, and it is the non-obvious finding: cutting the COUNT is free; banning RELOCATION is what costs keywords.** A skills entry absent from `master.skills` but present in the master's *prose* is the model moving a term the candidate demonstrates in a bullet up into the list — which is what keeps it on the page after the budget deletes the project that carried it. The correlation is exact across arms (−4 relocations → −13.2 coverage; −2 → −9.05; −1.5 → −3.85; 0 → +0). Any future prompt work here must leave relocation alone.
- **Three rules inside it, each avoiding a defect already paid for once.** It uses `scorer._keyword_present` — the same call `keyword_guard` picks carriers with and `length_budget._drop_unmatched_skill` protects entries with, so it cannot become a second opinion. **A `covered` entry is never dropped and neither is a restored carrier**, cap or no cap — a carrier for a multi-word keyword ranks `partial` on its own ("REST" against "REST APIs"), and evicting it would silently undo a restore the changelog then claims it made. And **the model's own order survives**, because the tailor is told to put JD-relevant entries first and does that well.
- **The cut is REPORTED in the changelog, never silent**, and by count plus a sample — the master's tail runs to forty entries and naming them all is the section over again, not a log.
- **`MAX_RESTORED` was never the cause, and the instrumentation is what proved it.** A probe recorded what the MODEL returned versus what `preserve_keywords` then added: the guard added **zero** on 18 of 18 runs. Lowering the constant would have changed nothing and re-opened the keyword-deletion defect. **Its contribution is inversely proportional to how well the model curates**, though — driven offline, a curated 20-entry list converges back to ~35 because the guard's fixed point on this master is 35 — so "the guard adds nothing" is true of the current model output and must not be read as a property of the guard.
- **A tailored CV is flat, and `ResumeModel`'s union validator has to be told so BEFORE it runs.** `tailor.py` strips `skill_groups` from the raw response whenever it carries both that and a flat list. Measured: 20 flat entries plus the real master's five groups validates to **66**, silently, with nothing reporting that the curation was reversed. The model complied on all 30 measured runs — but an instruction is not a guarantee, and when it fails it defeats every other thing that shortens this section. Both halves of the condition matter: a response with groups and no flat list has the union as its only content.
- **`ats_scan`'s skills verdict is two-sided, and only when there is a job to be two-sided about.** It used to return `severity="good"` for any count ≥ 5 with no upper bound, so a 79-skill tailored CV was told "79 skills listed: good" while the owner's complaint was that the section was overstuffed. The bound now exists **only when a JD is supplied**: a 66-skill master with no job attached is an inventory, which is what a master is FOR, and warning on it would be a guard firing on legitimate input. It REPLACES the count verdict rather than adding an issue — `format_health` is `good/len(issues)`, and whether the paper parses has nothing to do with which job it is aimed at.
- **The closed-set violation is a PROMPT fix, not a code one, and that asymmetry is measured.** The model mints skills the candidate never claimed — `Linux`, `Agile`, `ChatGPT`, `Slack`, `Jira`, `bash`, `AWS`/`GCP`/`Azure`, `gRPC`, `candidate sourcing` — all lifted from the job ad. `check_fabrication` does not read skills by design, and the shortlist cannot help: an imported JD term *is* JD-relevant, so a relevance trim keeps it preferentially. **A deterministic filter is also off the table**, and that was checked rather than assumed: no lexical rule separates an invented claim from a legitimate rewording. `LLMs` (master: "LLM cost optimization"), `prompting` ("prompt and system design") and `vector databases` (`pgvector`) all score as unsupported on a token test, and a looser stem test "justifies" `custom scripts` from *customer*. So the TAILOR prompt gained the anti-minting rule (2026-08-30): name the observed leaks, make the test a SEARCH of the original resume, and — the load-bearing half — **explicitly permit relocation**. Measured over 18 real-key runs per arm, unambiguous fabrications fell **0.78 → 0.22 per run (p = 0.0018** against the pooled control rate, two same-prompt arms giving 19 and 9 events per 18 runs**)**, at no measurable coverage cost and zero keyword regression.
- **THE CAP IS 30, NOT 20, AND THE STORY OF WHY IS THE MOST IMPORTANT THING IN THIS SECTION.** At 20 the shipped list filled with the model's JD-shaped PARAPHRASE — `orchestration patterns`, `tool use`, `feedback loops`, `unstructured data processing`, `software engineering` — and cut the candidate's actual toolchain: FastAPI, PostgreSQL, pgvector, RAG, embeddings, n8n, Vapi, MCP all absent from an AI-engineering application. **No metric here could see it, and one actively rewarded it**: `skills_precision` scores an entry as good when a JD term matches it, so a paraphrase derived from the ad counts as a win and `FastAPI` counts as noise. It read 18.6% → 55% while the document got worse. It was found by rendering the PDF and reading it — the repo's oldest lesson, arriving again.
  **Two fixes were tried and both are dead ends worth not repeating.** Re-ranking `shortlist_skills` to favour the candidate's own wording: three different rank rules produced **byte-identical output**, because the model front-ranks its own paraphrases, so its ordering and the JD-relevance ordering agree and no reordering can recover the toolchain. And a prompt arm telling the model to name the tool rather than describe the capability: on the job that motivated the whole investigation it changed **nothing** (own-wording 50% → 50%), and on the job where it did work it cost **30.7 coverage points**. Where it worked it hurt; where it was safe it did nothing.
  **Raising the cap is free, and that is provable rather than argued.** `shortlist_skills` never drops an entry the job named, so simulated against eighteen real 52-74 entry model outputs the JD coverage of the shipped list is **constant at 55.1 for every cap from 20 to 40** — a bigger cap can only add. Measured 20 → 30: own wording 72% → 82%, concrete tools 9.0 → 15.5, page count unchanged at 2, and still less than half the 66 that produced the original complaint. **A deterministic function applied to real recorded inputs IS a measurement**; it needed no further spend.
- **`skills_unowned` is a SCREEN, never a verdict** — the fabrication guard's own contract, one level down. It over-flags legitimate rewordings, so judge a prompt change on the DELTA between arms (the over-count is identical across arms and cancels) plus the unambiguous tool/platform names, never on the absolute number.
- **gpt-5.6-luna was measured and REJECTED — do not re-litigate it without new data.** It is 73% cheaper ($0.0084 vs $0.0314 per tailor), curates far better unprompted (returns 32 skills where gpt-5.4-mini returns 59) and mints **zero** unambiguous fabrications. It still loses: paired per-job coverage **−8.6 points** (outside the ±4.9 noise floor), `lost_keywords` 0 → 1, and **3.2× the latency (55.0 s vs 17.2 s per tailor)**. Coverage is the ATS gate on a job-application product, so a cheaper, cleaner model that costs keyword coverage is not a trade this app can take. The mechanism is the one already documented above: Luna relocates less (`skills_relocated` −2), and banning relocation is what costs coverage. Note also that OpenAI retired the mini/nano suffixes — Luna is priced at the old *nano* point and Terra, the balanced tier, is **2.7× dearer than gpt-5.4-mini**, so there is no like-for-like successor. The open idea worth measuring is **per-task routing**: TAILOR is the call that needs instruction-following, while FIT_SCORE and PLAN_CV are mechanical and could run on the cheap tier.
- **The prompt's apparent self-contradiction about the skills count is LOAD-BEARING. Do not "tidy" it.** Strategy rule 2 still says "roughly 15-25 INDIVIDUAL skills — plus however many more it takes" and "This OUTRANKS the shortlist length below", while `skills_shortlist` hard-caps at 20. That reads like stale documentation of behaviour the code now overrides, and removing it is the obvious cleanup. **It was measured, and it makes the CV worse.** Deleting the escape hatch and the OUTRANKS sentence — and telling the model a deterministic pass would cut the list, so it should rank honestly and stop — did exactly what it was supposed to on its own terms: the model returned **66 → 48.5** skills. But `skills_precision` fell **52.5 → 32.5** and `n_projects` fell by **1.5**, because the trim selects the best 20 *out of what the model returns, in the model's own order* — so a shorter, earlier-truncated list gives it fewer good candidates to choose from. **Over-production plus deterministic selection beats self-restraint.** The arm was rejected against a decision rule written down before the data ("ship only if precision does not fall"), and the variant is kept at `tests/fixtures/ab/variants/rule2.txt` so the next person can re-run it rather than re-derive it.
- **`cv_planner`'s project count varies run to run, TWO prompt fixes were measured, and BOTH made it worse.** The rubric says "There is NO fixed number", which is the same open-ended shape that let the skills list reach 59, and the planner picked 3, 3 and 7 projects on three identical runs of one job. **Calibrate that before acting on it: 3/3/7 is the WORST job, not the typical one** — the median within-job spread is **1 project** (range 0-4), measured twice on separate rounds. Two arms were tried against a decision rule written before the data, TAILOR held byte-identical so the planner was the only variable: `planrank` (rank strictly, err generous, let the page budget cut — today's proven pattern applied to projects) took the spread **1 → 2** and cost 10 points of skills precision; `plananchor` (derive the count from the posting's distinct requirements, so the same posting yields the same number) breached no quality floor but took the spread **1 → 3**. Neither shipped. Both variants are kept at `tests/fixtures/ab/variants/plan{rank,anchor}.plan.txt`. The lesson is the one this whole phase keeps teaching: **a prompt instruction about a COUNT is weakly followed, whatever shape it takes** — and unlike skills, project selection is judgement, so the deterministic answer that worked there would be worse here. Treat the residual spread as accepted, not open.
- **Trimming BEFORE the page budget does not buy projects back — refuted, don't retry it.** The theory was sound (the budget keeps 8 projects at 10 skills and 4 at 66, at a constant 2 pages, so the bloat is billed to the project list) but the measured paired delta on `n_projects` was **−0.5 [−3..+2]**, i.e. nothing. The shipped placement — after `preserve_keywords`, before `report_restore` — stands.

### What using the app found (2026-08-31) — and four measured dead ends

Phase 24's "next up" opened with **USE THE APP**. Two real tailors were run on the
real key, rendered, and read. Everything below came out of reading four pages;
none of it was visible to any metric the app records.

- **A skill could be drawn twice, and a duplicate bought a free cap slot.** 3 of 12
  real-key runs returned the same entry twice and every one shipped — `skill_blocks`
  hands the flat list straight to both renderers. `ResumeModel`'s union validator
  cannot see it (it dedupes what it ADDS from `skill_groups` and seeds `seen` FROM
  the flat list), and `shortlist_skills` counts the cap against a SET while emitting
  a LIST, so cap 30 shipped 31 and 32. `skills.dedupe_skills` fixes it — **not** in a
  `model_validator`, for the reason the multi-skill splitter documents one door
  over. **There are TWO doors, and the second was found by review after the first
  shipped**: `humanizer.py` validates its own raw HUMANIZE payload and
  `tailor_resume` ACCEPTS it after the first dedupe has already run. The humanizer
  is pointed straight at this list (`voice_audit` scans the joined skills for
  banned phrases), so it rewords entries routinely and two rewordings colliding on
  one string IS the duplicate. Patch `humanizer.get_llm_client` to drive it —
  patching the caller's binding is a no-op that reads as a pass.
- **THE CANDIDATE'S OWN WORDS LEAD THE SKILLS SECTION; THE AD'S FOLLOW.**
  `skills_shortlist.order_skills`, a stable partition applied last. **This replaces
  the old "the model's own order survives" rule**, whose premise — that the tailor
  "puts the JD-relevant entries first and does that well" — a rendered page
  falsifies: what it puts first is the ad's vocabulary. Measured on a real AI-
  engineering tailor, the first twelve chips were `workflow automation`, `LLM
  systems`, `retrieval`, `tool use`, `orchestration patterns`… — ten of thirty
  entries absent from the candidate's own 66 — with OpenAI, RAG, pgvector, MCP and
  FastAPI in the tail. **It is a PARTITION, never a re-sort**, and the model's
  ranking survives inside each group. **It is NOT free, and the claim that it was
  is the one this work got wrong** — caught in review, before deploy.
  `scorer._resume_text` joins skills with a SPACE and `_keyword_present` tries the
  verbatim phrase FIRST, so a multi-word JD keyword can match ACROSS the join
  between two adjacent entries, and Hebrew's ב/ל/ה/ו/מ/ש prefixes stop the token
  fallback rescuing it: measured, the same set reordered scores **100.0 then 50.0**
  against `פייתון מתקדם` — in the primary market. `_Chips._pack` also fills rows by
  WIDTH, so a reorder repacks the section and can change its rendered height after
  the page budget has signed the CV off. **`tailor_resume` therefore measures
  coverage and the page count either side of the reorder and keeps the old order
  unless the new one is free** — the guarantee is enforced, not argued, in the
  humanizer's acceptance-gate shape. Judged the only way a presentation change can be — three
  orderings of the identical set rendered and read side by side.
- **A changelog may not describe a document that does not exist.** That entry made
  three claims and two were false: "Cut the skills list to the 30 this job asks for"
  (the cap keeps the top N by relevance — the app's own `ats_scan` said 19 of those
  30 are not mentioned by the posting), and "Your master resume lists 75 skills"
  (75 is what the MODEL returned; the master lists 66). Its "stay in your master
  resume" sample was drawn from `dropped_noise`, which contains the model's own
  inventions, so it could promise `orchestration patterns` was in the master.

**Four dead ends, each measured, so they are not retried.**

- **The shortlist cannot be re-ranked into fixing the paraphrase problem.** Over 153
  recorded model outputs at cap 30: an own-wording FILL changes 8/153 outputs and
  buys nothing (this reproduces the earlier "byte-identical" finding and explains
  it — the fill is not where the paraphrase lives). Letting the cap EVICT covered
  entries that are the model's wording buys +3 own entries and +1 toolchain entry
  for **−8.5 median and −56.0 worst-job** coverage. Raising the cap is free on
  coverage (flat at every cap 20→45, confirming the earlier result) but buys only
  +1 toolchain entry per +6 chips. **The paraphrase is `covered` BECAUSE it is
  verbatim from the ad**, so any relevance ranking must rank it top — which is why
  the fix is ordering, not selection.
- **A deterministic minting screen tops out at 53% precision — a warning wrong half
  the time, so it is off the table as an advisory as well as a filter.** This is
  CLAUDE.md's earlier "checked rather than assumed" claim, now with a number. The
  best rule found (bounded matching, plural folding, stem comparison, compound-head
  so `vector` ⊂ `pgvector` clears) catches every invention CLAUDE.md names and
  clears every rewording it names — and still flags `Git`, `SQL`, `retrieval`,
  `observability` and `debugging`, all things the candidate genuinely does. Two
  traps worth keeping: the "master token inside the entry" direction is the
  dangerous one (`form` from "form submissions" clears **Terraform**; `gpt` clears
  **ChatGPT**), and a ≥4-character guard is the only reason `SQL` fails.
- **Naming a leak more precisely in the prompt did not help, and may backfire.** The
  `nomint2` arm (36 real runs, decision rule written first, kept at
  `tests/fixtures/ab/decision-nomint2.md`) targeted two classes the current rule
  does not name — regulatory marks (`CE`/`FCC`/`UL`) and requirement fragments
  (`modern programming language`, `open-source technologies`). REJECTED on 3 of 6
  criteria. `skills_unowned` was unmoved (1.39 → 1.22/run, inside noise) and one job
  lost 10.4 coverage points. **The result worth keeping is the backfire**: on class B
  the arm went BACKWARDS — `open-source technologies` shipped in 1/3 baseline runs
  and **3/3** nomint2 runs. Naming a string that is ALSO a verbatim JD keyword puts
  it in front of the model twice. The existing rule gets away with naming leaks
  because those strings are not in the ad being tailored against.
- **`CE`/`FCC`/`UL` is intermittent, and one rendered page is not a rate.** Three
  hardware-compliance marks shipped onto a Senior Quality Engineer CV — all verbatim
  `jd.hard_skills`, on a candidate who has never done compliance work. The chain:
  the model mints them, `shortlist_skills.relevance` ranks them `covered` (the JD
  names them, so they match themselves), a covered entry is never dropped, and
  `check_fabrication` does not read skills by design — **nothing in the pipeline can
  remove a JD-derived fabrication, and the ceiling actively protects it.** But six
  further runs of the same job across two arms produced **zero** occurrences, so at
  n=3 per arm there was no power to measure a change in it. Order it after the
  measurable work; the ordering partition at least puts it last on the page.

**Per-task model routing (PLAN 24 item 3) is REJECTED for `PLAN_CV` and blocked for
`FIT_SCORE`.** FIT_SCORE + PLAN_CV are **56.8% of prompt volume**, so the saving is
real (~$0.0021 of a $0.0051 tailor). But the latency was never measured per task,
and the 3.2× figure came from TAILOR alone: measured directly, **PLAN_CV is 4.22×
slower on gpt-5.6-luna** (2.55 s → 10.79 s) and FIT_SCORE 1.81×. Pool 1's wall time
is `max(FIT_SCORE, PLAN_CV)`, so routing both adds **+8.2 s to save $0.002**.
Routing FIT_SCORE alone costs +0.23 s and is plausible — but `metering` carries no
model dimension (`usage_log` folds everything into one `action="tokens"` row per
user per day), so a mixed run blends two price tiers with nothing recording the
split, and the saving would be unverifiable the moment it shipped. Add the
dimension first. Note also that one `OpenAIClient` per process means **one
`_unsupported` probe set**: two models through one instance would let a cheap
model's rejected `temperature` silently strip it from every TAILOR call.

### Skills are terms, not sentences

- **Splitting a multi-skill entry happens at ONE server-side door — `structure_resume` — and never in a `model_validator`.** A CV that writes "Python, SQL, Go" on one line arrives from the LLM as a SINGLE skill: one chip on the page, one keyword to the scorer, one fact to the x-ray. A validator runs on every construction, i.e. every READ of every stored master, tracker resume, saved kit and version snapshot, so it would rewrite all of them without any of them being a write — bypassing `resume_versions.snapshot` and breaking its byte-identical dedupe, so the first save after deploy burns an undo slot on a no-op. It would also fire between `original` and `tailored` inside `TailorResult`, orphaning the frontend's text-derived `@skills.<key>` anchors. Pinned three ways, because no one of them is enough: the flat-only form is asserted to DO resurrect, `app/models` is grepped, and a stored resume is PUT and read back verbatim — the grep cannot see an INLINE COPY of the splitter, and the round trip cannot tell a correct door from a validator that happens to agree with it.
- **The separator set is comma, semicolon, pipe, middot, bullet, newline and tab — and every omission is a guard that would fire on legitimate input.** `/` — the master holds `CI/CD`, `TCP/IP`, `A/B testing`, and splitting also drops `CI` under the x-ray's `_MIN_FACT = 3`, so BOTH halves vanish from coverage. `" and "` — `prompt and system design`, `evaluation and fallback handling`, `RTL and i18n` are three real entries, each ONE skill. Hebrew's vav is an inseparable prefix orthographically identical to a word-initial vav (the Python twin of check-mirrors 10), so that rule shreds `פיתוח ווב`, `עריכת וידאו`, `ולידציה`. The false-positive table sits in the SAME check as the positive, because "split multi-skill entries" is trivially satisfied by splitting on everything.
- **A separator inside brackets or quotes is not a separator.** `Cloud (AWS, GCP)` is one skill the user typed, and the splitter wrote `Cloud (AWS` and `GCP)` — unbalanced fragments nobody typed — into the master resume and the downloaded PDF, at the one door that parses the user's own CV. A depth counter over brackets and DOUBLE quotes fixes it. The apostrophe is deliberately NOT a delimiter: `Bachelor's` would open a run that never closes and suppress every separator after it in the same entry. Hebrew's geresh and gershayim are absent for the same reason — they sit INSIDE words (ד״ר, צה״ל).
- **There is NO length cap on a skill, in characters or in bytes.** A skill is the user's own text, so "never truncate the user's own document" applies verbatim: a separator-free entry passes through unchanged however long. `_Chips` wraps it and `ats_scan`'s twelfth check reports it; neither shortens it. The bytes-not-characters rule is scoped to PROMPT bounds where the quantity is tokens; for a DISPLAY limit the physical quantity is rendered width in POINTS and bytes are actively wrong — measured, the `split` rail holds 27 lowercase Latin characters, 16 capital M's and 28 Hebrew ones, so a byte cap would hand the primary market half the room it has earned.
- **A chip may not be wider than its column, and `_Chips` enforces it by reusing `_wrap_lines`.** `_pack` broke to a new row only when the row was already non-empty, so a lone over-wide item was admitted unconditionally and `wrap()` reported the column width regardless — reportlab believed it fit and nothing clipped. Measured on `split`: a 60-character skill drew 326pt past its column, straight across the main text, and because it overprinted the section heading at the same y, `'EXPERIENCE' in extract_text(...)` was **False** — one long skill deleted a standard section name from the file we tell the user is ATS-safe. The wrapped chip applies `_visual()` PER LINE after logical wrapping, and `split()` accumulates per-row heights. Pinned on GEOMETRY, not text: pdfplumber returns Hebrew already bidi-reordered, so a text-matching check passes by never firing in RTL.

Change one without the other and they overlap. Splitting them into components is the refactor that silently unguards the nav.

With a leading dot every wrapped line opened with "· ", which reads as a bullet list rather than a separator — seen on the real document at a 390 px viewport, not reasoned about.

A duplicate returns the resume **unchanged** (identity-compared by the caller), because adding a skill you already have is not an edit and must not burn an undo slot.
- **The add-skill chip is an `<input>`, and it must carry no `data-block`.** `ResumeView`'s five delegated root handlers key off `el.isContentEditable` and `closest("[data-block]")`, and an input that matches neither is invisible to all of them — including `onKeyDown`, whose `preventDefault` on `" "` runs only AFTER its path lookup, so the space bar survives. A `contentEditable` chip would need `stopPropagation` in four places instead.
- **An ENTRY is removable through the panel, never through the inline path.** `BlockEditSheet` gates Remove on `draft.removable || isEntryKind(draft.kind)`; `removable` stays FALSE for entries so the empty-means-remove rule cannot reach them. Gating on `removable` alone is what left `removeBlock`'s `RE_ENTRY` branch unreachable — a job, project, degree or service could not be deleted at all.
- **`DocumentTools` is one list mounted twice** — a sticky icon rail beside the sheet from `lg`, a scrolling labelled row below it. `display:none` removes the hidden copy from the accessibility tree, so there is no duplicate-control problem. Same reasoning as the old shared `SidebarBody`.
- **The template picker lives on the document, not inside the tailor result.** It governs the on-screen preview, the PDF preview, the ATS x-ray and both downloads at all times. While it was gated behind `result`, the file and ats views silently rendered whatever `template` state happened to be.
- **Two ways out, and they are not the same.** `DELETE /profile/data` wipes content and leaves the access code and the sign-in working; `DELETE /profile/account` wipes the same rows, deactivates the user and (since Phase 29) deletes the sign-in address, its tokens and every session. The Settings danger zone shows each action's consequence **at rest**, not only after arming — two destructive labels differing by three words cannot be told apart otherwise, and "read what it admits to once armed" is the wrong order for an irreversible action.

- The fabrication guard runs **after** every tailor call, not just in tests. If the LLM invents an employer/title/date/credential/number, the API still returns it but `fabrication_flags` will be non-empty. The UI surfaces these as warnings. Numbers are read from experience, military, the summary **and projects** — projects were missing until Phase 20 and the gap was invisible precisely because it was symmetric (the guard rebuilds the ledger the same way from the tailored resume, so nothing ever went red). Skills are still deliberately unguarded: the tailor is explicitly allowed to adopt the JD's wording for something the candidate has, so a strict check would false-positive on exactly that.
- **The ATS X-ray shows rather than asserts** (`app/core/ats_xray.py`, `POST /tools/ats-xray`, `/tools/xray`). Every competitor *claims* its templates are ATS-safe; we own both the renderer and a parser, so the tool renders the file the user would actually send and re-reads it with `resume_parser.extract_text`, then marks every protected fact `clean` / `split` / `polluted` / `missing` and prints the parser's verbatim text. It is deterministic — no LLM, no network — which is why the route is uncapped.
  Two things keep it honest, and both are smoke-pinned. **The false-positive pin:** no single-column template may ever report pollution. A guard that fires on clean input teaches users to ignore it, and the naive version did exactly that — a headline reading "Senior Backend Engineer · Distributed Systems" contains the *skill* "Distributed Systems" because the candidate wrote it there. Pollution therefore has a required SHAPE (`_collision`): the sidebar value must sit at one END of the line, because extraction fuses columns end-to-end, and the header block is excluded outright since it spans both columns. **The true-positive pin** uses its own fixture: interleaving is content-dependent — it needs sidebar content at the same height as a main-column entry — and the shared `resume` fixture happens to produce none, so a check written against it would have passed by never firing.
- **A template must differ from the others in SHAPE, not in hue.** The original five were one document in five colours, and that — not any single element — is what made the downloads read as undesigned. `TemplateSpec` therefore carries a presentation vocabulary (`header`, `heading`, `entry`, `skills`, `list_cols`, `rail`, `layout`, `page_bg`, `bullet_glyph`) and every option in it is reproducible in **both** renderers, so the two downloads can never disagree about what the document SAYS: a filled band is paragraph shading (`w:shd`) in DOCX, an accent bar is a left paragraph border (`w:pBdr`), a chip is a bordered run (`w:bdr`). None of them needs a table. A smoke check asserts the set stays structurally diverse, and another asserts no template ships a heading smaller than its own body text (the original five did — 9.5pt headings over 10.2pt body).
  **The one carve-out is `contact_icons` / `date_icon` (21.8), and it is a carve-out for ORNAMENT, never for layout.** The PDF draws small vector marks on the contact row; the DOCX draws none and renders the same document without them. There is no honest DOCX twin: `w:drawing`, `w:pict` and `graphicData` are the drawing objects the ATS rules forbid, and a unicode dingbat prints tofu in Calibri *and* lands in the extracted text right beside the email address. The omission is safe because an icon **carries no text and its absence changes no content** — the two files still say the same words in the same order, which is the property the rule above actually protects. A layout option that differed would change what the document says, and none of those may. Two smoke checks hold the line: the icon template's DOCX is **byte-identical** to an icons-off twin, and its PDF's extracted text is byte-identical to the same twin's.
- ATS rendering rules are enforced in both renderers: no tables, no text-boxes, no images, no Word header/footer, standard section names (`render/labels.py` — two sets, and `standard` prints the longer one at the owner's explicit request; the ATS note is recorded at that file). Everything that makes the download *look* designed is achieved without breaking those rules — hairlines are paragraph borders, flush-right dates are a tab stop (DOCX) or a drawn string (PDF), letter-spacing is small enough that extractors still read whole words, and the contact icons are drawn paths (a stroked vector is not an image, carries no text, and nothing has to un-pick it). The smoke test pins all of it.
### The default template — a reproduction, not a design (2026-09-06)

- **`standard` is `DEFAULT_TEMPLATE`, and it is a COPY of a real document**: the CV
  the owner actually applies with. Every number in it was measured off that file
  and the render was checked back against it line for line — the summary, the four
  skills groups, both roles and every bullet break at the same word, with
  cumulative vertical drift under 4pt across page 1. It is the only entry in the
  registry that is a reproduction rather than a design of ours, so "tidying" a
  value in it is changing the document, not the code.
- **Three grammars exist FOR it, and each is declarative.** `entry="run"` (title |
  employer bold, then location | dates italic, on ONE wrapping line — and the one
  entry style that can absorb a `detail` inline, which is what education's course
  list is), `skills="labeled"` (the group label bold and inline ahead of its own
  comma-joined items — same text and the same commas as `"inline"`, so a keyword
  parser splits it identically), and `label_set` (the longer business wording).
  Sixteen new `TemplateSpec` fields carry the rest; every one defaults to today's
  behaviour, so the other eleven templates render byte-identically.
- **`_RichText` is the flowable that makes `entry="run"` possible**, and it is the
  third case neither existing one covers: `_Text` wraps between words but is ONE
  style; `_Segments` mixes styles but treats every item as ATOMIC, so an item
  longer than the column draws past the margin. It **preserves whitespace
  exactly** — "  |  " and the three spaces before the italic tail are part of the
  design, and a tokeniser that normalised runs of spaces would quietly redesign
  the line. It follows `_Segments`' RTL contract, not `_Text`'s: each drawn piece
  is `_visual()`-reordered here and the pieces are laid out in reverse, so it
  draws with a raw `drawString` and must never route through `_draw_line`. And it
  `split()`s, because a labelled skills block on a 66-skill master is exactly the
  page-sized run that made `_Segments` and `_Chips` each ship a `LayoutError`.
- **THE BULLET DID NOT SURVIVE EXTRACTION, and that is the most important thing
  here.** `standard` asks for base-14 Helvetica deliberately — Arial and
  Liberation Sans metrics to the unit, which is what makes the line breaks match a
  document set in Liberation Sans, and no OFL face we could bundle reproduces
  those letterforms. reportlab encodes U+2022 as byte **0x7F**, one of the several
  slots Adobe's WinAnsiEncoding fills with `bullet`: it RENDERS correctly and
  every extractor using the plain WinAnsi table hands back `(cid:127)`. Measured
  on the first render: nine bullets, nine `(cid:127)`, on the one product whose
  promise is that the file parses. `_explicit_encoding` declares the encoding
  against **StandardEncoding** — that base is the whole mechanism, since reportlab
  only writes a `/Differences` array for slots that differ from the base — so the
  file states which character that byte is. **MacRomanEncoding also fixes the
  bullet and was measured and REJECTED**: no €, ½, ¼ or ×, and an unencodable
  character does not fail loudly — `unicode2T1` substitutes reportlab's notdef
  character, so "½ day" prints a letter nobody typed.
- **The page footer is the ONE place the PDF and the DOCX deliberately disagree,
  and it is NOT a fourth ornament carve-out.** Those three pass a test this one
  fails: an icon, a page tint and a rail dot carry NO TEXT, so their absence
  changes nothing the document SAYS. A footer is a word. Word can only repeat a
  line per page through a real `w:ftr`, which the ATS rules forbid and the smoke
  test pins. **The divergence is a user-made decision (2026-09-06), not one this
  code granted itself**, and `DocumentPanel` says so under the document.
- **`label_set="full"` was chosen over the standard short names, over the stated
  ATS objection**, and `labels.py` records that rather than re-arguing it: "Core
  Expertise" is not a heading a keyword parser is written to look for. Two of the
  long names are deliberately NOT verbatim copies of the source — it headed its
  projects "SELECTED AI SOLUTIONS & PRODUCTS", and a template cannot know the
  candidate's field, so the set carries the domain-free "Selected Projects".
- **Skills keep the master's headings through tailoring — DETERMINISTICALLY, after
  the fact, never by asking the model.** `tailor.py`'s strip stays, so not one of
  the thirteen measured prompt findings above is re-litigated.
  `skills.regroup_skills` files the entries that actually SHIPPED under the
  master's own labels in the master's own order; everything the master has never
  heard of lands in the trailing unlabelled block that `skill_blocks` already
  draws. **That block is the point**: it holds exactly the wording the model
  minted from the ad, which is where `order_skills` was pushing it anyway — so the
  two run as a FORK and never both. Reordering the same list twice would leave one
  of the two changelog entries describing an order the document does not have.
  Both go through the same acceptance gate `order_skills` already used (coverage
  must not fall, the page count must not grow), for the reasons recorded there.
- **`RenderRequest.template` defaulted to the literal `"classic"`** — the id that
  happened to be the default when it was written — so on the day `standard` took
  over, a client omitting the field kept downloading the old template while the
  preview beside it drew the new one. It is `""` now, like the six other request
  models that carry the field, and a smoke check reads the DEFAULT off every
  Pydantic model in `app.models` so a re-added literal cannot pass by equalling
  today's default.
- **Five page-budget checks went red, exactly as their own comment said they
  would.** Restoring 25 entries costs ~120pt under `skills="labeled"` and ~400pt
  under `skills="chips"`, so the fixtures stopped crossing the boundary they exist
  to cross. They are pinned to a NAMED template now (`_KG_TPL`) rather than
  retuned to a knife-edge the next change to the default would blunt again: the
  mechanism under test is the refit, which is template-independent.
- **Known and deliberately not reproduced**, each measured: the date range is an en
  dash where the source has a hyphen (the en dash is the correct range glyph and
  the app's convention across all twelve templates); a project's tech line has no
  field in `ResumeModel` to come from; and the entry, project and degree names are
  one size apart in the source (10 / 9.5 / 9) where `entry="run"` carries that
  hierarchy through a `bump` argument at the three call sites.

- **`ResumeModel.skills` is the flat surface everything SCORES; `skill_groups` is presentation.** The scorer's keyword coverage, the ATS scan, the ATS x-ray and resume health all read `skills` and none of them knows groups exist, so `skills` stays populated as the flat union of every group's items — enforced by a `model_validator` on `ResumeModel` rather than at each call site, because an LLM response, a stored JSON row and a test fixture all need the same guarantee. The validator only ever ADDS; the one place that removes a skill (`length_budget._drop_unmatched_skill`) drops it from its group too, or the union would resurrect it on the next round-trip and the trim would silently do nothing. Two consequences worth keeping: **nothing may be hidden** — a skill no group claims is still rendered, in a trailing unlabelled block, because an invisible skill is an x-ray "missing" on the file we told the user to send; and **group labels are not claims**, so the fabrication guard leaves them alone for exactly the reason it leaves skills alone. A tailored CV comes back from the MODEL flat — `tailor.py` strips `skill_groups` from the raw TAILOR response, for the measured reason recorded there — and is RE-GROUPED at the end of the pipeline by `skills.regroup_skills`, deterministically, under the master's own labels. See **The default template** below.
- `FactsLedger` is derived from the **original** resume (before tailoring) and is never mutated. It is the source of truth for the guard.
- `ResumeModel.headline` (the target-title line) is a **claim**, so the guard reads it — but only for rank. The ledger keeps `headlines` separate from `titles` on purpose: running the headline through the generic title diff would flag every honest reposition and teach users to ignore flags. Only a seniority word no real title carries is a fabrication.
- Tracker rows record what was sent (`template`, `voice_score`, `fabrication_flag_count`). All three are nullable/`""` — a row that predates the field means **unknown**, never zero, and the analytics drops it from that dimension instead of scoring it. When reading these off a stored kit, parse the RAW result JSON: validating through `TailorResult` silently substitutes schema defaults.
- **A ContextVar cannot be bound inside a FastAPI `yield` dependency.** FastAPI runs setup and teardown through `contextmanager_in_threadpool`, so they can land in different contexts: `reset()` raises `"Token was created in a different Context"`, and — worse — the endpoint never sees the value at all. Request-scoped state that the endpoint must read gets bound in **middleware** (one context for set and reset) and handed to dependencies via `request.state`. This is why `llm_metering` lives in `app/main.py` and not in `deps.py`.
- **A `ThreadPoolExecutor` worker starts from an EMPTY context.** Any pool whose work makes LLM calls must submit through `copy_context().run` or its tokens vanish silently — `job_search`'s scoring pool is the case that matters, since it is the biggest spender in the app. The tally is a mutable object precisely so a copied context still writes to the request's instance.
- **A search must survive one bad posting.** `_score_hit` never raises for a per-job problem: a failed fetch or a model error leaves that index `None` and lands in the existing `skipped` count. With up to 25 concurrent LLM calls per search, letting one propagate discarded 24 good results.
- **"Most recently updated" must be a TOTAL order, and the clock does not give one.** `_master_rows` sorts on `updated_at` alone and the column's `onupdate` reads the system clock — which ticks about every **15.6 ms on Windows**, so three consecutive `datetime.now()` calls return the identical value. Two saves inside one tick tied, and SQLite was then free to return them in either order: `GET /profile/resume` with no `lang` answered with whichever it liked, and the paired he/en master the user had just written was not necessarily the one they got back. It surfaced as a smoke check that was red on one run and green on the next — the shape of thing this repo's own note says never to re-run away. **A tiebreak in the `ORDER BY` cannot fix it**: `id` is creation order and the row being written is usually the OLDER one (the save upserts by language), so `id DESC` breaks the tie deterministically *wrong*. `save_master_resume` stamps `updated_at` one microsecond past the newest row for that user instead, and the pin FORCES the tie rather than waiting for one.
- **Overwriting the master resume snapshots it first** (`db/resume_versions.snapshot`, called from `PUT /profile/resume` and from restore). The dedupe compares the incoming content against the **current row**, not against the newest stored version — the latter looks right and lets an unchanged save through whenever the previous save did change something.
### The alert fit bar — "new" is necessary, not sufficient (2026-09-01)

- **The daily email used to carry every unseen posting the search returned**, which on a good morning is twenty jobs of which two are worth opening. `JobAlert.min_score` (default **75**, `0` = the old behaviour) is the bar; `alerts.above_min` applies it. 75 is not a new opinion — it is `KIT_DEFAULT_THRESHOLD` in `frontend/src/pages/jobs/kits.tsx`, so the email and the batch-tailor queue agree about which jobs clear it.
- **The bar filters the EMAIL, never the history, and the ORDER in `run_alert` is what enforces that** — it runs after `record_search_hits`. `job_search_hits` is what the History tab reads AND what `load_score_cache` reuses, so dropping below-bar rows would make every cron tick re-score them from scratch, which is the exact cost the cache exists to avoid. A posting hidden from the inbox is still one tap away in the app; a posting missing from history is one we deliberately lost. Smoke-pinned by asserting the below-bar URLs are no longer "new" on the next diff.
- **Compare on the DISPLAYED integer, not the raw float, and round it HALF-UP through `alerts.displayed_score`.** A posting at 74.6 renders as "75% fit" everywhere the user can see it, so a raw-float bar would have the History tab contradicting the email footer about the same job. One matcher, one answer, applied to the *displayed* value. **Python's built-in `round()` is half-to-EVEN and was the wrong tool** (fixed 2026-09-02): `round(74.5)` is 74 while `ProgressRing`'s `Math.round(74.5)` is 75, and `overall` is stored to one decimal (`round(0.5*cov + 0.5*fit, 1)`) so x.5 is reachable, not hypothetical — coverage 80.0 with fit 69.0 lands exactly there. The app painted "75% fit" on a job the 75%-bar email had silently dropped. `displayed_score` is `floor(x + 0.5)`; anything thresholding on a fit score the user can read goes through it. The old pins straddled the boundary (74.6 / 74.4) without ever landing on it, which is why this survived — the pin now uses 74.5 itself.
- **`KIT_DEFAULT_THRESHOLD` shares the number 75 with the alert bar, so the batch queue must threshold the same VALUE.** `kits.tsx` compared the raw float while the email compared a rounded one, so CLAUDE.md's own claim that "the email and the batch-tailor queue agree about which jobs clear it" was false across (74.5, 75.0). It is `Math.round(m.overall) >= threshold` now — sharing the constant is pointless if the two sides round differently.
- **`overall` is the right currency here even though it is off the tailor's live surface.** The "two numbers on two clocks" rule bans the blend where half of it is a stale before/after sample; in a search both halves are computed at the same moment against the same JD, and `overall` is what the search ranks by, what the card's ring shows, what the email prints and what the batch card thresholds on.
- **The footer names the RULE, never a held-back count.** The geo work already settled this for this email: "a number you cannot tap to reveal is a dead end in an inbox". "9 more were below your bar" invites a question the email cannot answer; "Only jobs at 75% fit or above — the rest are in your search history" explains the short list and says where the rest are. The filter stays OUT of `build_alert_email*`, which keeps both bodies pure functions of the list they are handed.
- **`new_count` and `above_min` are reported separately, and `last_above_min` is NULLABLE.** A run that finds 12 and emails 3 is working correctly and must not look like a broken search — but a run from *before* the bar never measured this, and a row that predates the field means **unknown, never zero**. `default=0` would have the ADD COLUMN shim backfill every historical row and the card assert "6 new jobs, 0 above your 75% bar" about a morning that had no bar — seen on the real page, which is why it is nullable. 0 stays a legitimate stored value ("it measured, none cleared"), so the two may not share a representation. Both halves are pinned.
- **`AlertSettingsIn.min_score` is `Optional[int] = None` meaning LEAVE UNCHANGED**, alone among that model's full-replace fields. A tab left open across a deploy PUTs the old field set, and for this one field that silently drops a user who chose 90 back to 75 and starts the mail again — the exact complaint the bar exists to fix. The client sends it explicitly, including `0`.
- **It is NOT a `SearchContext` field**, for the reason recorded in the geo section: that model is serialised into `job_alerts.context_json` and fed straight to the cron, and it carries three traps invisible to `tsc`. The bar is also not a search parameter — the interactive Jobs page still ranks and shows everything, because a list you are looking at with fit rings on it is not the same problem as an inbox.

- The alerts cron runs on a **wall-clock budget** (`ALERT_CRON_BUDGET_S`, under the 300 s platform ceiling) and orders users longest-unrun-first, so it degrades and reports `skipped` instead of being killed partway with the tail of the list silently never emailed. Check the budget *before* starting a user, never mid-run: an alert that already scraped and scored must finish and record its history, or the next tick redoes the work and calls the same postings "new".

### Has anyone actually opened it? (`users.last_seen_at`, 2026-09-02)

- **Nothing could answer "has this invitee ever used the app".** `usage_log` looked like the record and is not: `check_and_count` returns early for admins, so the owner's own row reads 0 searches and 0 tailors however heavy the use; and the deterministic routes (`/tools/*`, `/render`) are deliberately uncapped, so they write no row either. Web Analytics is off, and Vercel runtime logs retain roughly **three hours**. ### One clock, one frame — the "Posted N days ago" bug (2026-09-04)

- **The daily email aged every posting against the wrong clock.** `record_sightings` writes `first_seen_at` with an AWARE UTC clock and the DateTime columns read it back naive; `parse_board_date` returns naive UTC. But `search_jobs` measured `now` with a bare `datetime.now()`, which is naive **LOCAL** time — so `days = now_local - first_seen_utc` was inflated by the machine's UTC offset, **+3h in the primary market**. It never showed as an obvious error: `.days` truncates, so the skew only flips postings whose true age falls in the last three hours before a day boundary — roughly **one posting in eight, always reported a day OLDER than it is**, in an inbox where the reader cannot check it against anything.
- **`parse_board_date` DROPPED the offset instead of CONVERTING it, which is a second, larger error.** Greenhouse sends `2026-06-02T03:17:15-04:00`; `dt.replace(tzinfo=None)` reads that as 03:17 UTC when it is 07:17 UTC — four hours young. A UTC+13 board went thirteen hours old. The old docstring justified it as "day granularity is all any consumer needs", and that is exactly wrong: day granularity is what makes an offset error decide which side of a boundary the age lands on. **The old smoke check PINNED the defect** (`== _gh_dt(2026, 6, 2, 3, 17, 15)`); the assertion was fixed, not weakened, and both directions are now pinned because "convert" is trivially satisfiable in one of them by adding a constant.
- **`utc_now()` lives in `job_search.py`, NEVER in `ghost_signals.py`.** That module is source-pinned to read no clock at all, which is what makes `detect_ghost_signals` deterministic given its `now` parameter — putting the shared wall clock there to fix a bug about clocks would have deleted that guarantee. The first attempt did exactly that and the purity pin caught it.
- **Two prose traps, one after the other, both the "a grep cannot tell a promise from a call" shape** this repo already records for `resume_review` and `keyword_guard`. `ghost_signals`' own no-clock pin is a SUBSTRING check, so a new docstring that spelled out the forbidden call tripped it — the docstring now describes it as "an aware UTC clock" and says why. And the new pin on `job_search` had to become **AST**-based: that module's docstring says "never `datetime.now()` inside" in prose, so the substring version reported the promise as the violation.
- **`jobmaster.parse_jobmaster_results` was the last mixed frame** and is fixed for consistency, not accuracy: a Hebrew relative date is coarse enough that three hours never moves "לפני 3 ימים" to another day, but the `posted_at` it mints is compared against `job_search`'s UTC cutoffs, and one module keeping its own frame is how this bug happened in the first place.
- **`date.today()` in `dates.py` and `section_order.py` is CORRECT and must not be "fixed".** Resume dates are wall-clock calendar dates with no timezone at all; converting them to UTC would shift a start month for anyone east of Greenwich. The rule is one frame for *machine* timestamps, not one frame for everything.
- **The panel is a DRAWER, portalled to `document.body`, and the portal is not tidiness.** An ancestor of `DocumentPanel` carries a `transform` (a motion wrapper mid-tween), and a transformed element becomes the containing block for every fixed-position descendant — so `position: fixed` resolved against a div two thousand pixels down the page. Measured before the portal: `top 162, bottom 3316`, pinned to neither edge, on a green build. `BlockEditSheet` and `Modal` portal for the same reason (so did `AccessGate`, until Phase 29 made it render nothing).

### Phase 25 — the landing is its own route (2026-09-06)

- **`/` OWNS ITS SHELL AND ITS PALETTE, and that is what makes the redesign safe.** It used to sit inside `MarketingLayout` with `/scan`, sharing that layout's header, its `.paper` token scope and its aurora. `/scan` still does, unchanged. The landing is now a bare route rendering `LandingHeader` + `main` + its own footer inside a `.jobfinder-landing` wrapper — a THIRD token scope beside `.paper` and `.sheet`, same mechanism (re-declare `--bg` / `--ink` / `--line` / `--accent` on one subtree, so every Tailwind token utility underneath re-resolves by inheritance). Nothing in `components/landing/*` or in that CSS block can reach another route, and a browser check asserts `/scan` and `/app` mount zero `.jobfinder-landing` elements. Reusing `MarketingLayout` would have meant a `pathname === "/"` branch inside a component two routes depend on.
- **THE LANDING IS DARK BY DEFAULT AND IT MUST NOT WRITE THAT DOWN.** `useLandingTheme` resolves "explicitly saved, else dark" — where `useTheme` (the app's hook) resolves an ABSENT preference from the operating system, which would land a visitor on a light desktop in the pale composition they never asked for. While nothing is stored the hook also mirrors `dark` onto `<html>` for the LIFETIME OF THE LANDING ONLY (so the document scrollbar and `theme-color` agree with the page) and reverts on unmount; that revert is the whole reason the mirror is honest. Verified in the browser: dark on `/`, `light` handed straight back on navigating to `/app`, `localStorage.theme` still null throughout. A tap on the control IS an explicit choice and IS persisted — and unlike `useTheme.toggle` it never CLEARS the key when the new value matches the system, because doing that here would drop the visitor back onto the landing's dark default the instant they chose light on a light machine, i.e. the control would appear to do nothing.
- **The star sculpture is `lib/starfield.ts` — a seeded 3D formation, Canvas 2D, ~1450 particles.** Four things in it are load-bearing. It is a CLASS driven from a ref, never React state, because a `setState` per pointer event re-renders the landing at pointer frequency. Its geometry is SEEDED (`mulberry32`), so the sculpture is the same picture on every load and the static fallback is the same arrangement rather than a lookalike. Its draw order is sorted ONCE at build time by (halo, tint), because `fillStyle` re-parses a string on every assignment and that is the only genuinely expensive thing in a loop this size — sorted, a frame costs at most three assignments, and `globalAlpha` is a number and free. And compositing is the palette's job: `lighter` on the dark art direction so overlapping stars accumulate into a luminous nucleus, `source-over` with a quieter halo on the light one, which would otherwise bleach to white.
- **THE READING ZONE IS A DIMMER, NOT AN EXCLUSION, and the first version got that wrong in a way worth remembering.** The copy block is ~1040x500 CSS px on a 1440x900 hero, so a hard exclusion around it erased the entire formation and left what looked like debris in the corners. It dims to a 0.24 floor instead, and the composition keeps the centre quiet by putting the dense part of the sculpture somewhere else.
- **The nucleus is placed BELOW the copy, DERIVED from where the copy actually ends** (`zone.cy + zone.hh + 0.035h`, clamped), not at a fixed fraction of the hero. A constant was the first version and it fails on exactly the viewport that matters most: at 1366x768 the copy block sits ~200px lower relative to the hero than at 1440x900, and the brightest part of the formation landed directly behind the access-code line.
- **THE SCENE IS TALLER THAN THE HERO AND IS MASKED, NOT CLIPPED.** Held inside the section the composition read as a cropped photograph — the lower arms ended on a dead-straight horizontal line and the base wash stopped against the flat ground of the next section. `.lp-scene` runs **32% past** the hero, carries `.lp-space` with it, and dissolves over the overhang, so the arms thin out behind the following section's heading instead of being sliced. Three things make that work and each is a way it breaks: the bleed is a **FIXED RATIO, not a clamp**, because every position in `.lp-space` is a percentage of THAT box and a viewport-dependent bleed would slide the whole wash around (the stops are the hero-relative values divided by 1.32 — 116% becomes 87.9%, and so on, which is what keeps the composition identical to the one designed by eye); the scene sits at **`-z-10`** so it passes UNDER later sections' text rather than over it, which is also why the hero no longer carries `isolate` (a stacking context there keeps the whole hero, overhang included, painting above every later sibling); and **the landing root MUST be a stacking context** or that negative z escapes to the root element and paints behind the wrapper's own background — the entire sculpture disappears, on a green build. That last one happened; it was found by looking at the page, not by any check.
- **`Starfield.resize` takes the hero height SEPARATELY from the canvas height.** `unit` and the nucleus placement are measured against the hero; the overhang is only room for the arms. Sizing off the drawing surface would grow the sculpture and drag the nucleus down every time the fade region grew.
- **A concentration of 1px points is not a concentration.** The nucleus is two pre-rendered sprites drawn once per frame at the projected origin — where the density actually is — because at any honest per-particle alpha the centre read as slightly-denser dust. Glow sprites are pre-rendered per tint and drawn scaled; building a gradient per particle per frame, or leaning on `shadowBlur`, is how this becomes a slideshow.
- **Frames are not SCHEDULED, not merely skipped.** Offscreen (IntersectionObserver), a hidden document, `prefers-reduced-motion`, a coarse pointer, or the visitor's own Pause control each stop the loop entirely. Measured: with the scene scrolled out of view the canvas does not change at all. The pointer handler stores coordinates only and the frame resolves them against a CACHED rect, so there is no forced layout at pointer frequency; `dt` is capped at 50 ms so a restored tab cannot jump the ambient rotation.
- **THE POINTER IS TRACKED ON THE WINDOW AND NORMALISED AGAINST THE SCENE, NOT THE HERO.** Binding to the hero was right while the two were the same box, and became wrong the moment the scene overhung it — twice over. The lower third of the galaxy sits inside the NEXT section, whose content is on top and is not a hero descendant, and the scene layer is `pointer-events: none` and can never be a target; so moving over the visible lower arms fired `pointerleave` on the hero and eased everything to neutral. And the FIXED HEADER covers the hero's top 73 px without being a hero descendant either, so pointing at the top of the hero killed the parallax in exactly the same way. Measured before the fix: the same horizontal sweep moved the arms **27.9 px inside the hero and 2.9 px over the overhang**. The IntersectionObserver watches the SCENE for the same reason — watching the hero stopped the loop while up to 288 px of galaxy was still on screen.
  A consequence worth stating: normalising against the scene moves the neutral point from the hero's centre to the scene's, about two thirds down the hero, which is roughly where the nucleus sits. Resting on the bright knot is a better zero than an arbitrary one.
- **Measured, not asserted** (Playwright, 1440x900): the nucleus travels **26.3 px** between opposite hero corners and the band centroids up to 73 px, reaching 46% of the way at 45 ms and 87% at 200 ms — an exponential settle, not a snap. Under `prefers-reduced-motion: reduce` the travel is exactly **0 px** and the Pause control is not rendered at all. Paused, two frames 1.2 s apart are byte-identical and the pointer is inert.
  **These numbers replace an earlier 12.1 px / 33% / 85%, and the difference is a lesson about the probe rather than a change in tuning.** That measurement swept between opposite hero CORNERS, and the top corner is under the fixed header — which, before the pointer fix above, neutralised the scene. One endpoint of a corner-to-corner measurement was therefore not the corner at all. A probe that drives the product through its own surfaces inherits the product's bugs, and this one reported a number 2.2x too small without ever failing.
- **The Pause control is withdrawn when there is nothing to pause**, which is a different question from "is it animating right now" — reporting the latter would take the Resume button away the instant the visitor pressed Pause. It is hidden for a coarse pointer, for reduced motion, and when the 2D context is unavailable or lost.
- **The still CSS composition (`.lp-space`) is part of the design, not a placeholder.** With `getContext("2d")` forced to return null the page still paints a coherent dark space scene, renders the headline and every real link, mounts every section, and throws nothing — verified by driving it, not by reading the code.
- **The closing echo is a SEPARATE FILE with no loop in it** (`EchoCanvas`), and that separation is the point: it draws exactly one frame plus one per resize, so a second particle engine cannot be started here by accident. It is the same seeded sculpture at lower density, over the same `.lp-echo` gradient a context-less browser is left with.
- **Reduced motion zeroes the entrance DELAYS, not just the durations.** The global `prefers-reduced-motion` rule collapses `animation-duration` only, so the hero's 70-410 ms stagger still meant the headline was invisible for four tenths of a second for someone who asked for less motion. `.lp-in { animation-delay: 0s !important }` under that media query is what makes "reveal all content immediately" true. `Rise` (the section entrance) returns its children with no wrapper state at all under reduced motion, and falls back to revealing everything after 900 ms if `IntersectionObserver` never fires — a section left at `opacity: 0` because an observer did not initialise is the failure this page can least afford.

### Phase 29 — accounts, and a tracker that reads its own replies (2026-09-13)

The binding decisions came out of an adversarial design critique (29 issues, 5 blockers) and a five-dimension review of the build (34 findings kept: 6 high, 14 medium, 14 low, one of them a verdict that a suspected hole is not exploitable). Every fix below is smoke-pinned (`B<n>`) or check-mirrors-pinned (30, `F<n>`) with its false-positive half beside it.

**The gate — still ONE middleware.**
- **Every "who is calling" decision is made in `main.access_gate`, before routing.** That is what made `users.last_seen_at` able to see unrouted paths, and it is why the stamp STAYS in the gate: moving auth into a dependency would re-open that blind spot and split one decision across two places that can disagree.
- **Precedence: `X-App-Key` strictly outranks the `jf_session` cookie.** A bad key on a protected route is a 401 even beside a good cookie. **The one exception is an `_AUTH_OPTIONAL` path**, where a stale key falls through to the cookie (A10): a friend's phone still holding a dead invite code must be able to reach `/auth/login`, or it is locked out by the credential it is trying to replace. The frontend forgets a stored code when a request that carried it 401s, when `/auth/me` does not recognise it, and on any successful sign-in.
- **`_AUTH_OPTIONAL` is compared by `get_route_path(request.scope)`; `_GATE_EXEMPT` still compares `request.url.path` and needs both spellings.** The route path is bare locally and under Vercel's `/api` mount. A forgotten `/api` twin passes every smoke check, because the suite drives the unmounted app, and 401s only in production.
- **The order is credentials (401), then CSRF (403 `csrf`), then verification (403 `email_unverified`).** Credentials first, so a protected route with no credentials still says 401 rather than a misleading 403.
- **CSRF: with the gate ON, every POST/PUT/PATCH/DELETE that does not carry `X-App-Key` needs a non-empty `X-Requested-With`, cookie or no cookie, `/auth/*` included.** SameSite=Lax is not enough on its own — a top-level cross-site form POST still carries a Lax cookie — and FastAPI refusing a form body on a JSON route is an accident, not a defence. The frontend sends `X-Requested-With: jobfinder` on axios AND on the SSE `fetch`; **a new raw `fetch()` that forgets it 403s every write from that path.** With the gate OFF it applies only to a request carrying a session cookie and to `/auth/*` (FIXB B18): a keyless local request is the dev admin, and the installed Chrome extension sends no such header, so the unconditional rule 403'd it and every local script — installed software a deploy cannot update.
- **Verification skips exactly: every `_AUTH_OPTIONAL` path, `_UNVERIFIED_OK` (`/auth/resend`, `/auth/change-email`, `/auth/extension-key` — which refuses an unverified caller itself), and `DELETE /profile/account`** (the way out). Pinned: holding an unverified cookie, `POST /auth/login` for ANOTHER, verified account returns 200. Invite codes and the admin are verified by construction, and `users.signup_source` defaults to `""` so the ADD COLUMN shim grandfathers every pre-accounts user as verified.
- **The gate decides from a plain `_Identity` tuple read INSIDE the DB session, after every commit** (A11). `touch_last_seen` AND the sliding session renewal both commit, and a commit expires every attribute — the `DetachedInstanceError` recorded under `last_seen_at`, now with two writers. Pinned by a request that triggers both writes and returns 200.
- **A renewed session re-issues its cookie** (at most every 12 h, never past `SESSION_MAX_DAYS` = 180 after sign-in) unless the route itself set or cleared the cookie — re-issuing after a logout would resurrect it.

**Cookies.**
- **`jf_session` and `jf_oauth` are HttpOnly, SameSite=Lax, `Path = root_path or "/"`** — `/api` under Vercel's mount — and **`Secure` only when the request is https** (`sessions.is_https`), or local http dev silently drops the cookie. Sessions are opaque tokens stored as sha256, revocable.
- **The smoke test's Secure-cookie probe runs on a THROWAWAY TestClient and asserts the raw `set-cookie` header** (A13): a Secure cookie in the shared jar poisons every later check. New route modules read `get_settings()` per request, never a module-level `settings`, and the blank-before-import env loop sets the bool vars to `"false"`/`"true"`, because pydantic-settings raises on `""` for a bool.

**Tokens.**
- **A mailed token is bound to the address it was sent to** (A1, the critique's blocker #1). The payload stores the normalised email; consuming requires `payload.email ==` the login's CURRENT email, unconsumed, unexpired. Issuing a token consumes every earlier one of that purpose; change-email, change-password and reset consume every outstanding verify AND reset token; a reset link is single-use. A code issued before a change-email reads `used`.
- **A signup over an existing UNVERIFIED login never merges** (A3): the same password signs in (and mails a fresh code when the cooldown allows); a different one is 409 `email_taken`.
- **A reset on an unverified account verifies it, revokes every session, rotates the extension key and mints one new session** (A2). The only unverified logins that can exist belong to email signups holding no other credential, which is what makes a reset a safe takeover — and why Google sign-in and `/auth/claim` were deferred rather than built.
- **A verify LINK never mints a session and verifies only from a live session of the SAME account** (FIXB B1). Mail scanners pre-fetch GETs, so the link page needs a tap; and without the session rule a squatter signs up with someone else's address, the owner clicks "Confirm", and the SQUATTER's account is verified with its extension key one call away. Opened anywhere else it is 400 `session_required` and the page says to enter the 6-digit code on the device where the account was created. A code needs that pending session too.
- **An address is ONE plain addr-spec: `parseaddr(e)[1] == e` plus the regex** (FIXB B7). `x<victim@y.com>` was a distinct login, budget key and throttle key that SMTP delivered to `victim@y.com`. A plus tag, an apostrophe and 254 characters stay valid (pinned).

**Throttles and the security log.**
- **DB-counted, write-then-count, keyed on `HMAC-SHA256(auth_key, …)[:32]` — never plain sha256** (IPv4 reverses in seconds), and email keys are HMACs too, so a closed account leaves no plain address in `auth_events`. `auth_key` derives from `AUTH_SECRET`, else `CRON_SECRET`, else `APP_ACCESS_CODE`; rotating it resets the counters and nothing else. Client IP is the first `x-forwarded-for` hop only when `VERCEL` is set (Vercel overwrites the header), otherwise the socket address; IPv6 counts per /64.
- **Closing an account cannot reset a limit** (A7). `purge_on_close` deletes logins, tokens and sessions but only NULLs `auth_events.user_id`, because those rows are keyed on an email or a network: deleting them would make "close and re-sign-up" a way to reset the 30-wrong-codes-per-address-per-day ceiling. Pinned in exactly that shape.
- **Retention is 30 days, pruned on sign-in AND by the inbox cron** (FIXB B19). Pruning only on write left a quiet instance keeping the log forever, contradicting the privacy page. A session row's network label is an IPv4 /24 (`a.b.c.x`) or an IPv6 /48, never the full address.

**Mail budgets.**
- **200 auth mails an hour across all users, and nothing is sent over budget** (503 `email_unavailable`): the owner's SMTP account also carries the job alerts. Signup preflights the sender and the budget before creating anything.
- **Per recipient, three allowances that cannot drain each other**: verification mail 3/h (resends capped below it); **reset mail its own 3/h** (FIXB B4 — a squatter polling resends held the owner's reset link out indefinitely); and **the "password changed" security notice is EXEMPT from the per-recipient cap, global cap only** (FIXB B5 — three anonymous `/auth/forgot` calls silenced the one mail that tells the owner an attacker changed the password).

**The extension key.**
- **The key IS `users.invite_code`: a full `X-App-Key` credential with no expiry that also opens the web through "Have an invite code?"** So for an email account it is rotated on EVERY reset, password change and "sign out of other devices", in the same transaction (FIXB B1) — before, a key read by an attacker outlived all three while the copy promised "every other device was signed out". The responses carry `extension_key_rotated` and the notice mail says the key was replaced. **The admin's key is never rotated**: `APP_ACCESS_CODE` is the only way back into a deployed instance (the pinned false-positive half). A device signed in by that code stores the returned key under `ACCESS_CODE_KEY`, or its next request 401s.

**Sentry.**
- **`sentry_sdk.init` is built only by `sentry_scrub.sentry_init_options`: `include_local_variables=False` plus a `before_send` that drops frame `vars` and redacts every configured secret value** (settings named key/secret/password/token/dsn/access_code/database_url, at least 6 characters), and DROPS the event if scrubbing fails. Measured before: sentry-sdk 2.x defaults to local variables, and one exception inside an inbox sync shipped `OPENAI_API_KEY`, `CRON_SECRET` and email subjects and snippets. Mail content cannot be recognised by value, so the sync logs a failure as the exception TYPE and the failing frame's location only — never its message, never a traceback (AST-pinned). The smoke test initialises the real SDK from the same function, so the options it drives are the ones production runs.

**Gmail OAuth.**
- **The connect is bound to the browser that started it** (O1). `POST /inbox/google/start` sets `jf_oauth` (random, 600 s) and the state row stores its HMAC; the callback requires it in constant time, deletes it, and checks it BEFORE the state is consumed. A connect started with a session needs that same session back (none → `/login?next=/settings`; another account → `state_mismatch`). PKCE on top.
- **The invite-code exception is deliberate and was reviewed.** `X-App-Key` is a header Google's redirect cannot carry, so a connect started by code (the admin, the friends beta) completes on the binding cookie alone. Judged not exploitable because `CORS_ORIGINS` is an explicit list and `*.vercel.app` is on the public suffix list, so a foreign page can neither send the start request nor toss the cookie. **Widening `CORS_ORIGINS` to another origin, or moving under a shared parent domain, re-opens it.**
- **The redirect URI is built from `APP_BASE_URL`, never `request.url_for`** — behind the `/api` mount and the Vite proxy a derived URI never matches the registered one — so `google_ready` is false until `APP_BASE_URL` is set.
- **Who may connect: `INBOX_ACCESS=allowlist` (default) = `users.inbox_enabled` or admin** (O2), and since FIXB B15 the sync and the cron re-check it, so clearing `inbox_enabled` stops the reading rather than only the connect button. `GOOGLE_OAUTH_TESTING=true` sets `reauth_due_at = connected_at + 7 days`: Testing-mode grants expire weekly.
- **A grant is handed back whenever we stop holding it**: a refused callback (`missing_scope`, `profile_failed`) revokes the token it just received (FIXB B16); reconnecting as a DIFFERENT address revokes the old grant and restarts the import from its own backfill depth, while the same address revokes nothing (FIXB B8); Disconnect and the wipe report `google_revoked` false instead of claiming a revoke when `INBOX_TOKEN_KEY` is missing (FIXB B17). Refresh tokens are Fernet-encrypted (`token_crypto`, key rotation supported); **losing `INBOX_TOKEN_KEY` disconnects everyone.**

**The network door.**
- **Every call to Google goes through `google_oauth._http`: https only, host in `_HOSTS` (four Google hosts), a redirect is an error, 20 s timeout, JSON.** `gmail_api` only builds requests. **This is NOT the SSRF door and must not be "fixed" into `job_match._http_get`**: nothing here takes a URL from anyone, and for a constant URL a fixed allowlist proves the host IS Google, where `net_guard` can only prove it is public. Pinned both ways: every URL literal in the module names an allowed host, and the network is opened nowhere but inside `_http`. `_transport` is the offline seam.

**Rules before the model.**
- **The Gmail query is narrowed server-side** (I1: `after:`/`before:` in epoch SECONDS, job vocabulary en+he OR an ATS/LinkedIn application sender, `-in:sent -in:drafts -in:chats`, minus the alert senders), and the deterministic stage decides next: alert digests are noise; templated confirmations and "viewed" mails are rule-classified with NO model call — **only for a job sender and never for a Re:/Fwd: subject**, because universities and landlords write the same subject lines.
- **Everything else carrying job vocabulary reaches the model, so non-job mail with a job word in it DOES go to OpenAI.** The privacy page, Settings and the landing FAQ said such mail was set aside "before any AI sees it"; that was false and was corrected in both locales (review F2, pinned by check-mirrors 30). Keep the copy and `inbox_rules.candidate_reason` telling the same story.
- **The classifier runs on its own client, `inbox_classifier.get_inbox_llm_client`** (`INBOX_MODEL_ID`, default `gpt-4.1-nano` — see Testing). Patch THAT name to observe calls, not the client factory. The model is not trusted with the answer: evidence must appear verbatim (whitespace collapsed), the company is the HIRING employer or `""` when an agency hides it, and a platform or generic sender name (LinkedIn, Comeet, HR, Talent, `גיוס`, `צוות`…) is never a company.
- **Metering: every `/inbox/*` route is plain `Depends(current_user)`; the only charges are the `inbox` daily cap (`DAILY_INBOX_CAP`, charging what is left, never all-or-nothing) and tokens under `action="inbox_tokens"`** — never the `llm` cap, pinned by a capped friend whose `llm` row is unchanged by a sync. Both pools submit through `copy_context().run`.
- **One unreadable message may not stall the import** (FIXB B3). A message whose body read or model call fails stops the run the FIRST time with the cursor before it; the second time it is recorded as skipped — id and error code only, no subject, snippet or sender — the cursor moves past it, and it is not charged again. Before, one bad message was re-classified and re-charged every run, forever.

**The windowed backfill.**
- **The import walks FORWARD from the oldest day** (I2, a critique blocker). Gmail lists newest first, so "list after 60 days ago, take 500" imports the last week or two and skips exactly the confirmations that carry the real applied dates. The connection holds `window_lo_ms` (the next unfinished 7-day window) and `cursor_ms` (everything at or below it is handled); a run lists from `max(window_lo, cursor + 1)`, halves the window past 2,000 ids or past what the run can read in its budget, advances the cursor only across the CONTIGUOUS handled prefix with same-millisecond messages together, and moves the window only when all of it is done. Windows end 5 minutes before now so an unindexed message cannot fall behind the cursor. Once the windows reach the present the same arithmetic is the incremental sync.
- **A lease (`sync_lock_until`) keeps a cron run and a "Sync now" tap from classifying the same mail twice.** The UI runs at most 3 foreground rounds and says the import continues; the cron carries an unfinished backfill on.

**Tracker writes.**
- **Monotonic**: saved → applied → interview → offer, or rejected. An email never moves a card backwards and never changes an offer or rejected card; a different verdict waits in Needs review. Low confidence (`INBOX_REVIEW_THRESHOLD`), several candidate cards, a title similarity under 0.5, or a blank/agency company all go to review.
- **Rule 5 covers EVERY row the inbox did not write, not just manual edits** (I4). `marker = status_changed_at or created_at`; when `status_source != "email"` — manual, kit, extension and legacy `""` alike — an email older than the marker may still move a confirmation saved → applied, sends an interview/offer/rejection to review, and otherwise only links. Without it a first 60-day import lands a two-month-old rejection from a PREVIOUS application on the card made today. Writers stamp `status_source` and `applied_at`: POST, PATCH (`manual` only when the status changes) and `auto_submit`, which also stamps `status_changed_at` now (FIXB B13).
- **`execute` re-plans against the FRESH row** (FIXB B9). The plan was made from a card snapshot taken at the start of a run up to 240 s long, so a card the user dragged to Offer mid-sync was overwritten to rejected.
- **A short company name matches only as a WHOLE word of the longer one** (FIXB B10): IBM ~ IBM Israel, Wix ~ Wix.com, while HP never matches Hapoalim. The old ≥4-character floor created a phantom rejected card beside the tracked IBM one.
- **Honest dates** (I3): an inbox-created card is dated by its earliest email, and `applied_at` stays nullable and comes only from a confirmation — a rejection proves nobody's send date. The analytics bucket on `applied_at ?? created_at`.
- **Honest interviews** (I5): every matched interview email sets `interviewed` even when the status does not move, an assessment moves nothing, and **Undo clears `interviewed` only when no other interview email remains on the card** (FIXB B11). The header tile and the funnel read ONE definition, `interviewed || status === "interview"` (review F3).
- **Undo is exact, and it respects the user's edits**: an email-created card goes with its Undo only while untouched — stars, notes, a tailored resume or a hand-toggled Interviewed all count (FIXB B12) — and a kept Applied card keeps its `applied_at`. `DELETE /applications/{id}` unlinks that card's mail events, because SQLite can reuse the id. A card's timeline and Recent updates keep an UNDONE email, shown as "Undone" with no Undo button: Undo reverts the board change, it does not un-receive the email — filtered out, the invite that moved a card could no longer be seen anywhere (Phase 29 browser pass). "Add to tracker" on a review email with no detected company or title takes the subject as the card title, so it never creates a blank card — and never guesses the company from the sender's display name, which on a recruiter's mail is a person.

**Cron.**
- **`/api/inbox/cron` runs at 05:00 and 14:00 UTC as TWO `vercel.json` entries** — a Vercel Hobby cron entry fires at most once a day — beside the unchanged alerts (06:00) and nudges (07:00). That Vercel accepts two entries on one path is not yet confirmed on a deploy.
- **It FAILS CLOSED** (A12): gate on and `CRON_SECRET` empty is 503 `cron_unconfigured`, because an open copy would refresh every user's Gmail grant and spend model calls for anyone who found the URL. It is in `_AUTH_OPTIONAL` and checks its own Bearer secret, runs on a wall-clock budget checked before each user (`INBOX_CRON_BUDGET_S` = 240; each user gets `min(2 × INBOX_SYNC_BUDGET_S, what is left)`), and prunes the security log.

**The Arabic preference** (owner request, spec 07 / R1).
- **Opt-in and OFF for every user; an unreadable preference reads as OFF**, because the switch REMOVES a true fact from a document and must fail toward the one the user uploaded. It lives in `users.resume_prefs_json` behind `GET`/`PUT /profile/resume-prefs`, and `_wipe_user_rows` clears it: it implies the user's ethnicity.
- **"Is this job in Israel?" is deterministic** (`job_market.israel_market`, AST-pinned to no model, no network, no clock): a Hebrew posting, or an Israel/city token in the location or text. **Latin tokens are bounded** (Lod is inside "lodging"); **Hebrew tokens are substrings** (`בתל אביב`); "us" the pronoun is not the US; and **a posting naming no place is UNKNOWN, never "not Israel"**. `analyze_jd` stamps `JDModel.market` (`IL` / `other` / `""`) AUTHORITATIVELY over anything the model said, `stamp_market` only upgrades, `POST /jd/analyze` takes an optional `location`, kits stamp from the stored location without changing the one-argument `AnalyzeFn`, and the Jobs page prepends `Location: <location>` to the posting text rather than adding a `tailorStore` field (check-mirrors 12/13 derive that store's reset lists).
- **It applies only when the preference is on AND the market is IL AND the job does not ask for Arabic** (any requirement, preference, keyword, qualification or responsibility naming it; "selling into Saudi Arabia" is not asking). The pref on + the job asks → kept, "Arabic kept: this job asks for it"; unknown market → kept, "Arabic kept: we couldn't tell this job is in Israel", so the owner can remove it by hand; abroad, or a resume with no Arabic → nothing is said.
- **With the decision off the TAILOR message is BYTE-IDENTICAL to the call that never passed it** (pinned, driven); when it applies the message gains one instruction and nothing else.
- **Removal is deterministic, after the model, before `score_after`**: `languages` entries, and `skills` AND `skill_groups` (the two-field write, or the union validator resurrects it). A prose LIST form is removed cleanly; any other mention is REPORTED by section ("Arabic is still mentioned in your experience; edit it before sending") and left word for word. "Arabic translation", "Judeo-Arabic" and "United Arab Emirates" are not Arabic entries. The master resume is never touched.

**Numerals, and the guard re-check** (owner request, spec 07 / R2).
- **Quantity words become digits in TAILORED prose only** (summary, headline, experience/project/military bullets, project descriptions) — never titles, companies, dates, skills or the master. English: two..ninety-nine and hyphenated compounds, "one" only before a unit noun, never before of/or/and/to/the/than; a proper noun ("Seven Bridges"), "one or two", "twenty five" and a fraction stay words. Hebrew: 2-10 only as a standalone word before an allowlisted noun — `שבע`/`שש` are ordinary words, `חמש עשרה` is fifteen, a prefixed form and `שנתיים` are untouched. Idempotent, pinned.
- **The fabrication guard reads DIGITS only, so a number the model invented in words ("fifteen engineers") passed it unseen.** After a conversion the guard is re-run against a `model_copy` of the ledger whose `numbers` also hold the ORIGINAL resume's quantity phrases, built at runtime from the original resume because the kit path passes a STORED ledger. Pinned as a triple: an invented "fifteen" flags as `15`; the candidate's own "five teams" shipped as "5 teams" raises nothing; and the unextended ledger WOULD flag it, so the extension is what clears it. The ledger itself is never mutated.

**Deferred on purpose, and known open.**
- **Deferred** (each widened the account-takeover surface): Google sign-in (needs account-linking rules), `/auth/claim` for invite-code users, and the per-device sessions list with per-session revoke ("sign out of other devices" shipped instead).
- **Known open**: a job reply first filed in Spam is never imported after it is rescued (the cursor is `internalDate`-based and `messages.list` excludes SPAM); `/auth/forgot` sends SMTP inline for a known address, so its timing can reveal which addresses have accounts; `PATCH /admin/users` email edits do not update `user_logins.email`; the real Google path has run only through a fake transport (PKCE with a client secret on a Web client, the snippet on a `format=metadata` read, and the two cron entries are unconfirmed); the frontend's sync-error and refusal codes mirror the backend's by hand with no check pinning them (an unknown code falls back to a generic sentence, never a raw code); three smoke checks compare a superseded 6-digit code with the live one and would fail on a ~1-in-a-million coincidence.
